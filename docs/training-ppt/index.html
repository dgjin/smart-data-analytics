先建立整体认知。智能问数分析系统是一个自然语言数据分析平台，业内叫 NL2SQL。传统取数流程是：业务提需求、分析师写 SQL、跑数、做图、写结论，一个来回常常要半天。这个系统把链路压缩成一句中文提问——系统自动理解你要什么、在几十上百张表里圈出相关的表、生成 SQL、真实执行，再把结果转成图表和解读，最后还能一键产出高管简报。五个核心能力请记住：多源集成、自然语言交互、自动可视化、决策简报、企业级安全。特别强调第二点，遇到语义模糊系统会主动澄清而不是硬猜，这是它和普通聊天机器人的本质区别。

  • · 用业务口径词汇（知识库里有定义的词命中更准）

  • · 结果满意就点 👍 —— 系统会自动沉淀为样例，越用越准

⏱ 语义缓存

相同或等价的问题（归一化后）10 分钟内命中缓存，秒级返回，审计状态标记为 CACHE。

现在动手。第一步登录，输入账号密码，新账号会被要求先改密码。第二步，看页面顶部的数据源切换器，选你要分析的那个库——这一点很重要，因为问数的表、历史对话、推荐问题都是跟着数据源走的，选错源问出来的就不是你要的数。第三步，在输入框用中文把需求说清楚，回车提交。屏幕上会出现流式的处理进度，最后给你 SQL、数据表、图表和一段解读。右边是提问技巧：说清维度和指标，比如「按区域统计本季度销售金额」就比「看看销售」好得多；多用业务口径里的词；简单问题直接问，复杂清洗类的开深度分析；对结果满意记得点赞，系统会把这条问答自动沉淀进样例库，下次同类问题直接命中。另外重复提问十秒内必回——语义缓存十分钟有效。

很多同学好奇，回车之后那十几秒系统在干什么。看这条链路。第一关是输入防护，超长截断、注入检测；第二关鉴权限流，只有管理员和分析师能问数，每个用户还有查询配额，进行中的查询会互斥占槽，防止一个人把引擎打满。第三关查语义缓存，十分钟内同款问题直接秒回。第四关圈表，先用关键词粗排，再用向量精排，从上百张表里挑出真正相关的几张。第五关生成 SQL，这一步会把样例库里的相似问答、知识库里的业务口径注入给模型，如果语义有歧义，就在这里暂停反问用户。第六关安全执行，只放行 SELECT，行级权限强制注入。最后生成解读并审计落账。整条链路每一步都带 traceId 记录，结果出来后可以展开推导过程时间线回放，每一步用了什么 SQL、返回多少行、耗时多少，全程透明可审计。
MODULE 02 · 流式体验

SSE 流式阶段：等待时屏幕上是什么

请求以 stream 方式提交，服务端通过 Server-Sent Events 实时推送阶段事件。

understanding

语义理解中

正在理解问题语义并匹配数据字段

introspecting

数据自省中

执行探查 SQL，确认字段真实取值（需数据源开启自省）

executed

SQL 已执行

返回真实行数；SQL 就绪后即先行回显，可提前预览

analyzing

洞察生成中

基于真实数据生成解读与图表配置

📍 SQL 先行回显

SQL 生成完成即推送到界面（sql_ready），无需等待执行与解读完成——审核 SQL 的同事可以提前介入，发现口径问题可提前终止。

🛟 降级兜底

AI 引擎或数据库暂时不可用时，返回带明确标识的示例数据，界面不白屏；审计状态记为 FALLBACK，方便事后追溯。

等待的那段时间，屏幕不是空白转圈，而是实时告诉你系统进行到哪一步了。四个阶段：understanding 在理解语义；introspecting 是数据自省，只有数据源开了自省开关才会出现，它在真正出数前先探查一下字段里的真实取值；executed 表示 SQL 已经在数据库执行完，拿到真实行数了；analyzing 是最后的解读生成。这里有个很实用的细节：SQL 一生成完就会先行回显到界面上，不用等整条链路跑完。懂 SQL 的同学可以在这个窗口期先审一眼口径对不对，不对就提前停，省时间。另外记住降级兜底机制：万一大模型或者数据库临时不可用，系统会返回带明确标识的示例数据，保证界面不白屏，同时审计里记 FALLBACK，绝不会拿演示数据冒充真实结果。
MODULE 02 · 准确率保障

歧义澄清：问不准时，系统会反问

🤔 触发场景

「客户」可能指对公客户也可能含个人；「余额」可能是表里三个不同字段。此时系统不直接执行 SQL，而是返回澄清问题与候选理解，由用户点选确认后重新提交。

✅ 为什么重要

  • · 宁可多问一句，不给一个「看起来对」的错数
  • · 候选理解来自真实表结构，点选即可，无需改写问题
  • · 澄清结果随上下文带入，多轮对话不重复追问

让问数更准的四重机制

few-shot 样例注入

从 SQL 样例库挑选与问题最相似的 top-3「问题-SQL」对注入上下文

知识库 RAG

业务术语、口径、字段含义按相关性检索注入，带 token 预算控制

语义指标命中

问题命中登记的指标名/同义词时，直接模板化注入标准口径

反馈自学习

点赞自动沉淀样例（FEEDBACK_UP），点踩作为反例注入避免重蹈覆辙

这一页回答一个高频疑问：系统会不会理解错？会——但它的设计原则是宁可反问，绝不硬猜。比如你问「客户余额」，库里可能有好几个余额字段，这时系统不执行，而是把候选理解列出来让你点选，选完自动重新提交。右边四重机制让准确率随使用不断提升：第一，样例库注入，和你的问题最相似的三条历史问答会作为范例给模型参考；第二，知识库检索，业务口径和术语定义按相关性注入；第三，语义指标，问题里一旦命中管理员登记的指标名或同义词，标准口径直接模板化注入，保证同一个指标全系统算法一致；第四，反馈闭环，你点的每一个赞都会变成新样例，点踩则会作为反面教材提醒模型别再犯同样的错。所以这个系统是用得越多越懂你的业务。
MODULE 02 · 进阶模式

三个进阶开关与模型自选

计划模式

先出计划，批准再执行

提问后先生成分析计划（编号步骤、涉及表，不执行），展示计划卡片供批准；批准后携带 planId 执行。计划 10 分钟有效、一次性消费，过期或问题不匹配返回 409。

深度分析

中间表清洗链

复杂问题自动多步清洗（去重 / 标准化 / 过滤 / 聚合），逐步物化为 ait_* 中间表（TTL 24 小时，每用户最多 10 张），最终 SQL 只引用中间表；清洗失败不阻断主链路。

数据自省

先探查再生成

数据源级开关（默认关）。开启后模型可先执行一条探查 SQL（DISTINCT 取值 ≤30 行回喂），解决「取值不确定」型歧义。仅首轮一次，防止递归。

🎛 模型自选

输入框旁模型下拉实时列出可用模型（含本地 Ollama 已安装模型），选择随提问生效、持久化到浏览器；不同模型结果缓存互相隔离。

🧭 怎么选？

日常问数：默认即可；重要汇报口径：开计划模式先审步骤；数据脏、口径绕：开深度分析；字段取值拿不准：让管理员开自省。

这三个开关是分析师的进阶武器。计划模式适合重要场合：先看计划再执行，流程完全可控——系统列出编号步骤和要用的表，你批准了它才动手，而且计划十分钟内有效、用一次作废，防止拿着旧计划反复跑。深度分析对付脏数据和多步口径：系统会分步清洗，物化成 ait 开头的中间表，二十四小时自动清理，单人最多十张，不会把库占满；就算清洗失败，主链路照常出结果。数据自省是管理员在数据源上开的开关，让模型出 SQL 前先偷看一眼字段里的真实取值，解决「取值不确定」的歧义，只允许一轮，不会无限套娃。最后模型下拉，大家可以按需切换模型，不同模型的结果互不干扰。选择建议写在右下角，按场景开开关就好。

MODULE 03 · 数据安全

数据安全：四道防线层层设防

防线一 · 只读执行

所有问数与样例 SQL 强制走 SELECT 白名单校验（AST 解析），字符串字面量在校验副本中置空防关键字干扰，杜绝注入与写操作。

防线二 · 行级权限

数据源 scope 可登记行过滤谓词（如 region LIKE '安徽省%'）；所有真实执行链路（问数 / 报表 / 重跑 / 下钻）执行前由 AST 强制包裹为过滤派生表，注入失败一律 fail-closed 拒绝查询。

防线三 · 敏感信息过滤

Schema 上下文加载时剔除敏感列——AI 根本「看不见」这些字段，从源头防止敏感数据进入提示词与结果；数据源密码加密落库。

防线四 · 审计与限流

每次问数审计落账（SUCCESS / FALLBACK / CLARIFY / CACHE / DENIED）；API 访问日志含被拒请求；限流 + 每用户配额 + 并发槽互斥。

设计哲学：权限不是「建议」，是执行层强制——AI 生成的任何 SQL 都逃不出这四道防线；宁可拒绝查询（fail-closed），绝不越权出数。

安全这一页请管理员务必记住，也请分析师放心。第一道防线只读执行：AI 生成的每条 SQL 都经过解析器白名单校验，只能 SELECT，写操作和注入根本进不了数据库。第二道行级权限：可以按数据源配置行过滤，比如某个分析师只能看安徽省的数据，那他无论怎么问，SQL 都会被强制包上一层过滤条件，覆盖子查询、联合、连接各种写法，注入失败就整个拒绝，宁可不出数也不越权。第三道敏感信息：敏感列在 AI 读表结构那一步就被剔掉了，模型压根不知道有这个字段，提示词里不会出现，结果里自然也没有。第四道审计限流：每次提问都有审计状态，谁在什么时间问了什么、走没走缓存、有没有被拒，全部留痕。一句话总结：这个系统里，权限是墙不是帘子。

🔒 敏感数据怎么选

涉密数据源的分析全程走本地 Ollama，提示词与结果不出内网；云端引擎仅用于非敏感场景——由管理员在引擎配置中约束。

AI 引擎是这个系统的大脑供给线，目前接入三家。当前主力是本地部署的 Ollama 跑 deepseek-r1 三十二 B：数据完全不出内网，推理能力也足够应付复杂口径，敏感场景放心用。云端两家，Qwen 的 qwen3.8-max 参数量大、长上下文强，适合高峰分流和高质量需求；Gemini 作为第三选择扩展多样性。这里最值得讲的是故障转移：主引擎挂了，系统按管理员配置的顺序自动切到下一个可用引擎，用户几乎无感；万一全挂了，还有演示数据兜底，界面照常出结果但明确标识降级，审计记 FALLBACK。涉密数据的用法也强调一下：让管理员把敏感源的分析锁定在本地引擎上，提示词不出去，数据不出去，合规安心。
MODULE 04 · 安全合规

安全合规全景：账号、数据、审计三张网

账号与会话
  • · JWT 会话令牌，接口层统一鉴权
  • · 密码加密存储，永不明文回显
  • · 新账号首登强制改密
  • · 越权访问 403 + 路由重定向
数据防线（回顾 P15）
  • · SELECT 白名单（AST 解析）
  • · 行级权限强制注入，fail-closed
  • · 敏感列对 AI 不可见
  • · 数据源密码加密落库
审计与限流
  • · 问数审计五态：SUCCESS / FALLBACK / CLARIFY / CACHE / DENIED
  • · API 访问日志含被拒请求
  • · 限流 + 每用户配额 + 并发槽互斥
  • · 推导过程 traceId 全程可回放

合规要点：本地引擎方案下，提问、表结构、结果数据全程不出内网；全链路审计留痕满足内审与监管检查「谁在何时查了什么、看到了什么」的追溯要求。

安全讲了两页，这页收个总。三张网：账号层，JWT 会话加接口统一鉴权，密码加密存储永不明文回显，新账号强制改密，越权直接 403；数据层就是前面讲过的四道防线——只读白名单、行级权限、敏感列屏蔽、密码加密，这里列出来帮大家复习；审计层，每次问数落审计账，五种状态：成功、降级、澄清、缓存、拒绝，被拒的请求也记录，配上限流配额和并发槽，既能追责也能防滥用。合规角度总结一句话：用本地引擎部署时，从提问到表结构到结果数据全程不出内网；每个数字都能回答「谁、什么时候、问了什么、看到了什么」。这套体系拿去应对内审和监管检查，材料都是现成的。安全不是绊脚石，是这套系统能进生产环境的前提。

WRAP-UP · 总结与答疑

常见问题 FAQ

Q1 · 总是让我澄清？

说明问题里有系统拿不准的词。用业务口径提问、指明维度与指标；反复出现的术语建议管理员沉淀进知识库或登记为语义指标。

Q2 · 数字和报表对不上？

依次检查：数据源选对了没有 → SQL 预览里口径是否符合预期 → 是否被行级权限过滤（属正常现象）→ 结果标记是真实执行还是 FALLBACK 演示。

Q3 · 忘记密码 / 想问数没权限？

联系管理员重置密码（重置后首登强制改密）；只读用户需要问数时，由管理员评估后将角色调整为 ANALYST。

Q4 · 结果能直接对外引用吗？

重要场合先开计划模式审步骤，出数后用 SQL 预览复核口径，确认 dataProvenance 为真实执行；点 👍 沉淀样例，保证下次同口径复现。
