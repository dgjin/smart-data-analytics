# 混沌工程演练手册（依赖断连场景）

> 版本：v0.9.115 ｜ 适用对象：运维 / 值班 / 后端 ｜ 配套脚本：`scripts/chaosDrill.ts`（`npm run chaos:drill`）
> 关联能力：健康检查分级（3.21）、限流与查询缓存降级、Prometheus 指标、链路追踪（3.28）

## 1. 目的

回答一个问题：**依赖（Redis / MySQL）挂掉时，系统会怎样？我们怎么证明？**

本手册给出可重复、可留痕、默认安全的演练方法：脚本按「基线 → 注入 → 观察 → 恢复 → 冷却」采样
`/api/health/live`、`/api/health/ready` 与 `/metrics`，逐条比对下方降级契约，产出 JSON + Markdown 报告。
前置依赖为零（不需要 Docker、不需要 root），只要求目标服务在跑。

## 2. 降级契约（判定的唯一口径）

| 依赖 | 观测信号 | 期望行为 | 代码位置 |
| --- | --- | --- | --- |
| Redis | `/api/health/ready` | 503，`checks.redis.ok=false`，MySQL 仍 `ok=true`（故障不扩散） | `server/infra/health.ts` |
| Redis | `/api/health/live` | 恒 200 —— 进程不因依赖故障退出或被编排系统重启 | `server.ts` |
| Redis | 限流（登录/分析/Agent 等写接口） | **fail-closed**：存储异常一律 429，宁可拒绝也不放行，防止断连期被打穿 | `server/infra/rateLimiter.ts` |
| Redis | 查询缓存（L1/L2） | **fail-open**：读异常按未命中返回、写异常静默，业务继续打真库 | `server/query/queryCache.ts` |
| Redis | OIDC 登录 state | **fail-closed**：写不进 state 即登录失败（可重试），不签发无法校验的 state | `server/auth/oidc.ts` |
| Redis | 计划类一次性凭据（`qp:`/`ap:`/`rqp:`） | 读失败按无效处理，用户重新生成计划即可 | `server/query/queryPlan.ts` 等 |
| MySQL | `/api/health/ready` | 503，`checks.mysql.ok=false` | `server/infra/health.ts` |
| MySQL | 业务查询 | 5xx / 明确错误信息，不返回伪造数据 | `server/query/sqlExecutor.ts` |
| 两者 | `/metrics` | 始终可抓取（进程存活即可），`process_start_time_seconds` 全程不变 | `server/infra/monitoring.ts` |

> 口径与自动化测试一致：`server/infra/rateLimiter.test.ts`（5 例，含 fail-closed）与
> `server/query/queryCache.test.ts`（Redis 断连 2 例，fail-open）。**单测保证语义，脚本验证真实环境。**

## 3. 注入手法分级（先选轻的）

| 级别 | 手法 | 对数据的影响 | 适用 |
| --- | --- | --- | --- |
| **L1 卡顿** | Redis：`redis-cli -p 6379 CLIENT PAUSE 15000 ALL`，恢复 `CLIENT UNPAUSE` | 无（内存数据保留） | 默认推荐；验证超时/Fail-fast/降级全链路 |
| **L2 进程** | `brew services stop redis` / `docker compose stop redis` / `systemctl stop mysql` | **可能丢失未持久化的 key**（Redis 停机会丢弃未落盘数据） | 验证「连接被断开」与重连退避 |
| **L3 网络** | 防火墙 drop 对应端口（`pf`/`iptables`） | 无（数据保留），但需要 root | 最接近真实网络分区；生产演练首选 |

**默认安全边界**：脚本 **plan 模式不做任何注入**，只采基线并打印命令建议；只有显式
`--execute --yes` 才真正执行，且命令必须过危险词黑名单（`rm -rf`/`DROP`/`shutdown`/`mkfs` 等直接拒绝）。
目标地址默认只允许本机/私网，公网需 `--allow-remote`。

### 3.1 演练前检查清单

1. 服务已启动且 `/api/health/ready` 返回 200（preflight 会自动校验）。
2. `REDIS_URL` 已配置 —— 未配置时 readiness 不含 redis 探测，脚本会直接报错退出（无法区分"注入导致"与"本就故障"）。
3. 生产/共享环境：记录 `redis-cli DBSIZE`、`redis-cli INFO persistence | grep rdb_last_save_time`，
   确认持久化正常；有条件先 `BGSAVE`。也可直接 `curl -f http://127.0.0.1:3000/api/health/persistence`
   看落盘年龄与未落盘写入数（v0.9.116 新增；stale/failed 时返回 503，便于停服演练前的自检）。
4. 了解 Redis 中只有**临时态**（缓存/限流计数/锁/一次性计划），无持久业务数据（业务数据在 MySQL）：
   断连影响为「缓存冷启动 + 进行中的计划需重提 + 限流计数清零」，不会丢业务数据。
5. 选变更窗口；确认 `/metrics` 是否需要 `METRICS_TOKEN`（需要时传 `--metrics-token=`）。
6. 明确恢复命令，并保证执行人能在演练中止时立即恢复。

## 4. 执行

```bash
# 1) plan：零副作用，先看基线与建议命令
npm run chaos:drill -- --scenario=redis

# 2) L1 卡顿型演练（推荐默认）
npm run chaos:drill -- --scenario=redis --execute --yes \
  --inject-cmd="redis-cli -p 6379 CLIENT PAUSE 15000 ALL" \
  --recover-cmd="redis-cli -p 6379 CLIENT UNPAUSE"

# 3) L2 进程型演练（会丢未落盘数据，谨慎）
npm run chaos:drill -- --scenario=redis --execute --yes \
  --inject-cmd="brew services stop redis" \
  --recover-cmd="brew services start redis"

# 4) 人工已停库，脚本只负责观察 + 恢复
npm run chaos:drill -- --scenario=mysql --assume-injected --yes \
  --recover-cmd="brew services start mysql"

# 5) 双依赖同时断（验证故障叠加与恢复顺序）
npm run chaos:drill -- --scenario=both --execute --yes \
  --inject-cmd="..." --recover-cmd="..."
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--scenario=redis\|mysql\|both` | `both` | 注入目标 |
| `--base-url=` | `http://localhost:3000` | 目标服务（仅本机/私网，公网需 `--allow-remote`） |
| `--metrics-token=` | `METRICS_TOKEN` | `/metrics` 鉴权 |
| `--baseline-ms=` | 6000 | 基线采样时长 |
| `--settle-ms=` | 5000 | 注入后等待故障稳态（覆盖 ioredis 重试退避，最大 3s） |
| `--observe-ms=` | 12000 | 故障观察采样时长 |
| `--cooldown-ms=` | 4000 | 恢复后冷却采样时长 |
| `--interval-ms=` | 2000 | 采样间隔 |
| `--recover-timeout-ms=` | 60000 | 恢复轮询上限 |
| `--execute` / `--assume-injected` | — | 互斥：脚本注入 / 人工已注入 |
| `--yes` | — | 跳过交互确认（CI 必须显式给出） |
| `--out-dir=` | `logs/chaos-reports` | 报告目录（`logs/` 已 gitignore，产物不入库） |

**退出码**：`0` 断言全通过（或 plan 正常完成）｜`1` 存在失败断言 ｜`2` 环境不可达/参数非法/安全拒绝。

## 5. 断言与通过标准

| 断言 | 含义 |
| --- | --- |
| `baseline-healthy` | 注入前 live 与 ready 均 200（否则演练无意义） |
| `live-always-200` | 故障期 live 恒 200：依赖故障不得引发进程退出/重启 |
| `ready-503` | 故障期 ready 恒 503：上游可据此摘流量 |
| `injected-dependency-failed` | 被注入依赖的探测项为 `ok=false` |
| `peer-still-healthy` | 单依赖故障时对侧仍 `ok=true`（不扩散） |
| `recovered` | 恢复命令后 ready 在 `--recover-timeout-ms` 内回到 200，并记录耗时 |
| `cooldown-stable` | 冷却期 ready 稳定 200，无抖动 |
| `no-process-restart` | `process_start_time_seconds` 全程不变，证明上述 200 不是"重启后恰好健康" |

全部通过才判定 PASS。**任何一条 FAIL 都视为发现缺陷**，按第 8 节留档并转 issue。

## 6. 报告

每次演练在 `logs/chaos-reports/` 生成同名 `.json`（机器可读，含逐次采样）与 `.md`（人工阅读）：
断言明细 → 阶段采样表（live/ready/各依赖探测）→ 指标快照（基线/观察/冷却）→ 注入与恢复命令及退出码。
需要归档时把 `.md` 复制到 `docs/` 或工单附件，不要把 `.json` 提交进仓库（含内网地址）。

## 7. 已执行记录

| 日期 | 场景 | 手法 | 结果 | 恢复耗时 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 2026-10-22 | Redis | L2 `brew services stop redis` | 8/8 PASS | 4010ms（3 次轮询） | 故障期 8 次采样全部 503，MySQL 全程 ok；进程未重启 |
| 2026-10-22 | Redis | L1 `CLIENT PAUSE 15000 ALL` | 8/8 PASS | 3ms（1 次轮询） | 数据保留验证：pause 前写入的 key 演练后仍存在 |
| 2026-10-22 | MySQL | L2 `mysql.server stop` | 8/8 PASS | 4ms（1 次轮询） | 故障期 7 次采样全部 503，Redis 全程 ok；进程未重启 |

**复盘（L2 轮次的真实副作用）**：本机 `brew` 管理的 Redis 在停止前未落盘（RDB 停留在 8 天前），
停服后 1254 个临时 key 丢失 —— 因为全是缓存/计数/锁/一次性计划，业务无损，但说明：
**停服式注入必须预估"内存数据清零"**；生产演练优先选 L1（`CLIENT PAUSE`）或 L3（网络隔离），
既贴近真实故障又不丢数据。同时暴露了一个环境隐患：Redis 的 RDB 长期未更新，应检查持久化配置与目录权限。

## 8. 失败后的处置

1. **先恢复环境**（脚本已尽力执行 `--recover-cmd`；未提供则立即人工恢复），确认 `/api/health/ready` 200。
2. 从报告定位失败断言对应的阶段采样行（`at` 时刻 + live/ready/checks），结合 `logs/` 中的应用日志与
   `/api/ops/traces` 的慢请求瀑布复现。
3. 判定是**契约缺失**（代码需改）还是**预期漂移**（契约需改）：前者提缺陷修代码并补单测；
   后者更新本手册第 2 节并同步说明书。
4. 把报告 `.md` 归档到工单，注明版本（`package.json` version）与提交号。

## 9. 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| preflight 报 live 不可达 | 服务未启动/端口不对 | `npm run dev` 或 `--base-url=` 指定实际地址 |
| preflight 报「缺少 redis 探测项」 | 未配置 `REDIS_URL`，readiness 不含 redis | 配置 `REDIS_URL` 后重启服务；或改测 mysql 场景 |
| 故障期 ready 仍 200 | 注入命令未生效 / 目标不是同一实例 | 检查命令退出码；`--base-url` 是否指向被注入的实例 |
| 恢复一直超时 | 恢复命令失败 / 依赖启动慢 | 手动执行恢复命令并看输出；调大 `--recover-timeout-ms` |
| `/metrics` 403 | 配了 `METRICS_TOKEN` 但未传 | 追加 `--metrics-token=...` |
| 脚本拒绝执行命令 | 命中危险词黑名单 | 演练只允许"停/启依赖"，改写命令，不要绕过 |

## 10. 与 CI 的分工

- **CI（每次提交）**：跑 `server/infra/rateLimiter.test.ts` 与 `server/query/queryCache.test.ts` 中的降级用例，
  锁死 fail-open / fail-closed 语义，防回归。
- **环境级（发布前 / 季度演练）**：用本脚本对真实部署做一次 Redis 与 MySQL 演练，报告归档。
- 两者缺一不可：单测证明"代码写对了"，演练证明"部署环境里真的这样"。
