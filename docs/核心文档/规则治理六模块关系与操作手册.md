# 规则治理六模块关系与操作手册

> 适用版本：v0.9.110（业务本体 M1/M2、上下文仲裁器、统一记忆体已上线）
> 适用对象：系统管理员（ADMIN）为主要操作者，分析师（ANALYST）可参与指标提议
> 文档定位：说明「系统管理 → 规则治理」六个 Tab 各自管什么、彼此是什么关系、按什么顺序配置、配完怎么验收。所有口径均以当前代码实现为准，不描述未上线的规划能力。

---

## 0. 先看结论：三条主线

规则治理不是六个互不相干的配置页，而是同一条问数链路上的六个「上下文供给源」。理解下面三条主线，就能理解全部关系：

1. **谁决定 SQL 的「算法」**：铁律规则 > 语义指标 > 业务本体 > 业务口径摘要（Schema 维度/指标摘要）> 业务知识库。
   这是上下文仲裁器 `CONTEXT_PRIORITY` 的固定顺序，越靠前的块越晚被裁剪、越不可能被覆盖。
2. **谁决定 SQL 的「写法」**：SQL 样例库提供 few-shot 示例，只教形式（表选择、聚合风格、别名习惯），不定义口径；与铁律/指标冲突时一律按铁律/指标执行。
3. **谁决定答案的「口吻」**：专家角色只作用于阶段二（结果解读），按问题关键词路由，完全不参与 SQL 生成。

一句话概括六个模块的分工：

| Tab | 一句话定位 | 生效方式 | 是否按问题检索 |
|---|---|---|---|
| 语义指标 | 定义「指标怎么算」的权威口径 | 命中指标名/同义词才注入 | 是（子串匹配） |
| 铁律规则 | 定义「绝对不能怎么做」的红线 | 全部 ACTIVE 规则恒注入 | 否（全量） |
| 业务本体 | 定义「业务词对应哪张表哪个值」 | 实体命中后四段软注入 + 圈表加权 | 是（实体命中） |
| 业务知识库 | 沉淀口径/术语/枚举/规则的自由文本 | 向量 + 词法混合检索注入 | 是（RAG） |
| SQL 样例库 | 提供高质量「问题-SQL」对作 few-shot | 相关性打分后按预算注入 | 是（打分） |
| 专家角色 | 决定解读视角与专业话术 | 阶段二按关键词路由 | 是（关键词） |

## 1. 入口、权限与共同约束

### 1.1 入口位置

- 前端路径：左侧「系统管理」→「治理与审核」分组 →「规则治理」，页面顶部六个 Tab：**语义指标 / 铁律规则 / 业务本体 / 业务知识库 / SQL 样例库 / 专家角色**。
- 该入口仅在 ADMIN 身份下渲染；ANALYST/VIEWER 登录后进入业务工作台，看不到此页面。
- 六个 Tab 中，前五个各自带「数据源」下拉（按数据源隔离配置），**专家角色是全局配置，没有数据源维度**。

### 1.2 权限矩阵（后端真实校验）

| 模块 | 读取 | 写入 / 治理 | 特殊说明 |
|---|---|---|---|
| 语义指标 | 所有登录用户 | 新建：所有登录用户（ADMIN 创建即 ACTIVE，其他角色创建为 PENDING）；编辑/删除/审批/驳回/版本回溯/导入导出：仅 ADMIN；重新提议：提议人本人或 ADMIN | `POST /api/metrics/query` 允许 ADMIN + ANALYST（统一指标查询） |
| 铁律规则 | 仅 ADMIN（整个路由 `requireRole('ADMIN')`） | 仅 ADMIN | 创建即生效，无审批流 |
| 业务本体 | 所有登录用户（summary/entities/value-notes/relations/hierarchies/path） | 仅 ADMIN（含绑定、版本历史、回滚） | 写操作创建即 ACTIVE 并留版本快照 |
| 业务知识库 | 所有登录用户（文档列表/详情/预置条目） | 仅 ADMIN（新增/编辑/删除/导入/导出） | 外部知识源整体仅 ADMIN |
| SQL 样例库 | 所有登录用户（列表） | 仅 ADMIN（登记/编辑/删除/批量/反推/导入导出） | 点赞反馈会自动沉淀 FEEDBACK_UP 样例 |
| 专家角色 | 仅 ADMIN | 仅 ADMIN | 内置角色可编辑不可删除 |

### 1.3 六条共同约束（务必先理解）

1. **只注入 prompt，不拼 SQL**：六个模块产出的都是自然语言/结构化文本，最终由 LLM 生成 SQL，再经安全执行层校验。任何模块都不能绕过执行层。
2. **执行层 Schema 白名单是最终兜底**：本体关联路径、知识库写法、样例里的表名，只要不在当前用户可见的 Schema 白名单内，生成的 SQL 依旧会被拦截。本体和知识库不会「放开」表列权限。
3. **按数据源隔离**：同一份指标/铁律/本体/知识/样例只对登记时选中的数据源生效。跨数据源复用要走导出再导入。
4. **变更即时生效**：指标、铁律、知识库、样例、专家角色的写操作都直接落库；专家角色有 60s 读缓存，但写操作会即时失效缓存。
5. **失败降级不阻断**：任一模块加载/检索失败，问数链路按「该模块无命中」继续，不会中断问数。
6. **与「数据源与 Schema」分工**：Schema 负责「有什么表、什么列、列的中文含义、表级业务口径」；规则治理负责「业务上怎么算、不能怎么算、业务词怎么映射」。表级业务口径说明（`businessNote`）的编辑入口在数据源页，且它作为 Schema 的一部分直接注入、不参与仲裁；仲裁器里的「业务口径」块实际是 Schema 的维度/指标摘要（见 2.2、4.4）。

## 2. 总览：六个模块在问数链路中的位置

### 2.1 问数主链路（真实执行顺序）

```text
用户问题
  │
  ├─[0] 数据源上下文：Schema（含表级业务口径 businessNote）+ 权限过滤 + 敏感字段移除
  │
  ├─[1] 业务本体加载（ONTOLOGY_ENABLED，默认开）
  │      └─ 实体命中（名称/别名 +10、描述 bigram×2；多命中时 embedding 余弦×10 精排）
  │      └─ 绑定加权 → 表级 boost（IDENTITY +8 / RELATION_KEY +4 / ATTRIBUTE +3，单表封顶 +15）
  │
  ├─[2] Schema 圈表（关键词粗排 + embedding 精排，本体 boost 参与打分）
  │
  ├─[3] 七路并行召回 + 统一记忆体（互不依赖，各自失败降级）
  │      ├─ SQL 样例库（few-shot）
  │      ├─ 业务知识库（本地 RAG）
  │      ├─ 外部知识库（企业 RAG）
  │      ├─ 语义指标（ACTIVE 指标按名称/同义词命中）
  │      ├─ 点踩反例（默认 2 条）
  │      ├─ 个人对话沉淀（本人历史成功问答）
  │      ├─ 铁律规则（ACTIVE 全量）
  │      └─ 统一记忆体（8 通道，命中时覆盖上述七路结果）
  │
  ├─[4] 宽表列级裁剪（>50 列的表只注入 top-N 列；指标引用列/主键强制保留）
  │
  ├─[5] 业务本体提示词构建（实体/值域/关联路径/业务层级四段，预算默认 1500 tokens）
  │
  ├─[6] 复杂度评估 → 必要时中间表清洗链
  │
  ├─[7] 上下文仲裁：铁律 > 指标 > 本体 > 业务口径 > 知识
  │      ├─ 跨块去重
  │      ├─ `表.列 = 值` 冲突裁剪（低优先级行丢弃并记 warning）
  │      └─ 总预算默认 6000 tokens，从最低优先级尾部逐行裁剪
  │
  ├─[8] 阶段一 system prompt 拼接（固定顺序，见 2.2）→ LLM 生成 SQL
  │
  ├─[9] 安全执行（SELECT-only + 表白名单 + 行级权限 + 超时）→ 失败回喂重试（最多 3 次）
  │
  └─[10] 阶段二解读：专家角色路由（ACTIVE 按 sortOrder 升序关键词匹配，default 兜底）
```

### 2.2 阶段一提示词的固定拼接顺序

```
Schema → 已批准计划 → 中间表 → 业务笔记（表级业务口径）→ 铁律 → 指标 → 本体 → 业务口径摘要 → 知识 → few-shot → 反例
```

注意两个容易混淆的点：

- **业务笔记（`extractBusinessNotes`）** 直接从 Schema 的 `businessNote` 字段提取，拼在 Schema 之后、铁律之前，**不经过仲裁器**。
- **业务口径摘要（`guidance`）** 是 Schema 摘要（每张表的维度列/指标列清单），作为仲裁器五块中的一块参与裁剪。

### 2.3 仲裁器的四步处理（对应代码里的三类规则）

| 动作 | 规则 | 结果 |
|---|---|---|
| 排序 | 固定 `iron → metric → ontology → guidance → knowledge` | 高优先级块先登记，低优先级块后处理 |
| 去重 | 规范化空白后整行比对，已出现过的行直接丢弃 | 跨块重复行只保留高优先级那份 |
| 事实冲突 | 识别 `表.列 = 值` 形态；同 key 不同值且来自不同块时，丢弃低优先级行并记 warning | 冲突不只影响排序，会真的删行 |
| 预算裁剪 | 总 token 超预算时，从 knowledge 块尾部开始逐行弹出，最后才动 iron | 铁律几乎不会被裁 |

规范化细节：值会去引号、去空白、转小写后比较（`'1'`、`1`、`A`/`a` 视为同值）；占位符（`值`、`value`、`xxx`）与空值不参与冲突判定。

### 2.4 报表链路与问数链路的差异（重要）

| 能力 | 问数链路 | 报表链路（`liveReport`） |
|---|---|---|
| 语义指标 | 命中注入 | 命中注入（主题+额外要求参与匹配） |
| 铁律规则 | 全量恒注入 | 全量恒注入 |
| 业务知识库 | 检索注入 | 检索注入（与问数同一函数、同一预算） |
| 业务本体 | 圈表加权 + 四段注入 | **未接入** |
| 上下文仲裁器 | 生效（6000 tokens） | **未生效**，按 `指标 → 铁律 → 知识` 直接拼接 |
| 专家角色 | 阶段二解读 | 不适用 |

因此：**报表端只看得到指标、铁律、知识三类规则**。只在本体里登记、没写进知识库的口径，报表不会遵守。若某条规则对报表同样重要，应同时写入铁律或知识库。

### 2.5 统一记忆体的覆盖关系

v0.9.106 起可选启用统一记忆体（`MEMORY_ROUTER_ENABLED=off|shadow|on`，默认 off）。启用后：

- 八通道：`IRON / METRIC / KNOWLEDGE / EXTERNAL / EXAMPLE / NEGATIVE / CONVERSATION / CORRECTION`。
- 铁律与指标为**强制段**（`forced`），其余通道共享总预算（默认 6000 tokens）。
- 通道预算：纠错 600、知识 2700、外部 1200、few-shot 3600（example + conversation 共享）、反例 2 条。
- 单通道超时 400ms，Router 整体超时 800ms，超时按无命中处理。
- **命中时覆盖七路结果**：`metricPrompt / ironRulesPrompt / knowledgeBlock / fewShotPairs / negativeExamples` 全部改用记忆体返回；未命中或未启用则回退原七路逻辑。
- `shadow` 模式只召回、写留痕、不注入，适合上线前对比。

对治理的含义：如果开启记忆体，规则治理的改动仍需经过记忆体召回才进入 prompt；`shadow` 模式下改了配置也「看不到效果」，这是预期行为，不是配置没生效。

## 3. 六个模块逐项操作手册

### 3.1 语义指标（语义指标 Tab）

#### 3.1.1 它解决什么问题

同一句「不良率」，不同人可能写成 `COUNT(不良)/COUNT(全部)`、`SUM(不良余额)/SUM(总余额)`、带不带核销、按不按五级分类，结果能差一倍。语义指标把这套算法固化成结构化定义，问题命中关键词后强制 LLM 使用同一口径。

#### 3.1.2 命中与生效规则

- 加载：`loadActiveMetrics` 只取 `status='ACTIVE'`，按 `id` 升序最多 200 条。**超出的第 201 条以后不参与问数**（管理列表仍可见，最多 500 条）。
- 命中：指标名或任一同义词作为**子串**出现在问题中即命中（确定性、零延迟、不做模糊匹配）。
- 注入：`buildMetricPrompt` 逐条输出「名称（同义词）= 表达式，基于表 X，固定过滤条件，可切分维度，口径说明」。
- 阶段一约束：问题涉及命中指标时，必须使用给定表达式、归属表、固定过滤；按维度切分只能使用登记的可切分维度列。

#### 3.1.3 字段与校验上限

| 字段 | 必填 | 上限 / 规则 | 说明 |
|---|---|---|---|
| 指标名 name | 是 | ≤50 字，数据源内唯一 | 命中匹配的主键 |
| 同义词 aliases | 否 | ≤10 个，每个 ≤50 字，不能与指标名相同 | 参与子串命中 |
| 口径说明 description | 否 | ≤300 字 | 面向人的解释，也注入 prompt |
| 聚合表达式 expr | 是 | ≤200 字，禁止多语句（`;` 后接内容） | 如 `SUM(CASE WHEN ... THEN amt END)` |
| 归属表 tableName | 是 | 合法标识符 `^[A-Za-z_]\w*$` | 必须与 Schema 表名一致 |
| 固定过滤 filters | 否 | ≤300 字，禁止多语句 | 如 `status = 'active'` |
| 可切分维度 dimensions | 否 | ≤10 个，合法标识符，不能与表同名 | 统一指标查询的 GROUP BY 白名单（面板暂未提供输入框，走 API/导入维护） |
| 状态 status | — | 外部提交仅接受 ACTIVE/DISABLED | PENDING/REJECTED 只能由治理流程产生 |

#### 3.1.4 状态机

```text
ADMIN 创建 ─────────────────────────► ACTIVE ──停用/启用──► DISABLED
                                        ▲
ANALYST 创建 ──► PENDING ──审批通过──────┘
                   │
                   └──驳回──► REJECTED ──重新提议（提议人或 ADMIN）──► PENDING
```

要点：

- `PENDING` / `REJECTED` **不进入问数**（`loadActiveMetrics` 只取 ACTIVE）。
- `PENDING` 状态不允许直接编辑，必须先审批或驳回。
- 「重新提议」只作用于 `REJECTED`（回到 `PENDING`）；`DISABLED` 走「启用」直接回 `ACTIVE`。
- 每次创建 / 审批生效 / 变更 / 回滚都写 `metric_versions` 快照，`version` 递增。

#### 3.1.5 操作步骤

**① 新建指标**

1. 顶部选择数据源 → 点「新建指标」。
2. 填写指标名、同义词（逗号/中文逗号/顿号分隔）、聚合表达式、归属表、固定过滤、口径说明。
   > 说明：当前面板表单提供「名称/同义词/表达式/归属表/过滤/说明」六项；**可切分维度**后端已支持（≤10 个合法标识符），需通过 `POST/PUT /api/metrics` 或导入文件维护，面板暂未提供输入框。未登记维度时，统一指标查询不允许按任何列下钻。
3. 保存：
   - ADMIN 保存后直接「已生效」（version=1）；
   - ANALYST 保存后提示「已提交，待管理员审批」，状态为 PENDING。

**② 审批 / 驳回 / 重新提议**

- ADMIN 在列表 PENDING 行点「提议/审批」→ 通过则 ACTIVE，驳回则 REJECTED。
- 被驳回的指标，提议人本人或 ADMIN 点「重新提议」→ 回到 PENDING。
- 顶部会显示待审批数量提示。

**③ 编辑与启停**

- ADMIN 可编辑非 PENDING 指标（数据源归属不可变），保存后 version+1 并留快照。
- ACTIVE ↔ DISABLED 用行内「停用 / 启用」按钮，停用后立即退出问数。

**④ 版本历史与回溯**

- 行内「版本」→ 查看历史快照（新→旧），可「回溯」到指定版本；回溯本身也记一次快照，可再次回滚。

**⑤ 导入 / 导出**

- 导出：当前数据源全部指标 → `指标库-<数据源名>-<日期>.json`（`type='metric-definitions'`）。
- 导入：选择备份文件 → 选合并策略：
  - `skip`（默认）：同名指标跳过；
  - `overwrite`：同名指标覆盖，版本 +1 留历史（**不支持 append**，因为指标名数据源内唯一）；
  - 可勾选「仅预检（dryRun）」先看导入/更新/跳过/错误条数，再决定是否写库。
- 上限：单次导入最多 500 条。

**⑥ 统一指标查询（报表/看板/问数三端共享）**

`POST /api/metrics/query`，入参 `{ metricId, dimensions[], limit, amountUnit }`：

- 只能按登记的可切分维度 GROUP BY；
- 复用 SELECT-only 安全执行层，结果按角色 DLP 脱敏；
- 金额类指标（名称/说明/表达式命中金额关键词且非 COUNT）支持单位换算，COUNT 类不换算。

#### 3.1.6 写指标的六条硬要求

1. 归属表必须在当前数据源 Schema 中存在，否则生成的 SQL 会被安全层拒绝。
2. 表达式只写聚合部分，不要把 `SELECT` / `FROM` / `WHERE` 写进 expr；过滤条件放 filters。
3. filters 里如果需要写字符串值，用标准 SQL 引号；不要写多语句。
4. 同义词要覆盖业务口语（如「不良率」→「不良贷款率、NPL 比率」），但不要让同义词过短（如「率」），否则几乎每个问题都命中。
5. 维度列必须是归属表真实列名；登记后即为该指标唯一允许的下钻维度集合。
6. 指标名不要与铁律标题、本体实体名重复使用同一串关键词，否则同一问题会同时命中多个模块（虽然仲裁能裁决，但会增加冲突概率）。

### 3.2 铁律规则（铁律规则 Tab）

#### 3.2.1 它解决什么问题

有些约束不是「口径」，而是「红线」：禁止跨法人统计、禁止把测试数据算进业务量、金额必须按某字段过滤、某些表禁止关联。这类规则不能依赖检索命中，必须每次都出现在 prompt 里。

#### 3.2.2 生效规则

- 该数据源**全部 ACTIVE 规则全量恒注入**，不按问题匹配，不参与相关性排序。
- 注入文案带强约束措辞：「最高优先级，高于一切样例与知识片段；若用户问题或样例与铁律冲突，一律按铁律执行」。
- 同时注入问数链路与报表链路。
- 列表按 `id` 升序，即**创建顺序就是 prompt 中的出现顺序**。

#### 3.2.3 字段与校验上限

| 字段 | 必填 | 上限 / 规则 |
|---|---|---|
| 标题 title | 是 | ≤100 字，数据源内唯一 |
| 正文 content | 是 | ≤2000 字 |
| 状态 status | — | ACTIVE / DISABLED / PENDING |
| 条数 | — | 每个数据源最多 100 条（创建时硬校验） |

#### 3.2.4 三种状态

- `ACTIVE`：生效，恒注入。
- `DISABLED`：停用，不注入，保留内容。
- `PENDING`：由「数据源接入自动化配置」预填的铁律模板（`v0.9.73`），**不注入**，等待管理员确认。前端按钮显示为「确认启用」。

#### 3.2.5 操作步骤

1. 选择数据源 → 点「新建铁律」。
2. 填标题 + 正文 → 保存。**创建即生效**，提示语会明确「该数据源所有问数与报表将逐条遵守」。
3. 行内「编辑」可改标题/正文/状态；「停用 / 启用 / 确认启用」一键切换。
4. 「导入 / 导出」与指标库同模式：`type='iron-rules'`，`skip`（默认）/ `overwrite`，支持 dryRun，单次最多 500 条。
5. PENDING 规则在列表顶部有数量提醒，建议接入新数据源后第一件事就是处理这批待确认项。

#### 3.2.6 铁律的写法规范（直接影响是否生效）

- **可判定**：写「金额类指标必须过滤 `biz_type = 'NPL'`」，不要写「注意数据质量」。
- **单一事实**：一条铁律只讲一件事，便于冲突裁剪时精确丢弃。
- **优先使用 `表.列 = 值` 形态**：仲裁器只识别这种形态做冲突判定。写成「订单表的订单类型字段等于 1」不会参与冲突裁剪，可能与本体值域释义同时存在而互相矛盾。
- **不要与指标口径重复**：如果某条规则是「指标怎么算」，应写成指标；铁律只放「不论怎么算都不许做」的约束。
- **不要写超过 20 条**：全量注入会挤占其他上下文；规则越多，单条被模型忽略的概率越高。

#### 3.2.7 与指标冲突时谁赢

铁律赢。且如果两者都以 `表.列 = 值` 形态描述了同一列的不同取值，仲裁器会直接丢掉指标那一行，并在 trace 里记一条 `[metric] 丢弃与高优先级块冲突的行`。若你发现指标「明明登记了却没生效」，先查铁律是否有同列不同值的表述。

### 3.3 业务本体（业务本体 Tab）

#### 3.3.1 它解决什么问题

Schema 只告诉你「有一张表叫 `dn_tzsy`，有一个列叫 `BNTFJE`」，但不知道「项目」对应哪张表、「机构名称」是哪个列、「状态=1」是什么业务含义、「项目→合同→回款」怎么关联。业务本体就是这层业务语义的登记簿。

**它不做的事**：不新增表、不改 Schema、不放开权限、不直接拼 SQL。所有内容都是「软注入」——只影响 LLM 的选择倾向和写法，最终仍受 Schema 白名单约束。

#### 3.3.2 四类资产

| 资产 | 作用 | 注入段落 |
|---|---|---|
| 业务实体 + 表/列绑定 | 把业务词映射到表/列，并给圈表加权 | 【业务实体】 |
| 值域释义 | 枚举/编码列每个取值的业务含义 | 【值域释义】 |
| 关联路径 | 已登记的 JOIN 路径（表、列、JOIN 类型、基数、用途） | 【关联路径】 |
| 业务层级 | 下钻/分组用的层级列序（如：集团 > 分公司 > 项目） | 【业务层级】 |

#### 3.3.3 命中与加权规则（决定「为什么我的本体没生效」）

实体命中打分：

- 问题包含实体名称：+10
- 问题包含任一别名：+10
- 描述文本 bigram 重合率 × 2（最高 +2）
- 得分 > 0 才算命中；按得分降序
- 命中多于 1 个且开启 embedding 精排时，叠加「问题向量与实体文本余弦 × 10」

绑定加权（参与 Schema 圈表）：

| 绑定角色 | 权重 | 适用场景 |
|---|---|---|
| IDENTITY | +8 | 实体的主标识列（如机构代码） |
| RELATION_KEY | +4 | 关联键（如合同 ID、客户 ID） |
| ATTRIBUTE | +3 | 普通属性列 |

- 同一张表的多个绑定累加，**单表封顶 +15**。
- 绑定只有命中实体后才参与加权；没有实体命中时，本体对圈表零影响。

注入上限（超出按得分/顺序截断）：

- 实体 8 个、关联路径 12 条、值域释义 40 条、业务层级 5 个
- 本体段总预算默认 1500 tokens（`ONTOLOGY_TOKEN_BUDGET`）

关联路径匹配逻辑：只注入「命中实体绑定的表 + 已圈定表」之间的路径；若这些表之间一条路径都没登记且表数 ≥2，会给一句候选提示「未登记关联路径，多表查询须按 Schema 同名列/外键语义推导 JOIN，并在 thoughtProcess 说明依据」。

#### 3.3.4 校验上限

| 字段 | 上限 |
|---|---|
| 实体名 | ≤50 字，数据源内唯一 |
| 别名 | ≤10 个，每个 ≤50 字，不能与实体名相同 |
| 实体描述 | ≤300 字 |
| 单实体绑定 | ≤20 条；同一（实体, 表, 列）唯一；列名留空 = 表级绑定 |
| 值域释义 | `表.列 + 值 + 含义` 唯一；含义 ≤200 字 |
| 关联路径 | 关联列拼接后 ≤300 字；同一方向不可重复登记 |
| 业务层级 | 2–10 级（`MAX_LEVELS=10`），层级名 ≤50 字，数据源内唯一 |

#### 3.3.5 操作步骤

**① 实体与绑定（实体与绑定 Tab）**

1. 点「新建实体」→ 填实体名、类型（SUBJECT/OBJECT/TIME/GEO）、别名、说明 → 创建即生效（version=1）。
2. 列表顶部搜索框支持按名称 / 别名 / 说明 / 绑定表列即时过滤；勾选「仅看未绑定」可快速找出还没登记绑定的实体，计数提示显示「共 N 个 · 已绑定 X 个 · 当前显示 Y 个」。
3. 列表行点「维护绑定」→ 进入绑定编辑器：
   - 点「添加绑定」或直接在最后一行按 `Enter` 新增，逐行填表名、列名（留空 = 表级）、角色（IDENTITY/ATTRIBUTE/RELATION_KEY）；
   - 表名/列名有 Schema 输入建议，未命中时黄色提示（只提示、不阻断保存）；
   - 任意编辑后出现「有未保存改动」徽标，保存按钮才可用；「重置」恢复库内内容，切换实体或收起时未保存会二次确认；
   - 保存是**整组替换**：提交的数组即最终集合，未包含的旧绑定会被删除；`Ctrl/Cmd + Enter` 可快捷保存。
4. 行内「编辑」改实体内容（version+1）；「删除」会连带删除绑定并留删除快照。
5. 行内电源图标可「停用 / 启用」：停用后不参与圈表加权与提示词注入，绑定保留，概览计数减一。
6. 行内「版本」→ 查看历史 → 可回滚。快照以可读摘要展示（名称 / 类型 / 别名 / 状态），最新版本带标记且不可回滚。回滚只作用于治理元数据，不改变执行层 Schema 与已生成 SQL。

**② 值域释义（值域释义 Tab）**

1. 先选表名、列名（下拉来自当前数据源 Schema）。
2. 单条新增：填「值 = 含义」→ 保存；同键（表.列+值）再次保存即覆盖含义。
3. 批量粘贴：每行一条「值=含义」，写入上方所选表.列 → 「批量保存」。兼容全角 `＝`、中文冒号与 Excel 两列制表符；输入时实时显示「将写入 N 条 / 重复 N 条按后者覆盖 / N 行无法解析」；单次最多 200 条，整批只发一次请求，返回成功 / 失败条数与首条失败原因。
4. 搜索框与表名 / 列名筛选均为本地即时过滤，不逐字请求。
5. 列表支持编辑含义与状态、停用 / 启用、删除；状态默认 ACTIVE。

**③ 关联路径（关联路径 Tab）**

1. 点「登记关联路径」→ 填起始表/列、目标表/列、JOIN 类型（INNER/LEFT/RIGHT）、基数（1:1/1:N/N:1/N:N）、用途说明。
2. 表列可用联想，多列点「从表结构追加列」逐个加入（也可逗号分隔手填）；已选列以 chips 展示，点击即移除；「交换起点 / 终点」一键互换两侧。
3. 起止列均为必填且两侧数量必须一致——表单即时提示，不满足时提交按钮禁用（服务端同样校验）。
4. 「路径预览」调用 `GET /api/ontology/path`，用 BFS 查两表间最短路径（最多 3 跳、最多 3 条），用于验证登记是否正确。
5. 列表支持按表名 / 列名 / 用途筛选，支持编辑、停用 / 启用、删除、版本回滚。

**④ 业务层级（业务层级 Tab）**

1. 点「新建层级」→ 填层级名，并用层级编辑器逐级填写（由粗到细，2–10 级）；可点「填入示例」快速体验，支持上下移与增删，底部实时预览「集团 > 分公司 > 项目」。
2. 列表支持按名称或列名搜索，支持编辑、停用 / 启用、删除、版本回滚。

#### 3.3.6 什么时候值得建本体（决策清单）

建议优先登记：

- 业务口语与物理表名差异大（「项目」→ `dn_xmxx`，「机构」→ `dn_jgxx`）；
- 同一业务概念分散在多张表，需要圈表加权把正确表顶上来；
- 枚举值含义不直观（`status=1/2/3` 分别代表什么），且 SQL 里必须写对；
- 多表 JOIN 关系稳定且容易写错（项目→合同→回款）；
- 报表/看板需要按固定层级下钻。

不建议登记：

- 表名已经足够语义化、问题几乎不会提业务别名；
- 关系不稳定或经常变化（本体是「已登记路径优先」，写错会引导错误 JOIN）；
- 把「指标怎么算」写进本体描述（应写指标）。

#### 3.3.7 开关

- `ONTOLOGY_ENABLED=0`：全局关闭（圈表不加权、prompt 不注入），可作一键回退。
- `ONTOLOGY_TOKEN_BUDGET`：本体段预算，默认 1500，最小 200。
- `ONTOLOGY_EMBEDDING_ENABLED=0`：关闭实体 embedding 精排，省一次 embedding 往返（无 embedding 模型的本地环境建议关）。
- 问数接口支持单次 `disableOntology` 做 A/B 对照（管理端评测用）。

### 3.4 业务知识库（业务知识库 Tab）

#### 3.4.1 它解决什么问题

有些知识不是结构化口径，也不是硬约束，而是一段说明：某个术语的定义、某类报表的口径差异、枚举写法速查、历史踩坑记录。这类内容用自由文本登记，问数时按相关性检索片段注入。

#### 3.4.2 切块与检索参数（决定「为什么我的知识没被召回」）

| 参数 | 值 | 含义 |
|---|---|---|
| CHUNK_SIZE | 400 字 | 单块目标长度 |
| CHUNK_OVERLAP | 80 字 | 相邻块重叠 |
| TOP_K_CHUNKS | 6 | 最多注入块数 |
| MAX_CHUNKS_PER_DOC | 2 | 单文档最多入选块数（防止长字典占满槽位） |
| knowledgeMinScore | 默认 0.5 | 向量相似度准入阈值（`KNOWLEDGE_MIN_SCORE`） |
| 融合策略 | RRF（默认） | k=60，向量权重 1、词法权重 0.8；`KNOWLEDGE_RANK_STRATEGY=legacy` 可回退旧策略 |
| 词法救回 | bigram 重合 ≥2 且覆盖率达标 | 精确术语命中可救回向量漏召 |
| 口径类保留槽 | 标题含 `口径/指南/速查/规则/枚举/对比/模式` | 有命中时至少保留一个注入名额 |
| 注入预算 | 2700 tokens | `KNOWLEDGE_TOKEN_BUDGET` |

关键含义：

- **标题很重要**。标注类文档（字段字典、枚举大全）在向量上通常全面占优；标题带「口径」「规则」「对比」等关键词的文档才有保留槽，不会被挤掉。所以口径类文档请在标题里明确写出「口径」「规则」。
- **阈值 0.5** 是经过评测的默认值：低于它会放行域外问题（天气类问题也注入知识），高于 0.55 会误杀正例。
- **单文档最多 2 块**，所以不要把多个独立口径塞进一篇超长文档；一篇文档讲一个主题，命中率更高。

#### 3.4.3 操作步骤

**① 登记知识**

1. 选择数据源 → 点「登记知识」。
2. 填标题 + 内容（多行 Markdown 均可）→ 保存。
3. 保存时立即切块并生成向量；提示会显示「切分为 N 个片段」。向量生成失败时降级为无向量（仍可通过词法检索命中）。

**② 查看详情（切块明细）**

- 列表行点标题或「查看详情」→ 展示该文档的片段数、创建人、创建时间、docId，以及每个片段的内容。
- 用途：确认切块是否把一条完整口径切断（如果关键句被切断，考虑缩短文档或调整表述）。

**③ 编辑**

- 行内「编辑」→ 回填完整内容（由片段拼接）→ 保存后**重新切块并重算向量**，问数检索即时生效。

**④ 删除**

- 行内删除，删除该文档全部片段。

**⑤ 导入 / 导出**

- 导出：`type='knowledge-docs'`，含 docs 数组（标题 + 完整内容）与来源数据源信息。
- 导入：支持 `knowledge-docs` 新格式与旧的 `knowledgeBase` 条目格式；
  - `skip`（默认）：同名文档跳过；
  - `overwrite`：同名文档覆盖并重新切块；
  - `append`：同名也照常导入（会产生重复条目，一般不建议）。
- 导入接口单独放宽了 body 限制到 10MB。

**⑥ 外部知识源（本 Tab 下方卡片）**

用于对接企业已有 RAG / 知识服务：

1. 点新增 → 填名称、接口地址（必须 `http(s)://`）、认证方式（`none` / `bearer` + API Key）、超时（500–30000ms，默认 5000）、生效数据源（`*` 全部或指定数据源）、启用开关。
2. 「测试」会真实调用一次，返回 `ok / latencyMs / chunks / error`。
3. 协议约定：`POST {endpoint}`，请求体 `{ "query": "...", "topK": 4 }`，`Authorization: Bearer <key>`（bearer 模式）；响应命中列表放在 `results / documents / data / items` 任一字段或顶层数组，每项取 `content / text / chunk / pageContent` 作为片段，`source / title / name` 作为来源。
4. 单片段截断 600 字、单源最多 20 条；任一源超时/非 2xx/解析失败都降级为空，不阻断问数。
5. 外部知识独立预算 1200 tokens，追加在本地知识之后，互不挤占槽位（启用记忆体时并入统一预算）。
6. API Key 以 AES-256-GCM 加密落库，列表不回显明文。

**⑦ 自动化生成的文档（autokb_ / autosch_）**

数据源接入自动化配置（`autoKnowledgeSync`）会自动向知识库写入两类文档：

- `autokb_*`：由结构化知识条目（`knowledge_base_entries`）同步切块而来；
- `autosch_*`：按表切块的 Schema 元数据文档，单数据源最多 60 篇。

这些文档与其他知识文档一起参与检索，也会出现在列表/详情/导出中。**它们是幂等同步的**：同一数据源重新执行自动化配置会覆盖更新，并按前缀清理已不存在的残留文档。因此：

- 想长期修改自动生成的口径，建议另建手工文档（标题不要与自动文档重名），或直接改自动条目的来源配置；
- 不要只依赖「删除自动文档」来消除某条口径，下次同步可能重建。

#### 3.4.4 知识库与知识漂移联动

「质量监控 → 知识漂移」提供观察名单机制（`kb_drift_watch` / `kb_drift_events`）：

- 把关键表/字段加入观察名单；
- 扫描后生成漂移事件（如字段消失、取值分布突变）；
- 事件确认后应回到知识库更新对应口径文档，形成闭环。

接口：`GET /api/ops/drift`、`POST /api/ops/drift/scan`、`POST /api/ops/drift/watch`、`DELETE /api/ops/drift/watch`、`POST /api/ops/drift/:id/ack`。

#### 3.4.5 知识写法建议

- 一条知识一个主题；标题写清业务域与类型（如「不良率口径规则」「五级分类枚举速查」）。
- 枚举写成 `表.列 = 值 → 含义`，与本体值域释义保持完全一致的写法（理由见 4.2）。
- 不要写「根据实际情况判断」「酌情处理」这类无法执行的表述。
- 不要在知识库里重复指标表达式（指标应登记在指标 Tab），否则两处口径变更容易不同步。
- 文档控制在几百字到一两千字；超长文档会被切成多块，单文档最多入选 2 块。

### 3.5 SQL 样例库（SQL 样例库 Tab）

#### 3.5.1 它解决什么问题

样例库教模型「这类问题在本数据源通常怎么写」：选哪张表、怎么聚合、别名风格、日期过滤习惯。它以 user/assistant 消息对形式注入对话历史，比平铺文本更贴合多轮格式。

**它不定义口径**：样例里的算法如果与指标/铁律冲突，一律以指标/铁律为准。样例是「参考写法」，不是「权威口径」。

#### 3.5.2 检索与打分规则

- 取该数据源最近 100 条样例（`ORDER BY id DESC LIMIT 100`）。
- 打分 = 问题 bigram 重合 + 问题向量余弦 × 8 + 表重合数 × 3（表重合基于当前圈定表）。
- 得分 > 0 才进入候选；**相同归一化 SQL 去重**（保留最高分）。
- 按 `FEWSHOT_TOKEN_BUDGET=3600` 贪心装入，**最多取 3 条**。
- 样例来源：`MANUAL`（手工登记）、`FEEDBACK_UP`（用户点赞自动沉淀）、`IMPORT`（批量/备份导入）。

#### 3.5.3 字段与校验

| 字段 | 规则 |
|---|---|
| 问题 question | 必填，≤500 字 |
| SQL sql | 必填，≤2000 字，必须 `SELECT` 开头（忽略前导空白/注释） |
| 数据源 | 必填，样例只对该数据源生效 |

#### 3.5.4 操作步骤

**① 登记样例**

选择数据源 → 「登记样例」→ 填问题 + SQL → 保存（来源 MANUAL，自动生成问题向量）。

**② 批量导入（粘贴 SQL 反推问题）**

1. 「批量导入」→ 粘贴一条或多条 SQL（多条以分号分隔）。
2. 单次最多 10 条；系统调用 LLM 反推问题，展示「问题 + SQL」对。
3. 逐条确认或修改反推问题后保存（来源 IMPORT）。

**③ 编辑 / 删除**

- 编辑会重算问题向量，避免旧向量与新问题语义脱节。
- 删除用于剔除劣质样例（口径错误、表选择错误的样例会持续带偏问数）。

**④ 导出 / 导入备份**

- 导出：`type='sql-examples'`。
- 导入：`skip`（默认）/ `overwrite` / `append` 三种策略；支持 dryRun；样例无唯一键，默认按「同问题」判冲突。

**⑤ 自动化种子样例**

数据源接入自动化配置会基于真实 Schema 生成 few-shot 种子样例（趋势/排名/快照最新期/版本过滤/去重计数等范式），单数据源最多 8 条，并按「数据源 + 问题 + 归一化 SQL」去重。这些样例：

- 会出现在样例库列表中（`source` 为 `IMPORT`，由同步逻辑写入）；
- 与手工样例一起参与检索，是冷启动阶段的主要召回来源；
- 重新执行自动化配置时不会重复插入（按三元组去重）。

#### 3.5.5 样例治理建议

- 优先保留「复杂但正确」的样例（多表 JOIN、同比环比、条件聚合），简单单表聚合价值低。
- 每个业务域保留 3–5 条即可；样例过多会稀释注意力，且预算只有 3600 tokens。
- 定期清理口径已变更的旧样例——**过时样例比没有样例更危险**。
- 点赞自动沉淀（FEEDBACK_UP）的样例置信度低于手工样例（记忆体通道置信度：MANUAL 0.95 / FEEDBACK_UP 0.7 / IMPORT 0.6），重要口径仍建议手工登记。

### 3.6 专家角色（专家角色 Tab）

#### 3.6.1 它解决什么问题

同一个查询结果，风控专家关注敞口与迁徙，财务分析师关注收入结构与现金流。专家角色决定阶段二解读的身份设定、分析框架和术语体系。

**它不影响 SQL**：角色在阶段一 SQL 生成之后才用于阶段二 system prompt；改角色不会改变查询结果，只改变解读文字。

#### 3.6.2 路由规则

1. 只取 `status='ACTIVE'` 的角色，按 `sortOrder` 升序（同序按 id 升序）。
2. 跳过 `default`，其余角色按顺序做**关键词包含匹配**，第一个命中的角色生效。
3. 全部未命中时使用 `default`（不参与匹配，关键词恒空，sortOrder 恒 9999，不可停用、不可删除）。
4. 60s 内存缓存；任何写操作即时失效缓存，下一次问数回读最新配置。
5. 库不可用时回退代码内置常量路由（功能可用，但管理员修改暂不生效）。

内置 5 角色：

| key | 标签 | sortOrder | 典型关键词 |
|---|---|---|---|
| risk | 不良资产风险管理专家 | 10 | 风险、逾期、违约、不良率、拨备、抵质押、集中度 |
| customer | 不良资产客户分析管理专家 | 20 | 客户、借款人、画像、分层、拜访、转化 |
| finance | 专业财务分析师 | 30 | 财务、营收、利润、成本、现金流、周转 |
| npl | 资深不良资产从业者 | 40 | 不良、资产包、处置、清收、回收、IRR |
| default | 金融数据分析师 | 9999 | —（兜底，不参与匹配） |

**排序语义**：具体职能排在宽泛领域之前。例如「不良率」同时含「不良」（npl）与「不良率」（risk），因为 risk 的 sortOrder 更小，先命中 risk——这是刻意的设计，避免风险指标被宽泛的「不良」领域词抢走。

#### 3.6.3 字段与校验

| 字段 | 规则 |
|---|---|
| 角色标签 label | 必填，≤50 字（显示在回答卡片角标） |
| 触发关键词 keywords | ≤20 个，单个 1–30 字，自动去重去空 |
| 角色提示词 rolePrompt | 必填，≤2000 字 |
| 匹配优先级 sortOrder | 0–9999，默认 100；越小越先匹配 |
| 状态 status | ACTIVE / DISABLED（default 恒 ACTIVE） |

#### 3.6.4 操作步骤

1. 「新建角色」→ 填标签、关键词（分隔输入）、rolePrompt、sortOrder、状态 → 保存即生效。
2. 行内「编辑」修改；「删除」仅对自定义角色可用（内置角色拒绝删除，可编辑或停用）。
3. 行内状态切换可停用/启用；「已停用」角色不参与路由。

#### 3.6.5 内置角色内容版本（content_version）

- 代码内置角色带 `BUILTIN_PERSONA_CONTENT_VERSION`。
- 版本升级后，服务启动时一次性把内置角色的 label/keywords/rolePrompt 同步为代码常量；`status` / `sortOrder` 保留管理员设置。
- 同步后管理员的再编辑不会被覆盖，直到下一次版本升级。
- 因此：如果你改了内置角色的提示词，下次系统升级可能被覆盖——需要长期保留的自定义逻辑，建议新建自定义角色。

#### 3.6.6 角色设计建议

- 关键词要「专」不要「泛」：单个关键词越短越容易抢路由（如「率」「表」）。
- 新角色 sortOrder 要么排在最具体的职能之前，要么明确排在宽泛角色之后，避免随机抢占。
- rolePrompt 要写「分析维度 + 输出要求 + 术语要求」三段式，并明确「所有结论必须引用真实数据」，否则容易出现泛泛而谈。
- 角色数量控制在 10 个以内；过多角色会让路由边界变得难以预测。

## 4. 模块之间的关系（核心章节）

### 4.1 分层关系矩阵：谁约束谁

下表读法：行是「上游」，列是「下游」；单元格说明上游对下游的影响。`—` 表示无直接依赖。

| 上游 ↓ / 下游 → | 指标 | 铁律 | 本体 | 知识库 | 样例库 | 专家角色 |
|---|---|---|---|---|---|---|
| **指标** | — | 同列不同值时被铁律压制 | 本体应与指标口径一致，冲突时指标赢 | 知识库不应重复指标表达式 | 样例写法不得违背指标 | 无 |
| **铁律** | 强制约束指标的使用方式 | — | 铁律可否定本体登记的路径/取值 | 铁律高于知识 | 铁律高于样例 | 无 |
| **本体** | 提供实体→表/列映射，帮助指标归属表被圈中 | 本体值域与铁律冲突时被裁剪 | — | 同一枚举两处登记时必须写法一致 | 无 | 无 |
| **知识库** | 无（优先级更低） | 被铁律压制 | 被本体值域压制（同 `表.列=值`） | — | 知识补充样例未覆盖的口径 | 无 |
| **样例库** | 提供形式参考，不改口径 | 被铁律压制 | 无 | 无 | — | 无 |
| **专家角色** | 无 | 无 | 无 | 无 | 无 | — |

### 4.2 六种典型冲突与裁决

#### 冲突 1：铁律 vs 指标（同一列不同取值）

- **现象**：指标登记了 `dwd_loan.status = 'A'`，铁律写着「只统计 `dwd_loan.status = '1'` 的有效合同」；问数结果指标口径「没生效」。
- **原因**：两者都以 `表.列 = 值` 形态描述同一事实，仲裁器保留铁律行、丢弃指标行，trace 记 `冲突 1 行`。
- **处理**：确认哪个是权威事实，改掉另一处；不要在两处登记同列不同值。

#### 冲突 2：指标 vs 本体（本体描述里写了另一套算法）

- **现象**：指标定义「不良率 = 不良余额/总余额」，本体实体描述里写「不良率按笔数计算」。
- **原因**：指标优先级高于本体，模型最终按指标执行；但本体描述仍会干扰注意力。
- **处理**：本体描述只写「业务含义/别名/归属」，不写计算公式；算法统一放指标。

#### 冲突 3：本体值域 vs 知识库枚举

- **现象**：本体登记 `status = 1 → 正常`，知识库文档写 `status = 1 → 有效`；模型输出不稳定。
- **原因**：两处都命中，且不是同值；仲裁器丢弃知识库那一行（本体优先级更高）。
- **处理**：枚举只在**一处**登记。建议：结构化枚举放本体值域；成段说明（如「1/2/3 的历史沿革」）放知识库，但不要重复逐值映射。

#### 冲突 4：指标 vs 知识库（口径描述不一致）

- **现象**：指标已定义表达式，知识库文档又写了一段「该指标应按另一口径计算」。
- **原因**：指标优先，知识库那段会被模型视为补充说明，可能造成解释与 SQL 不一致。
- **处理**：知识库只写「为什么这样定义」的背景，不写「应该怎么算」。

#### 冲突 5：样例 vs 铁律/指标

- **现象**：一条老样例用了不存在的表或过期口径，新问题却召回了它。
- **原因**：样例在 prompt 中只是「参考写法」，措辞明确要求优先参考但必须重新生成；铁律/指标优先级更高。
- **处理**：发现样例带偏，立即在样例库删除或修正。样例治理是持续动作，不是一次性配置。

#### 冲突 6：专家角色关键词互抢

- **现象**：问「不良率趋势」，却路由到「资深不良资产从业者」而不是「风险管理专家」。
- **原因**：sortOrder 顺序不当，或宽泛关键词（「不良」）排在具体关键词（「不良率」）之前。
- **处理**：具体职能 sortOrder 调小；或给宽泛角色去掉过短关键词。

### 4.3 一致性的四条黄金规则

1. **单一事实源**：同一个「值 → 含义」只登记一处；同一个指标算法只登记在指标 Tab。
2. **统一事实写法**：需要参与冲突裁决的内容，统一写成 `表.列 = 值`（或 `表.列 = 值 → 含义`）。仲裁器只识别这种形态。
3. **命名三层去重**：指标名 / 同义词、实体名 / 别名、铁律标题，不要复用同一串短关键词，避免同一问题多模块同时命中。
4. **先铁律后指标再本体**：配置顺序决定你发现问题时的排查顺序，也决定冲突时的默认胜者。

### 4.4 与「数据源与 Schema」的关系

| 能力 | 归属页面 | 说明 |
|---|---|---|
| 表/列清单、类型、中文说明 | 数据源与 Schema | 执行层白名单的唯一来源 |
| 列角色（指标列/维度列） | 数据源与 Schema → Schema 元数据编辑 | 影响 `guidance` 摘要中的「维度[] 指标[]」 |
| 表级业务口径 businessNote | 数据源与 Schema → Schema 元数据编辑 | ≤500 字，拼在阶段一 Schema 之后、铁律之前，**不经仲裁器** |
| 敏感字段、行级权限 | 数据源与 Schema / 权限体系 | 先于所有规则生效 |

因此，出现「知识库写了但模型没用」时，先确认该表/列是否在当前用户可见 Schema 中；不在白名单里的内容永远不会被执行层接受。

### 4.5 与其他治理模块的关系

| 模块 | 与规则治理的关系 |
|---|---|
| 质量监控 → 知识漂移 | 观察名单发现 Schema 漂移 → 回到知识库/本体更新口径，形成闭环 |
| 质量监控 → A/B 实验 | 可用 `disableOntology`、记忆体三态做规则效果的对照实验 |
| 记忆管理（v0.9.106） | 纠错候选审核通过后进入 `memory_items`，以 CORRECTION 通道参与召回，优先级高于知识/样例 |
| AI 审核 | 审核问数留痕与回答质量，发现规则问题时回流到本页修正 |
| 需求反馈 | 业务方提出口径变更需求 → 评估后落到指标/铁律/知识库 |

## 5. 推荐配置顺序（新数据源上线 SOP）

按下面顺序配置，可以最大限度地减少返工和冲突。每一步都给了「产出物」和「验收标准」。

### Step 1：Schema 与表级业务口径（数据源与 Schema）

- **动作**：确认表/列清单、中文说明、指标列/维度列角色；给核心表填表级业务口径（≤500 字）。
- **产出物**：可用的 Schema 白名单 + 表级口径说明。
- **验收**：问一个简单问题，`linking` 节点能圈中正确表；`guidance` 中维度/指标列符合预期。

### Step 2：铁律规则（3–10 条）

- **动作**：先写「绝对不能违反」的硬约束：过滤条件、禁用表、口径红线、金额单位规则。
- **产出物**：ACTIVE 铁律列表。
- **验收**：问一个会触发红线的问题，trace「铁律规则注入」节点显示注入条数正确；SQL 中体现约束。

### Step 3：语义指标（10–30 条核心指标）

- **动作**：按业务域登记核心指标，同义词覆盖口语说法，维度白名单只放常用下钻列。
- **产出物**：ACTIVE 指标定义。
- **验收**：问「<指标名>是多少」，trace「语义指标层命中」显示命中该指标；SQL 的聚合表达式与登记一致。

### Step 4：业务本体（先实体+绑定，再值域，最后关系/层级）

- **动作**：
  1. 登记 5–15 个核心业务实体，配 IDENTITY 绑定；
  2. 给高频枚举列登记值域释义；
  3. 给稳定的多表关系登记关联路径，用「路径预览」验证；
  4. 需要下钻的登记业务层级。
- **产出物**：四类本体资产。
- **验收**：问一个含业务别名的问题，trace「业务本体命中」显示实体命中、加权表数、关联路径数；`linking` 圈表结果向绑定表倾斜。

### Step 5：业务知识库（口径/术语/枚举/踩坑）

- **动作**：把无法结构化进指标/本体的说明写成文档；标题带「口径」「规则」「枚举」「速查」等关键词；一篇一个主题。
- **产出物**：知识文档 + 必要的外部知识源。
- **验收**：问一个口径类问题，trace「知识库检索与 Few-shot 样例」显示知识片段字数 > 0；详情页切块完整。

### Step 6：SQL 样例库（每业务域 3–5 条）

- **动作**：登记高质量复杂样例；用「批量导入」把历史正确 SQL 反推成问题对；清理过时样例。
- **产出物**：样例库。
- **验收**：trace 中 few-shot 组数 > 0；相同问题连续问两次，SQL 结构稳定。

### Step 7：专家角色（按需调整）

- **动作**：确认内置 5 角色关键词是否覆盖业务；新增角色时注意 sortOrder。
- **产出物**：角色列表。
- **验收**：问一个风险类问题与一个财务类问题，回答卡片角标分别为对应角色标签。

### Step 8：整体验收（用 trace 逐节点核对）

按第 6 章的验收清单逐项核对，并做 5–10 个典型问题的回归。

> 顺序理由：Schema 是所有规则的基础；铁律是硬约束必须先立；指标决定「算得对」；本体解决「找得到」；知识补充「说不清」；样例优化「写得像」；角色只影响「讲得好」。反过来配置（先样例后指标）最容易出现「样例带偏口径」。

## 6. trace 验收：怎么确认配置真的生效

每次问数都会在「推导过程」里留下节点。规则治理相关的关键节点如下（按出现顺序）：

| 节点标题 | stepType | 关键摘要 | 期望 |
|---|---|---|---|
| Schema 圈表：选定相关表 | `linking` | `命中 x/y 张表：...` | 本体绑定表应出现在结果中 |
| 业务本体命中 | `ontology` | `实体命中 n 个（...）；加权表 m 张；关联路径 k 条；注入 t tokens` | 问业务别名时 n>0；未命中时 n=0 且零注入 |
| 列级裁剪：宽表 top-N 列注入 | `linking` | `表名 before→after 列` | 指标引用列应被保留 |
| 知识库检索与 Few-shot 样例 | `knowledge` | `知识片段 x 字；外部知识库 y 字；few-shot z 组；点踩反例 w 组` | 与配置规模相符 |
| 统一记忆体召回（仅启用时） | `knowledge` | `通道命中 iron:x metric:y ...；强制段 n 条；注入 t tokens` | off 时无此节点；shadow 有节点但不注入 |
| 语义指标层命中 | `metrics` | `命中 n 个指标定义：...` | 命中预期指标名 |
| 铁律规则注入 | `metrics` | `注入 n 条铁律：...` | 条数 = ACTIVE 铁律数 |
| 上下文仲裁 | `ontology` | `仲裁注入 x/6000 tokens（iron:.. metric:..）；去重 a 行、冲突 b 行、预算裁剪 c 行` | x ≤ 6000；b>0 说明存在冲突 |
| 数据解读（角色标签） | `analysis` | 标题形如 `数据解读（不良资产风险管理专家）` | 角色符合预期 |

### 6.1 仲裁行的读法

示例：`仲裁注入 4210/6000 tokens（iron:320 metric:280 ontology:610 guidance:1500 knowledge:1500）；去重 0 行、冲突 1 行、预算裁剪 0 行`

- `x/6000`：实际注入 / 总预算。长期接近 6000 说明上下文过载，应精简知识或样例。
- 分块 token：可看出哪一块占了大头。`guidance` 高是正常的（Schema 摘要）。
- `冲突 1 行`：存在 `表.列=值` 的矛盾表述，应去定位（warning 里有明细，形如 `[metric] 丢弃与高优先级块冲突的行（t.c=1）：...`）。
- `预算裁剪 >0`：说明被裁了行，优先检查 knowledge 块是否堆了太多低价值内容。

### 6.2 三种典型异常与处置

| trace 现象 | 可能原因 | 处置 |
|---|---|---|
| 本体节点 `实体命中 0 个`，但已登记实体 | 问题用词与实体名/别名都不匹配；或 `ONTOLOGY_ENABLED=0` | 补别名；确认开关 |
| 指标节点无「命中」 | 问题未包含指标名/同义词；指标仍是 PENDING；指标排在第 201 条之后 | 补同义词；审批；清理停用指标 |
| 仲裁 `冲突 > 0` 且指标疑似失效 | 铁律/本体里存在同列不同值的表述 | 统一事实写法，删除重复登记 |

## 7. 开关与环境变量

以下变量均通过环境变量配置，缺省值即当前默认行为。

| 变量 | 默认 | 作用 | 建议 |
|---|---|---|---|
| `ONTOLOGY_ENABLED` | 开（仅 `0` 关闭） | 本体总开关：关闭后圈表不加权、prompt 不注入 | 本体数据质量差时可一键回退 |
| `ONTOLOGY_TOKEN_BUDGET` | 1500（最小 200） | 本体四段提示词预算 | 实体多时可上调到 2000 |
| `ONTOLOGY_EMBEDDING_ENABLED` | 开（仅 `0` 关闭） | 实体 embedding 精排 | 无 embedding 模型时设 `0` 省一次往返 |
| `CONTEXT_ARBITER_TOKEN_BUDGET` | 6000 | 仲裁器五块总预算 | 模型上下文较小可下调到 4000 |
| `KNOWLEDGE_MIN_SCORE` | 0.5（0–1） | 知识向量召回阈值 | 域外知识误注入时上调；正例漏召时下调至 0.45 |
| `KNOWLEDGE_RANK_STRATEGY` | `rrf` | 检索融合策略；`legacy` 回退旧版 | 仅排障/评测时切换 |
| `MEMORY_ROUTER_ENABLED` | `off` | 记忆体三态：`off` / `shadow` / `on` | 先 `shadow` 观察，再 `on` 灰度 |
| `MEMORY_ROUTER_ROLLOUT_PCT` | 20 | `on` 时按 userId 哈希灰度百分比 | 逐步放量 |
| `MEMORY_TOTAL_TOKEN_BUDGET` | 6000（最小 500） | 记忆体共享预算（不含铁律/指标强制段） | 与仲裁预算协同调整 |
| `MEMORY_CHANNEL_TIMEOUT_MS` | 400（最小 50） | 单通道超时 | 外部知识慢时保持默认 |
| `MEMORY_RECALL_TIMEOUT_MS` | 800（最小 100） | Router 整体超时 | 同上 |
| `MEMORY_HALF_LIFE_DAYS` | 120 | 记忆衰减半衰期 | 一般不改 |
| `MEMORY_CORRECTION_LIMIT` | 2 | 纠错记忆最多召回条数 | 纠错多时可上调 |

回退优先级建议：

1. 单条规则有问题 → 停用该条（不改开关）；
2. 整个模块有问题 → 关模块开关（本体）；
3. 上下文过载 → 降仲裁预算 + 精简知识/样例；
4. 记忆体引入异常 → `MEMORY_ROUTER_ENABLED=off` 立即回到七路逻辑。

## 8. 排错速查表

| 现象 | 优先排查 | 处理 |
|---|---|---|
| 指标登记了但 SQL 没用 | ① 是否 ACTIVE ② 问题是否含指标名/同义词 ③ 是否被铁律同列不同值压制 ④ 是否排在 200 条之后 | 审批/补同义词/统一事实/停用低价值指标 |
| 指标审批后仍不生效 | 前端是否刷新；指标是否被停用；仲裁冲突 | 重新加载页面；看 trace 仲裁行 |
| 铁律看不到效果 | 规则是否 ACTIVE；是否超过 100 条（创建会被拒）；措辞是否可判定 | 启用；拆分规则；改写为可执行约束 |
| 本体实体命中 0 | 问题用词与名称/别名不匹配；实体被删除；开关关闭 | 补别名；确认 `ONTOLOGY_ENABLED` |
| 本体命中了但圈表没变 | 绑定角色/表名是否与 Schema 一致；boost 是否被更强关键词盖过 | 修正绑定；用 IDENTITY 提升权重 |
| 关联路径没注入 | 两张表是否都在圈定表/命中实体绑定表内；路径是否 DISABLED | 补绑定；启用路径 |
| 知识库检索不到 | 标题是否含口径类关键词；向量阈值是否过高；文档是否超长被切碎；相似度确实不足 | 改标题；调 `KNOWLEDGE_MIN_SCORE`；拆/并文档 |
| 知识库内容生效但用了错误枚举 | 与本体值域冲突被仲裁丢弃 | 统一枚举登记处 |
| 样例被召回但写法错误 | 样例已过期/口径错误 | 编辑或删除样例 |
| 样例完全不召回 | 样例数超过最近 100 条窗口；问题与样例 bigram/向量都不相似 | 清理旧样例；补典型问法 |
| 专家角色不对 | sortOrder 顺序；宽泛关键词抢占；角色被停用 | 调整 sortOrder/关键词 |
| 改了内置角色，升级后被还原 | `content_version` 同步机制 | 改为自定义角色 |
| 报表没遵守某条本体口径 | 报表链路未接本体 | 同步写入铁律或知识库 |
| 改了配置在 `shadow` 下无效果 | 记忆体 shadow 不注入 | 切 `on` 或 `off` 验证 |
| 导入报「无法识别的文件格式」 | `type` 字段不匹配（metric-definitions / iron-rules / knowledge-docs / sql-examples） | 用对应模块导出的文件 |
| 导入冲突太多 | 合并策略选择不当 | 先 dryRun 预检，再选 skip/overwrite |

## 11. 一页纸检查清单（上线前打勾）

- [ ] 每条铁律都是可判定、单一事实、优先用 `表.列 = 值` 写法
- [ ] 核心指标的归属表在 Schema 中存在，同义词覆盖业务口语，无过短同义词
- [ ] 指标总数（ACTIVE）不超过 200 条
- [ ] 本体实体有 IDENTITY 绑定，绑定表名与 Schema 完全一致
- [ ] 枚举只在「本体值域」或「知识库」其中一处登记，写法一致
- [ ] 知识库口径类文档标题含「口径/规则/枚举/速查/对比/模式」
- [ ] 每篇知识一个主题，没有重复指标表达式
- [ ] 样例库已清理过期口径与不存在表的样例
- [ ] 专家角色 sortOrder 具体职能在前，宽泛领域在后
- [ ] 用 3–5 个典型问题跑 trace，确认六个节点摘要符合预期
- [ ] 报表场景需要的规则，已同时写入铁律或知识库（本体对报表不生效）
