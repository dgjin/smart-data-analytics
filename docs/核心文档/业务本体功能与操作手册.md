## 0. 一分钟了解

**一句话定义**：业务本体是给问数系统用的「业务词典 + 取数地图」——把「机构」「本期」「项目归属机构」这些业务说法，登记成系统能理解的实体、表列绑定、取值含义、JOIN 路径与层级关系。

**它解决的核心问题**：大模型看得懂 SQL，但看不懂你们的业务黑话；Schema 里有几十张表几百个列，模型不知道「机构」该查哪张表、「BB=1」是什么、两张表该怎么 JOIN。业务本体就是把这些「人知道、模型不知道」的知识提前登记下来。

**生效方式**：登记即生效（状态 ACTIVE），**下一问立即参与**——问数时命中实体名或别名，就把绑定表加权进分析范围，并把四段说明注入提示词。无需重启、无需改配置。

**它不做什么**（边界必须清楚）：

- 不改变任何权限，不放开表白名单——SQL 最终仍受 Schema 白名单与安全执行层约束；
- 不直接拼接 SQL，不替模型做推理，只提供「推荐与释义」；
- 不引入 OWL/RDF、图数据库与推理机；路径检索是内存 BFS，不落图库；
- 不会因为登记了本体就必然改变 SQL——它是软提示，模型仍按铁律、指标、Schema 综合判断。

**五分钟上手**：

1. 系统管理 → 治理与审核 → 规则治理 → 顶部「业务本体」；
2. 选数据源 → 点「智能预填」→ 看预览 → 应用；
3. 回「实体与绑定」补绑定、改别名；
4. 去问一句含实体名的话，展开 trace 看「业务本体命中」；
5. 确认无误后保持「本体注入」开关开启。

## 1. 功能定位与作用

### 1.1 没有本体时，问数会踩的五类坑

| 典型问题 | 现象 | 根因 |
|---|---|---|
| 选错表 | 问「各机构客户数」，模型选了客户表而不是机构表，或漏掉机构维表 | 业务词与物理表没有映射 |
| 口径错位 | 「本期/同期」被当成字面字符串，或 `BB=1` 未加过滤 | 枚举取值含义未登记 |
| JOIN 臆造 | 两表关联列猜错、漏关联条件、笛卡尔积 | 关联口径只存在于人脑 |
| 层级混乱 | 「按集团汇总」按分公司列分组，或层级顺序颠倒 | 层级列序未登记 |
| 同义词漏召回 | 用户说「组织」，系统只认「机构」 | 别名未沉淀 |

业务本体的作用，就是把这五类「隐性知识」变成**显式、可版本化、可回滚**的治理资产。

### 1.2 四类资产各自管什么

| 资产 | 回答的问题 | 生效方式 | 是否按问题命中 |
|---|---|---|---|
| 业务实体 + 表列绑定 | 「机构」对应哪张表、哪个列？「主体/客体/时间/地理」是什么类型？ | 命中实体后，绑定表参与圈表加权（+3~+8，单表封顶 +15） | 是（名称/别名子串 + 描述相似度） |
| 值域释义 | `BB=1` 是什么意思？哪些列有枚举口径？ | 仅对**命中相关表**的列注入「表.列 = 值 → 含义」 | 是（跟随命中表过滤） |
| 关联路径 | 两张表按哪些列 JOIN？方向、JOIN 类型、基数是什么？ | 命中表之间的已登记路径注入；路径预览支持 ≤3 跳 BFS | 是（命中表之间） |
| 业务层级 | 「集团 > 分公司 > 项目」的由粗到细列序是什么？ | 作为【业务层级】段落注入，指导下钻与分组顺序 | 是（ACTIVE 层级按上限注入） |

四类资产不是四份孤立配置，而是**同一段提示词的四个段落**：实体决定「圈哪些表」，值域决定「过滤条件怎么写」，关联路径决定「多表怎么连」，层级决定「分组按什么顺序」。缺一段，模型就少一条依据。

### 1.3 在问数链路中的位置

```
用户问题
  │
  ├─ ① 加载本体快照（仅 ACTIVE，失败降级为空，不阻断问数）
  ├─ ② 实体匹配（名称/别名 + 描述相似度，可选 embedding 精排）
  ├─ ③ 圈表加权（绑定角色折算分数，参与 Schema 表选择）
  ├─ ④ 列裁剪 + 构造四段提示词（实体/值域/关联路径/层级）
  ├─ ⑤ 上下文仲裁（iron > metric > ontology > guidance > knowledge，总预算裁剪）
  ├─ ⑥ 注入 Stage-1 提示词 → LLM 生成 SQL
  └─ ⑦ SQL 安全执行（白名单、只读、行数上限等约束与本体无关）
```

关键点：本体只作用于 ③④⑤ 三步，**第 ⑦ 步的安全约束完全不受影响**。即使本体登记错了，最坏结果是「提示不准」，不会变成「越权查询」。

### 1.4 与相邻治理资产的分工

| 治理资产 | 管什么 | 与业务本体的关系 |
|---|---|---|
| 铁律规则 | 绝对不能怎么做（只读、白名单、敏感列） | 优先级最高，本体冲突时一律让位 |
| 语义指标 | 指标怎么算（口径表达式、同义词、审批状态） | 优先级高于本体；本体负责「实体/值域/路径」，不定义指标公式 |
| 业务本体 | 业务词对应哪张表、哪个值、怎么关联、什么层级 | 本文档主题 |
| 业务知识库 | 自由文本口径、术语、业务背景（RAG 检索） | 本体是结构化短条目，知识库是长文本；二者可互补，冲突时本体优先于知识块 |
| SQL 样例库 | 教模型「写法」的 few-shot | 只教形式，不定义口径 |
| 专家角色 | 阶段二解读口吻与视角 | 不参与 SQL 生成，与本体无直接关系 |

固定优先级（上下文仲裁器）：**铁律 > 语义指标 > 业务本体 > 业务口径摘要 > 知识库**。本体段超出预算时从本体段尾部裁剪，不会挤掉铁律与指标。

### 1.5 对三类角色的价值

- **管理员**：把散落在文档、聊天记录、老员工脑子里的口径，沉淀成可维护、可回滚的资产；用智能预填把「从零登记」变成「先审草案再修订」。
- **分析师**：不用在提问里反复解释「机构指的是 JGXX 表」「本期是 BB=1」，问法更自然，结果更稳定。
- **运维/实施**：无需改代码或重启即可上线/下线；出问题可一键关闭本体注入回退到「纯 Schema」行为，且资产与版本历史完整保留。

## 2. 核心概念与数据模型

### 2.1 四类资产与两张辅助表

系统在业务库中维护 6 张表（`initSchema()` 幂等建表，仅新增，不改动业务表）：

| 表 | 作用 | 关键约束 |
|---|---|---|
| `ontology_entities` | 业务实体（名称、类型、别名、说明、状态、版本） | `(data_source_id, name)` 唯一 |
| `ontology_bindings` | 实体与表/列的绑定及角色 | `(entity_id, table_name, column_name)` 唯一 |
| `ontology_value_notes` | 值域释义（表.列 = 值 → 含义） | `(data_source_id, table_name, column_name, value_code)` 唯一 |
| `ontology_relations` | 已登记 JOIN 路径（起止表列、JOIN 类型、基数、用途） | `(data_source_id, from_table, from_columns, to_table, to_columns)` 唯一 |
| `ontology_hierarchies` | 业务层级（名称 + 由粗到细的列序） | `(data_source_id, name)` 唯一 |
| `ontology_versions` | 版本快照（仅实体/关系/层级） | `(asset_type, asset_id, version)` 索引 |

**数据源隔离**：所有资产都带 `data_source_id`，不同数据源之间互不影响。切换数据源后，面板只显示该数据源的资产与计数。

### 2.2 业务实体与表列绑定

**实体**是业务概念的载体，字段规则如下：

| 字段 | 必填 | 规则 | 说明 |
|---|---|---|---|
| 实体名称 | 是 | ≤50 字，数据源内唯一 | 建议用业务常用词（机构、客户、项目），不要用表名 |
| 实体类型 | 是 | SUBJECT 主体 / OBJECT 客体 / TIME 时间 / GEO 地理 | 默认主体；用于提示词标注语义角色 |
| 业务别名 | 否 | ≤10 个，每个 ≤50 字，不能与名称重复 | 参与命中，建议收全同义词、缩写、列名（如 JGMC） |
| 说明 | 否 | ≤300 字 | 参与弱匹配（描述 bigram 相似度），写清业务范围与粒度 |
| 状态 | 是 | ACTIVE / DISABLED | 停用后不再参与加权与注入，数据保留 |

**绑定**把实体落到物理表列上，一条绑定 = 一个「表.列 + 角色」：

| 角色 | 含义 | 圈表权重 | 典型用法 |
|---|---|---|---|
| IDENTITY 标识 | 该列唯一标识这个实体 | +8 | `JGXX.JGMC`（机构名称） |
| RELATION_KEY 关联键 | 用于与其他表关联的键 | +4 | `JGXX.JGBH`（机构编号） |
| ATTRIBUTE 属性 | 实体的普通描述属性 | +3 | `JGXX.JGZT`（机构状态） |

规则与限制：

- **列名可空 = 表级绑定**：表示「这个实体整体对应这张表」，不指向具体列；表级绑定同样参与加权。
- 单个实体最多 20 条绑定；表名/列名必须是合法标识符（字母或下划线开头，仅字母数字下划线）。
- **整组替换语义**：面板保存时用当前草稿整体替换该实体的全部绑定，不是增量追加。删掉一行再保存，就等于删除该条绑定。
- 同一张表可被多个实体绑定，权重会累加，但**单表封顶 +15**，防止一张表因绑定过多而「垄断」圈表结果。
- 绑定不单独版本化：实体快照只保留实体定义，绑定变更不产生实体版本。若需追溯绑定历史，目前只能依赖操作日志与数据库审计，**不要指望「版本」按钮能回滚绑定**。

### 2.3 值域释义

值域释义回答「这个编码值在业务上是什么」：

- 唯一键：数据源 + 表 + 列 + 值编码；同一组合重复提交是 **upsert**（更新含义/状态），不会产生重复行。
- 字段限制：表名/列名合法标识符；值编码 ≤100 字；含义 ≤200 字。
- 批量写入：单次 ≤200 条，支持「值=含义」「值:含义」、全角等号、Tab 分隔（Excel 两列粘贴）、中文冒号；重复值后者覆盖；失败明细最多回传 20 条。
- **只对命中相关表注入**：问数时只取「本轮圈定表」相关列的释义，避免无关枚举稀释注意力。
- **无版本、无回滚**：值域只有新增/更新/停用/删除，删除不留版本快照。这是当前实现的重要边界，变更前请先在测试数据源验证或做好备份。

**什么该登记、什么不该登记**：

| 场景 | 是否登记 | 原因 |
|---|---|---|
| `BB=1 → 本期`、`BB=2 → 同期` | 登记 | 编码与含义不同形，模型无法从字面推断 |
| `SF=Y → 是`、`SF=N → 否` | 建议登记 | 虽可猜，但统一写法可减少 `'Y'/'1'/true` 混用 |
| 列说明已写「取值如：主营业务、金融市场业务」 | 不登记 | 文本型取值本身即含义，重复登记会挤占预算 |
| 指标列上的 `BB=1 防重复` 之类口径 | 不登记 | 属于计算口径，应进语义指标或知识库 |
| 值编码与含义完全相同（如 `北京 → 北京`） | 不登记 | 零信息增量 |

### 2.4 关联路径

关联路径登记「两张表之间怎么 JOIN」：

| 字段 | 规则 | 说明 |
|---|---|---|
| 起点表 / 终点表 | 合法标识符 | 方向按业务语义填，检索时支持反向遍历 |
| 起点列 / 终点列 | 必填，多列逗号分隔，两侧数量必须一致，各 ≤10 列，拼接 ≤300 字 | 多列即复合键，顺序一一对应 |
| JOIN 类型 | LEFT（默认）/ INNER / RIGHT | 不确定时用 LEFT，避免丢主表数据 |
| 基数 | `1:1` / `1:N` / `N:1`（默认）/ `N:N` | 表示「起点 → 终点」的基数，用于提示模型是否聚合去重 |
| 业务用途 | ≤300 字 | 会随路径一起注入，建议写「资产归属机构，按机构编号关联」 |
| 状态 | ACTIVE / DISABLED | 停用后不参与提示词与血缘声明边 |

能力与限制：

- **路径检索为内存 BFS**：最多 3 跳，最多返回 3 条最短路；关系量大时也不引入递归 CTE。
- 检索是**双向**的：登记 A→B 后，查 B→A 也能命中，返回的边上标记 `reversed`。
- 路径预览只做「已登记路径」检索，不会猜测未登记的外键关系；查不到时会明确提示未登记。
- 关联路径会同步到数据血缘图，作为 `joins` 类型的 declared 边（见 4.9）。
- 同一对表如果既登记 A→B 又登记 B→A，属于重复登记；唯一键按方向区分，不会自动去重，需人工避免。

### 2.5 业务层级

业务层级登记「由粗到细的分组列序」：

- 名称 ≤50 字，数据源内唯一；层级 ≥2 级、≤10 级。
- 每一级是一个**列名**（合法标识符），按由粗到细排列，例如「集团 > 分公司 > 项目」对应 `JTMC > FGSMC > XMMC`。
- 面板要求列名尽量来自真实 Schema（提供联想与未命中提示），但**不阻断**保存——允许先登记后建列，代价是注入后模型可能找不到该列。
- 注入时最多取前 5 个 ACTIVE 层级；超出按登记顺序截断。
- 层级只影响「分组/下钻顺序」的提示，不是强制 SQL 模板；模型仍会结合问题与 Schema 判断。

### 2.6 状态、版本与生效时机

**状态**：

| 状态 | 来源 | 含义 |
|---|---|---|
| ACTIVE 生效中 | 手工创建/启用 | 参与概览计数、圈表加权与提示词注入 |
| DISABLED 已停用 | 手工停用 | 退出注入与计数，数据与绑定保留 |
| PENDING 待确认 / REJECTED 已驳回 | 预留 | 当前版本**没有审批流**，管理端不会产生这两个状态（M3 规划） |

**版本**：

- 覆盖范围：**实体、关联路径、业务层级**三类；值域释义没有版本。
- 快照动作：CREATE / UPDATE / DELETE / RESTORE，均记录操作者与时间（`ontology_versions`）。
- 回滚语义：把指定版本的内容**写成一个新版本**（version+1，动作 RESTORE），不是删除中间历史；因此「回滚」本身也可再回滚。
- 实体回滚**不改变当前启停状态**：回滚只恢复名称/类型/别名/说明等定义，当前是停用就仍是停用。
- 删除会留快照，但**列表里已经看不到该资产**；回滚入口只对现存资产开放。需要恢复已删除资产时，当前版本没有「回收站」界面，只能通过数据库或重新创建。

**生效时机**：

- 资产写库即生效，下一问参与；没有「发布」按钮。
- 全局开关关闭后，下一问立即停止加权与注入，但资产、绑定、版本全部保留。
- **结果缓存**：同一问题在缓存有效期内可能直接复用旧结果，登记后立刻重问同一句可能看不到变化。验证请换一个新问法，或在结果卡片点「重新查询」强制刷新。

### 2.7 与执行层的关系

| 关注点 | 本体是否影响 |
|---|---|
| 表/列白名单 | 否。本体推荐的表若不在白名单，仍会被拒绝 |
| 权限与数据范围 | 否。不改变任何用户可见范围 |
| 只读与安全 SQL | 否。执行层约束独立生效 |
| 行数上限与超时 | 否 |
| SQL 写法与 JOIN 选择 | 是（软提示，可能影响） |
| 圈表范围 | 是（加权，可能影响） |

## 3. 工作原理

### 3.1 一次问数的七步

1. **加载快照**：按 `data_source_id` 并行读取五类 ACTIVE 资产（实体+绑定、值域、关系、层级）。读取失败不阻断问数，等价于「没有本体」，并记录告警。
2. **实体匹配**：问题文本与实体名称/别名/描述比对，得到候选实体及分数。
3. **圈表加权**：命中实体的绑定表按角色折算权重，叠加到 Schema 表选择打分上；单表封顶 +15。
4. **构造提示词**：按本轮实际圈定的表裁剪列，再生成四段本体说明；值域与关系只保留与命中表相关的条目。
5. **上下文仲裁**：本体块与铁律、指标、业务口径摘要、知识块一起排序、去重、冲突裁剪，受总预算约束（默认 6000 token 量级）。
6. **注入生成**：本体块位于「指标之后、业务口径与知识之前」，模型据此生成 SQL。
7. **执行与留痕**：安全执行 SQL；trace 记录「业务本体命中」与「上下文仲裁」两步，血缘图补 `joins` 声明边。

### 3.2 实体匹配打分

确定性规则（无 LLM 调用，零额外延迟）：

| 信号 | 计分 | 说明 |
|---|---|---|
| 问题包含实体名称 | +10 | 子串匹配，区分大小写按原文 |
| 问题包含任一如别名 | +10 | 多个别名同时命中只计一次；与名称命中分别计分 |
| 描述相似度 | 0~+2 | 问题与描述的 bigram 重合率 × 2，作为弱信号兜底 |

因此「名称 + 别名同时命中」最高 20 分；描述只能补足，不能单独压过名称命中。

**可选 embedding 精排**：当命中实体多于 1 个且 embedding 可用时，对候选做向量余弦相似度，叠加 `余弦 × 10` 重新排序；任何失败（无模型、网络异常）自动降级为纯关键词排序，不影响问数。可用 `ONTOLOGY_EMBEDDING_ENABLED=0` 显式关闭（本地无 embedding 模型时建议关闭，省一次往返）。

**命中示例**：

- 登记实体「机构」，别名「机构名称、JGMC、组织」。
- 问「各机构的客户拜访次数是多少？」→ 命中「机构」名称，score=10。
- 问「按组织统计客户数」→ 命中别名「组织」，score=10。
- 问「各分行客户数」→ 若未登记「分行」别名，只能靠描述相似度得到低分，可能不命中。**这就是要收全同义词的原因**。

### 3.3 圈表加权

命中实体的绑定表获得权重：

```
表得分增量 = Σ(该表上所有命中实体的绑定角色权重)
IDENTITY=8，RELATION_KEY=4，ATTRIBUTE=3
单表增量 = min(增量, 15)
```

示例：实体「机构」在 `JGXX` 上有 IDENTITY(`JGMC`) + RELATION_KEY(`JGBH`) + ATTRIBUTE(`JGZT`)，则 `JGXX` 得 8+4+3=15（封顶）；实体「项目」也在 `JGXX` 上有 1 条 RELATION_KEY，则总增量 19 → 仍按 15 计。

加权只影响「哪些表进入候选与提示词」，不保证模型一定使用；最终仍由模型结合问题与 Schema 决定。

### 3.4 四段提示词与预算

命中实体后生成本体段，格式固定：

```
【业务实体】（管理员登记的业务实体与绑定，问题涉及这些实体时必须使用其绑定表/列）
- 机构（SUBJECT；别名：机构名称、JGMC；绑定：JGXX.JGMC[IDENTITY]、JGXX.JGBH[RELATION_KEY]；说明：…）

【值域释义】（枚举/编码列的权威取值含义，过滤条件必须按此写法）
- JGXX.BB = 1 → 本期
- JGXX.BB = 2 → 同期

【关联路径】（管理员登记的 JOIN 路径，涉及多表关联时优先按此写法）
- JGXX(JGMC) -[LEFT, 1:N]-> XMXX(JGDM)（项目归属机构）

【业务层级】（下钻/分组时按层级列序由粗到细）
- 机构层级：JTMC > FGSMC > XMMC

【本体使用约束】以上本体信息仅作推荐与释义：优先级 铁律 > 语义指标 > 业务本体 > 业务口径 > 知识库；
关联路径未经登记时不得臆造 JOIN 条件，最终表/列仍须严格取自 Schema 白名单。
```

预算与截断：

- 本体段预算默认 **1500 token**（近似值），可用 `ONTOLOGY_TOKEN_BUDGET` 调整，最小有效值 200，低于 200 或非法值回退 1500。
- 段内按行追加，超预算即停止；某段一行都放不下时，该段头会被撤销，不留空标题。
- 注入上限：实体 8、值域 40、关联路径 12、业务层级 5。**这些是单次注入上限，不是登记上限**；登记更多资产不会报错，但超出部分不会被注入。
- 实体按匹配得分降序取前 8；值域按查询顺序取前 40；层级按登记顺序取前 5。极端情况下「重要但排在后面」的资产可能进不了提示词，应通过停用低价值资产来控制。

### 3.5 上下文仲裁

本体块不是「无条件全量拼进去」，而是与其它上下文一起仲裁：

| 块 | 优先级 | 超预算时 |
|---|---|---|
| 铁律 | 最高 | 最后被裁剪 |
| 语义指标 | 高 | 优先保留 |
| 业务本体 | 中 | 在铁律/指标之后裁剪 |
| 业务口径摘要 | 较低 | 先于本体被裁剪 |
| 知识库 | 最低 | 最先被裁剪 |

仲裁还会做去重与 `表.列 = 值` 冲突裁剪，避免同一枚举在两处给出不同含义。最终各块 token 数与裁剪统计会写进 trace 的「上下文仲裁」步骤，便于判断「到底是本体没生效，还是被裁掉了」。

### 3.6 降级与容错

| 故障 | 行为 |
|---|---|
| 本体读取失败（DB 异常） | 返回空快照，问数继续；记录告警 |
| embedding 精排失败 | 降级为关键词排序 |
| 提示词构造异常 | 本体段为空，主链路不受影响 |
| 开关关闭 | 完全不加载、不加权、不注入，行为回到「纯 Schema」 |
| 结果缓存命中 | 复用缓存结果，不重新走本体链路（缓存键区分开/关本体两种变体） |

设计原则：**本体是增强项，不是依赖项**。任何本体侧异常都不应导致问数失败。

### 3.7 观测：trace 与血缘

- **trace**：每次问数新增两步（在问数结果的「推导回放」中可查看；ADMIN 也可用 `GET /api/ops/traces` 查请求级链路瀑布）：
  - 「业务本体命中」：命中实体数及名称、加权表数、关联路径数、注入 token 数；
  - 「上下文仲裁」：本体块等各块 token 与裁剪统计。
- **血缘**：ACTIVE 关联路径会生成 `joins` 类型的 declared 边，边上带基数、JOIN 类型、关联列与用途；表不存在时标记 stale。`joins` 边**不计入**解析覆盖率分母，前端图例中显示为「关联路径」，避免把治理声明误当成血缘解析结果。

## 4. 功能清单

### 4.1 面板总览

进入「业务本体」后，顶部是统一操作区，自上而下：

1. **数据源选择**：下拉切换数据源，所有资产与计数随数据源隔离。
2. **智能预填**：基于该数据源 Schema 生成四类资产草案（先预览后写入）。
3. **本体注入开关**：一键启停本体参与问数（写入 `ONTOLOGY_ENABLED`，下一问生效）。
4. **刷新概览**：重新拉取五类 ACTIVE 计数。
5. **五张计数卡**：业务实体 / 表列绑定 / 值域释义 / 关联路径 / 业务层级；除「表列绑定」外均可点击直达对应子页签，当前页签高亮。
6. **子页签**：实体与绑定 / 值域释义 / 关联路径 / 业务层级。

计数口径提醒：前四项只统计 ACTIVE；**「表列绑定」统计该数据源下全部绑定**（绑定没有独立状态，随实体停用而不参与注入）。

### 4.2 智能预填

读取数据源已保存的 Schema（表名、列名、中文描述），用纯规则引擎推断四类资产：

| 推断对象 | 规则 | 产出上限 |
|---|---|---|
| 实体与绑定 | ① 表主题：去「宽表/明细表/统计表」等后缀生成表级 IDENTITY 绑定，首个日期列登记为 RELATION_KEY；② 编号-名称列对：`XXXBH/XXXDM/XXXID` 与 `XXXMC` 配对生成概念实体，跨表同名概念合并绑定 | 10 个实体 |
| 值域释义 | 识别 `X=Y`、`取值：`、`取值如：`、`如：` 等描述；跳过指标列、自指、SQL 片段；代码与含义同形不生成 | 200 条 |
| 关联路径 | 两表共有的编号类维度列生成 `N:1 LEFT`，大表指向小表，用途标注「自动推断，使用前请复核」 | 12 条 |
| 业务层级 | 识别「一级/二级/三级/四级」+ 分类/行业/地域列族，以及「所属省/所属市」，按由粗到细输出 | 5 个 |

特性：

- **默认只预览不写库**（`apply=false`）；确认后点「应用 N 项」才写入。
- **幂等**：同名实体、同键值域、同方向关联、同名层级默认跳过，不覆盖人工维护内容；`overwrite=true` 才更新已存在项（界面默认不覆盖）。
- 所有写入都留版本快照（实体/关系/层级可回滚）。
- 推断不出的项列在「未自动生成的项」，按提示手工补登记。
- 前置条件：数据源必须已提取 Schema，否则返回 400；数据源不存在返回 404。

### 4.3 实体与绑定

- 列表：实体名称、类型徽标、别名、绑定条数、状态与版本、操作列。
- 检索：按名称/别名/说明/绑定表列即时过滤；「仅看未绑定」快速定位漏配实体。
- 新建/编辑：名称、类型、别名、说明；创建即 ACTIVE。
- 绑定维护：行内展开，表/列输入带 Schema 联想（未命中仅黄色提示不阻断）；角色三选一；支持 Enter 在当前行后新增、Ctrl/Cmd+Enter 保存。
- 脏标记：草稿与库内不一致时显示「有未保存改动」，按钮变为「保存绑定」；一致时按钮为「已保存」并禁用。
- 停用/启用：停用后退出加权与注入，绑定保留。
- 删除：级联删除该实体全部绑定，并写入删除快照；不可恢复（界面无回收站）。

### 4.4 值域释义

- 筛选：值/含义关键字、按表名、按列名（全量加载后本地过滤，输入即筛）。
- 单条新增：表名、列名、值编码、含义；同唯一键重复提交为覆盖更新。
- 批量粘贴：先在上方选定「表.列」，再粘贴多行；支持 `=`、全角 `＝`、中文冒号、单逗号、Tab（Excel 两列）；实时显示「将写入 / 重复 / 无法解析」；单次 ≤200 条。
- 行内操作：编辑（含义 + 状态）、停用/启用、删除。
- **无版本历史**：值域的修改与删除不可回滚，重要变更建议先在测试数据源验证。

### 4.5 关联路径

- 新建/编辑表单：起点表、起点列、终点表、终点列、JOIN 类型、基数、业务用途。
- 校验即时反馈：起止列必填、两侧列数一致；不满足时提交按钮禁用。
- 「交换起点 / 终点」：一键对调，减少重复录入。
- 路径预览：输入任意起止表，点「检索最短路」，返回 ≤3 跳、最多 3 条已登记路径；未登记时明确提示。
- 列表：按表名/列名/用途筛选；每条展示正反向与基数；支持停用/启用、编辑、版本、删除。

### 4.6 业务层级

- 新建/编辑：层级名称 + 逐级编辑器（输入、上移/下移、增删，至少 2 级）；底部实时预览「A > B > C」；「填入示例」快速体验。
- 列表：名称、层级序列、状态、版本；按名称或列名搜索。
- 停用后保留数据但不再注入。

### 4.7 版本历史与回滚

- 入口：实体/关联路径/业务层级行内「版本」按钮。
- 展示：版本号、动作标签（创建/更新/删除/回滚）、操作者、时间、可读摘要；首条标「最新」。
- 回滚：非最新版本可点「回滚到此版本」，二次确认后生成一个新版本（version+1，动作 RESTORE），当前内容保留为历史。
- 回滚后子面板自动刷新，概览计数同步更新。
- 边界：只作用于治理元数据，不改变执行层 Schema，也不重写已生成 SQL；值域没有版本。

### 4.8 全局开关

- 位置：数据源选择右侧「本体注入」开关。
- 开启态：绿色，显示「本体注入已开启」；关闭态：灰色 + 琥珀色提示条。
- 语义：关闭后**只停止加权与注入**，不删除任何资产，不改权限；下一问立即生效。
- 同源：状态写入 `env_config.ONTOLOGY_ENABLED`，与「系统管理 → 环境配置」是同一个键，任一处修改都即时热更；重启后以保存值为准。
- 读取失败时开关置为不可操作，资产浏览与维护不受影响。

### 4.9 与血缘、评测、审计的联动

| 数据血缘 | ACTIVE 关联路径生成 `joins` declared 边，图例显示「关联路径」；不计入解析覆盖率 |

## 5. 操作步骤

### 5.0 前置条件

| 条件 | 说明 | 不满足时 |
|---|---|---|
| 已用 ADMIN 登录 | 写操作全部要求 ADMIN | 只读可见，按钮无写权限或接口 403 |
| 数据源已接入 | 「数据源与 Schema」中已添加数据源 | 面板提示「暂无可用数据源」 |
| Schema 已提取 | 表/列/中文描述已保存 | 智能预填返回 400；手工登记仍可用但无联想 |
| 明确目标问数场景 | 建议先列 3~5 个高频问题与涉及表 | 容易堆砌无关资产，稀释注入预算 |

### 5.1 进入面板

1. 左侧「系统管理」→「治理与审核」分组 →「规则治理」；
2. 顶部 Tab 选「业务本体」；
3. 在顶部下拉选择数据源（默认选中第一个）。

此时应看到五张计数卡（新数据源全为 0）与四个子页签。若开关显示「本体注入…」并不可点击，说明设置读取失败，先检查后端与网络，不影响资产维护。

### 5.2 第一步：智能预填（推荐起点）

1. 选好数据源，点右上「智能预填」；
2. 等待「正在分析 Schema 并生成本体草案…」结束，弹窗显示 5 张计数卡（实体/绑定/值域/关联/层级）与四个分组，标题下方另显示表数与列数；
3. **逐条审阅草案**（实体名称/别名/绑定、关系用途、层级顺序），重点关注：
   - 实体名称是否业务常用词（如「主营业务」是否应叫「业务条线」）；
   - 别名是否含歧义短词；
   - 关系方向与基数是否符合实际（自动推断默认「大表 → 小表、N:1、LEFT」）；
   - 层级列序是否由粗到细；
4. 看底部「未自动生成的项」，记下需要手工补的编号列/层级；
5. 点「应用 N 项」；写入完成后显示新增/更新/绑定/值域/关系/层级统计与错误明细；
6. 点「完成并刷新」，四个子页签与概览自动刷新。

**注意**：预填是「草案生成器」，不是「一键正确」。自动推断的路径用途已标注「使用前请复核」，生产数据源务必逐条核对表、列、基数。

### 5.3 第二步：实体与绑定

#### 5.3.1 新建实体

1. 子页签「实体与绑定」→ 右上「新建实体」；
2. 填写：
   - 实体名称：如「机构」（≤50 字，数据源内唯一）；
   - 实体类型：主体/客体/时间/地理；
   - 别名：如「机构名称、JGMC、组织」（逗号分隔，≤10 个）；
   - 说明：如「机构主数据，覆盖集团/分公司/项目三级」（≤300 字）；
3. 可点「填入示例」快速看格式；
4. 点「确认创建」。重名会提示「同名业务实体已存在」（HTTP 409）。

#### 5.3.2 维护绑定

1. 在实体行点「维护绑定」展开绑定区；
2. 点「添加绑定」，逐行填写：
   - 表名：如 `JGXX`（带 Schema 联想）；
   - 列名：如 `JGMC`；**留空表示表级绑定**；
   - 角色：标识 / 关联键 / 属性；
3. 重复第 2 步添加多条；行尾垃圾桶可移除；最后一行按 `Enter` 可直接新增一行；
4. 观察顶部徽标：出现「有未保存改动」说明草稿与库内不一致；
5. 点「保存绑定」（或 `Ctrl/Cmd + Enter`）。成功后按钮变「已保存」，徽标变「与库内一致」；
6. 需要放弃修改时点「重置」；切换实体或收起时若有未保存改动会二次确认。

#### 5.3.3 绑定配置建议

| 实体 | 表.列 | 角色 | 理由 |
|---|---|---|---|
| 机构 | `JGXX.JGMC` | 标识 | 名称是业务最常用识别列 |
| 机构 | `JGXX.JGBH` | 关联键 | 编号用于跨表 JOIN |
| 机构 | `JGXX.JGZT` | 属性 | 状态是筛选属性，权重低 |
| 机构 | `JGXX`（列空） | 标识 | 表级兜底：不确定具体列时先绑定整表 |

绑定不是越多越好：同一实体绑 20 列会让该表必然拿满 +15，反而压制其他候选表。**优先 1 个标识 + 1 个关联键**，属性按需补。

### 5.4 第三步：值域释义

#### 5.4.1 单条新增

1. 子页签「值域释义」，在上方表单填写表名（如 `JGXX`）、列名（如 `BB`）、值（如 `1`）、含义（如 `本期`）；
2. 点「新增/覆盖」。若同「表.列.值」已存在，会覆盖含义而不是新增一行。

#### 5.4.2 批量粘贴（推荐）

1. 先在上方选定表名与列名（批量写入的目标）；
2. 在「批量粘贴」文本框中每行一条，例如：

   ```
   1=本期
   2=同期
   9=其他
   ```

3. 支持 `值:含义`、全角 `＝`、中文冒号、Excel 两列直接粘贴（Tab 分隔）；重复值按后者覆盖；
4. 观察实时预览：「将写入 N 条 / 重复 N 条 / 无法解析 N 行」；
5. 点「批量保存」。单次超过 200 条会被拒绝；部分失败仍返回 200 与成功/失败统计，失败明细最多显示 20 条。

#### 5.4.3 维护

- 行内「编辑」可改含义与状态（生效中/已停用）；
- 「停用」只停止注入，不删除；「删除」不可回滚（无版本）。

### 5.5 第四步：关联路径

1. 子页签「关联路径」→ 点「登记路径」；
2. 填写起点表 `JGXX`、起点列 `JGBH`、终点表 `XMXX`、终点列 `JGDM`；
3. 选择 JOIN 类型（LEFT/INNER/RIGHT）与基数（起点 → 终点，如 `1:N`）；
4. 填写业务用途：「项目归属机构，按机构编号关联」；
5. 若方向填反，点「交换起点 / 终点」；
6. 点「确认登记」。校验失败会就地提示：起止列必填、两侧列数必须一致、列名必须是合法标识符；
7. 保存后用「路径预览」验证：输入起点表 `JGXX`、终点表 `XMXX`，点「检索最短路」，应返回刚登记的 1 跳路径；
8. 多跳场景（A→B→C）无需重复登记 A→C，BFS 会自动串联，但最多 3 跳。

**常见错误**：把「关联键」写成中文列名、两侧列数不一致（如左侧两列右侧一列）、把方向与基数写反（`N:1` 写成 `1:N`）。这些都会导致提示词给出错误的 JOIN 建议。

### 5.6 第五步：业务层级

1. 子页签「业务层级」→「新建层级」；
2. 填写名称，如「机构层级」；
3. 在层级编辑器中逐级输入列名：`JTMC` → `FGSMC` → `XMMC`；
4. 用上下箭头调整由粗到细顺序，可增删（至少 2 级、最多 10 级）；
5. 底部预览应为「JTMC > FGSMC > XMMC」；
6. 点「确认创建」。列表显示层级序列与状态，可按名称/列名搜索。

层级只影响「下钻/分组顺序」的建议，不会自动生成下钻 SQL；真正下钻仍由用户问题与模型决定。

### 5.7 第六步：开关与效果验证

1. 确认顶部开关为「本体注入已开启」（绿色）；
2. 用一个**包含实体名或别名**的新问题提问，例如「各机构的客户拜访次数是多少？」；
3. 在问数结果卡片点「推导回放」，找到「业务本体命中」与「上下文仲裁」两步（ADMIN 也可用 `GET /api/ops/traces?limit=20` 查请求摘要），检查：
   - 「业务本体命中」：实体命中数 > 0、加权表数 > 0、注入 token 数 > 0；
   - 「上下文仲裁」：本体块 token 未被裁到 0；
4. 若注入为 0，按第 9 章逐项排查；
5. 需要对照实验时，由 ADMIN 调接口带 `disableOntology: true` 重问，或运行 `npm run eval -- --ontology off`；
6. 打开「数据血缘」，确认 ACTIVE 关联路径以「关联路径」图例出现。

**验证注意**：同一问题在结果缓存有效期内会直接复用旧结果，登记后立刻重问可能「看不出变化」。请换一个新问法，或在结果卡片点「重新查询」。

### 5.8 日常维护操作

| 操作 | 路径 | 影响 | 可恢复性 |
|---|---|---|---|
| 编辑实体/关系/层级 | 行内「编辑」 | 立即生效，version+1 | 版本回滚 |
| 修改绑定 | 行内「维护绑定」→ 保存 | 立即生效 | **无版本**，只能手改回 |
| 修改值域含义 | 行内「编辑」 | 立即生效 | **无版本** |
| 停用 | 行内电源图标 | 退出加权/注入与计数，数据保留 | 一键启用 |
| 删除 | 行内「删除」 | 数据移除；实体级联删绑定 | 实体/关系/层级留快照但界面无入口；值域不可恢复 |
| 回滚 | 行内「版本」→ 选版本 → 回滚 | 生成新版本，不改启停状态 | 可再次回滚 |
| 全局关闭 | 顶部开关 | 停止全部本体参与，资产保留 | 一键开启 |

### 5.9 交互快捷键与提示

| 场景 | 操作 |
|---|---|
| 实体绑定新增一行 | 在最后一行按 `Enter` |
| 实体绑定保存 | `Ctrl/Cmd + Enter` |
| 关闭弹窗 | `Esc`（回滚进行中不可关闭） |
| 检索实体 | 顶部搜索框，支持名称/别名/说明/绑定表列 |
| 清除筛选 | 无结果时点「清除筛选」 |
| 未保存提醒 | 切换实体/收起绑定/关闭页面时二次确认 |

## 6. 典型场景实战

以下场景均可在测试数据源复现。表名为示例，请替换为实际 Schema。

### 6.1 场景一：统一「机构」口径

**背景**：业务库中机构信息在 `JGXX`，项目表 `XMXX` 用 `JGDM` 关联；用户常说「机构」「组织」「分行」，模型经常选错表或漏掉机构维表。

**配置**：

1. 实体「机构」，类型主体，别名「机构名称、JGMC、组织、分行」，说明「机构主数据，覆盖集团/分公司/项目三级」；
2. 绑定：`JGXX.JGMC`（标识）、`JGXX.JGBH`（关联键）；
3. 关联路径：`JGXX(JGBH) → XMXX(JGDM)`，LEFT，`1:N`，用途「项目归属机构」。

**验证问题**：「各机构的项目数量是多少？」

**预期**：

- trace「业务本体命中」：实体命中 1（机构）、加权表 ≥1、注入 token > 0；
- 生成的 SQL 使用 `JGXX` 作为机构维表，按 `JGBH/JGDM` 关联 `XMXX`，而不是按名称模糊匹配或漏表；
- 血缘图出现 `JGXX → XMXX` 的「关联路径」边。

### 6.2 场景二：消除枚举值歧义

**背景**：报表列 `BB` 存储 `1/2`，分别表示「本期/同期」；用户问「去年同期收入」时，模型可能直接过滤 `BB='同期'` 或漏掉过滤。

**配置**：

1. 值域：`JGXX.BB = 1 → 本期`、`JGXX.BB = 2 → 同期`；
2. 若同一编码在多表复用，需按表分别登记（值域按「表.列」隔离）。

**验证问题**：「本期和同期的收入分别是多少？」

**预期**：

- 提示词出现【值域释义】两行；
- SQL 过滤条件写成 `BB = 1` / `BB = 2`（或 `IN`），而不是中文字符串；
- 若模型仍写错，检查该表是否真的进入命中表集合（值域只注入命中表相关列）。

### 6.3 场景三：多表 JOIN 不再臆造

**背景**：`HTXX`（合同）与 `KFXX`（客户）通过「客户编号 + 机构编号」复合键关联；模型经常只按客户名称 JOIN，导致重复或漏数。

**配置**：

1. 关联路径：起点 `HTXX`，列 `KHBH,JGBH`；终点 `KFXX`，列 `KHBH,JGBH`；JOIN `LEFT`；基数 `N:1`；用途「合同归属客户，复合键关联，避免同名客户串号」；
2. 两侧列顺序必须一一对应，数量一致。

**验证问题**：「各客户的合同金额合计是多少？」

**预期**：

- 提示词【关联路径】出现两列复合键；
- SQL 的 `ON` 同时包含两个条件；
- 路径预览能检索到 1 跳路径。

**注意**：如果登记时把两列写成一列，服务端会拒绝（两侧数量必须一致）；如果列名拼错，保存能通过（只校验标识符），但提示词会给出不存在的列，模型可能报错或改写——**保存后务必用路径预览与真实 Schema 对照**。

### 6.4 场景四：层级下钻不串级

**背景**：机构有「集团 > 分公司 > 项目」三级，用户说「按集团汇总」时，模型按项目列分组，导致结果过细。

**配置**：

1. 层级名称「机构层级」；
2. 层级序列：`JTMC` → `FGSMC` → `XMMC`（由粗到细）；
3. 确认三列都真实存在于命中表。

**验证问题**：「按集团汇总客户数」

**预期**：

- 提示词出现【业务层级】「机构层级：JTMC > FGSMC > XMMC」；
- SQL 按 `JTMC` 分组，而不是 `XMMC`；
- 若用户追问「再按分公司拆分」，模型能沿层级向下选择 `FGSMC`，而不是回到最细粒度。

### 6.5 场景五：智能预填 + 人工复核（推荐落地路径）

以本项目实测的「数据资源」数据源（2 张宽表 / 298 列）为例：

1. 智能预填生成：10 个实体 / 28 条绑定 / 4 条值域 / 4 条关联 / 4 个层级；
2. 人工复核重点：
   - 实体名是否业务化（「主营业务」是否应改为「业务条线」）；
   - 自动推断的 4 条 `N:1 LEFT` 路径是否与真实主外键一致；
   - 值域是否只保留了「代码 ≠ 含义」的项；
   - 层级列序是否由粗到细；
3. 二次执行预填：60 项全部跳过，验证幂等，不会覆盖手工修改；
4. 落库后问数，提示词四段完整注入 1402 字符（未触发预算截断）；
5. 观察一周问数质量后再决定是否补充更多实体或别名。

这条路径的价值：把「从零登记」变成「审草案」，通常 30 分钟内可完成一个数据源的首版本体。

## 7. 配置规范与最佳实践

### 7.1 命名与别名

| 规范 | 建议 | 反例 |
|---|---|---|
| 实体名 | 用业务最常用名词，2~6 字 | 「JGXX 机构信息宽表」 |
| 别名 | 收全同义词、缩写、常见列名、口语说法；≤10 个 | 只写一个英文列名 |
| 别名歧义 | 避免「单」「号」「表」这类过短词 | 别名「单」会命中「订单/单据/单价」 |
| 说明 | 写业务范围 + 粒度 + 与其他实体的区别 | 「机构表」（无信息量） |
| 不要重复 | 别名不要与名称完全相同 | 名称「机构」+ 别名「机构」 |

判断别名是否值得加：**用户会不会在提问里说这个词？** 会，就加；只是数据库列名而用户从不说，可不加（列名可放在绑定里）。

### 7.2 绑定策略

1. 每个实体至少一条绑定，否则只参与匹配不参与加权（提示词仍会显示「未维护绑定」）；
2. 优先「1 标识 + 1 关联键」，属性按需；
3. 不确定具体列时用表级绑定兜底，之后再细化；
4. 同一实体绑同一张表的多列会累加到封顶 +15，注意不要「霸榜」；
5. 列名必须与 Schema 完全一致（大小写按数据源实际），否则模型可能找不到列；
6. 绑定是整组替换：多人同时维护同一实体时，后保存者覆盖前者，需约定维护窗口。

### 7.3 值域取舍

- 只登记「代码 ≠ 含义」且用户会用来筛选/分组的列；
- 文本型枚举若列说明已完整，不重复登记；
- 指标计算口径不要塞进值域，放语义指标；
- 同一列值域建议一次批量粘贴完成，避免逐条覆盖；
- 单列释义很多时（如行政区划几百个值），只登记高频值，避免挤占 40 条注入上限；
- 值域无版本：大批量覆盖前先导出/备份（可通过 `GET /api/ontology/value-notes` 留存）。

### 7.4 关联路径

- 只登记**真实存在**的 JOIN 关系，不要把「可能相关」写成路径；
- 方向按「事实表 → 维表」或业务语义填写；系统支持反向遍历，无需重复登记反向；
- 基数不确定时优先 `N:1`（事实 → 维度最常见），并在用途里写清；
- 多列复合键必须两侧数量一致、顺序对应；
- 用途写「业务含义 + 关联依据」，这句话会进入提示词，直接影响模型判断；
- 关系数量多时优先登记高频 JOIN，上限 12 条注入，超出按登记顺序截断。

### 7.5 业务层级

- 层级必须是同一分析视角下的列族（组织/地域/产品/时间），不要把无关列拼在一起；
- 由粗到细，最少 2 级；列名必须真实；
- 一个数据源可登记多个层级（如「机构层级」「地域层级」），注入取前 5 个；
- 层级不是计算字段，不支持下钻表达式；需要派生列请先在数据源侧建好。

### 7.6 预算治理

| 资源 | 上限 | 超出行为 | 治理建议 |
|---|---|---|---|
| 单次实体注入 | 8 | 按匹配得分降序截断 | 停用低价值实体，或提高别名精度 |
| 单次值域注入 | 40 | 按查询顺序截断 | 只登记高频枚举；按表收敛 |
| 单次关系注入 | 12 | 按登记顺序截断 | 优先登记高频 JOIN；停用低频 |
| 单次层级注入 | 5 | 按登记顺序截断 | 只保留常用分析视角 |
| 本体段预算 | 1500 token（可配） | 段内按行截断，段头自动撤销 | 精简说明/用途文字；减少资产数量 |
| 上下文总预算 | 约 6000 token | 按优先级裁剪 | 本体位于中优先级，先于业务口径/知识被裁 |

判断是否超预算：看 trace「业务本体命中」的注入 token 数是否接近 1500，以及「上下文仲裁」中本体块是否被裁剪。若长期顶格，说明资产过载，应做减法而不是继续加。

### 7.7 变更流程（建议）

1. **草案**：智能预填 dryRun，或在测试数据源手工登记；
2. **复核**：业务方确认实体名、别名、值域、关系方向与基数、层级顺序；
3. **小步上线**：先上 1~2 个高频实体，观察一周；
4. **对照评测**：用 `--ontology on/off` 双跑同一评测集，确认没有负向退化；
5. **扩量**：逐步补值域、关系、层级；
6. **留退路**：每次批量变更前记录版本号；值域先导出；必要时关闭全局开关回退。

### 7.8 多数据源与环境

- 资产按数据源隔离，同一业务概念在不同数据源需分别登记；
- 不同环境（开发/测试/生产）的本体不自动同步，需通过接口或 SQL 迁移；
- 生产变更建议先在测试数据源验证注入效果，再复制到生产；
- 切换数据源后概览与列表都会变化，不要误以为资产丢失。

### 7.9 停用与删除的选择

| 诉求 | 操作 | 原因 |
|---|---|---|
| 暂时不想让它参与问数 | 停用 | 保留数据与绑定，一键恢复 |
| 名称/口径写错，想回到旧版 | 版本回滚 | 生成新版本，历史保留 |
| 资产重复/废弃 | 删除 | 实体级联删绑定；值域不可恢复 |
| 整体回退到「纯 Schema」 | 全局开关关闭 | 资产全部保留，下一问生效 |

**默认选停用**。删除只在确认无历史价值时使用，尤其是值域——它没有版本与回收站。

### 7.10 常见反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 把整张宽表的所有列都绑给一个实体 | 单表封顶 +15，压制其他表；提示词冗长 | 只绑标识/关联键/关键属性 |
| 别名堆到 10 个且含超短词 | 误命中率上升，无关问题也注入 | 只收用户真实会说的词 |
| 给每列都登记值域 | 40 条上限被低价值项占满 | 只登记代码≠含义的高频列 |
| 登记「可能相关」的 JOIN | 模型按错误路径连接，结果偏差 | 只登记验证过的真实关联 |
| 层级列序写反 | 下钻方向错误 | 由粗到细，保存前看预览 |
| 直接在生产大改值域 | 不可回滚，出错难恢复 | 先导出/测试源验证，分批写入 |
| 用本体替代语义指标 | 指标口径仍不稳定 | 计算口径进指标库，本体只做映射 |

## 8. 验收与回归

### 8.1 配置完成自检

- [ ] 数据源选择正确，概览计数与预期一致（计数只算 ACTIVE）
- [ ] 每个实体至少 1 条绑定；关键实体有标识 + 关联键
- [ ] 别名覆盖用户常用说法，无超短歧义词
- [ ] 值域只登记代码≠含义的项，批量写入条数与预期一致
- [ ] 关联路径两侧列数一致、方向与基数正确、用途可读
- [ ] 层级 ≥2 级、由粗到细、列名真实存在
- [ ] 无重复实体/层级；无重复反向关系
- [ ] 开关状态符合预期（生产一般保持开启）

### 8.2 效果验收（trace 三个数）

对每个高频问题提问一次，查看「业务本体命中」：

| 指标 | 期望 | 异常含义 |
|---|---|---|
| 实体命中数 | ≥1 | 0 表示名称/别名未覆盖，或问题不含实体词 |
| 加权表数 | ≥1 | 0 表示实体没绑定，或绑定表名与 Schema 不一致 |
| 注入 token | >0 且未顶格 1500 | 0 表示被预算裁掉或开关关闭；接近上限表示资产过载 |
| 关联路径数 | 多表问题应 ≥1 | 0 表示未登记或命中表不在路径两端 |

再看「上下文仲裁」：本体块是否被裁到 0；若被裁，先减资产或提预算，而不是盲目继续加。

### 8.3 A/B 对照方法

- 接口：ADMIN 调 `POST /api/query/natural-language` 时带 `disableOntology: true`，与默认请求对比 SQL 与结果；
- 评测：`npm run eval -- --ontology off`（或 `--ontology on`）双跑同一评测集，比较均值与单跑跌幅；
- 注意：开关状态进入结果缓存变体键，开/关两组不会互相复用缓存，可放心对照。

### 8.4 验收判据

| 现象 | 判定 |
|---|---|
| 同一问题 SQL 从「漏机构表」变为「正确 JOIN 机构表」 | 通过 |
| 枚举过滤从中文/错误值变为登记编码 | 通过 |
| 层级分组从最细粒度变为正确层级列 | 通过 |
| SQL 结果与人工核对一致，且未触发安全拦截 | 通过 |
| SQL 使用了不存在的列/表 | 不通过：检查绑定、关系列名是否与 Schema 一致 |
| 注入 token 长期 0 | 不通过：按第 9 章排查 |
| 关/开本体结果无差异 | 可能未命中或资产无效，检查问题是否含实体词 |

### 8.5 自动化用例索引

维护回归请配合《业务本体维护测试案例》执行，覆盖：

- 入口与权限（管理员可写、分析师只读）
- 概览计数与页签跳转
- 实体创建/重名/检索/仅看未绑定/绑定整组保存与脏标记
- 值域单条/批量/部分失败/上限
- 关联路径校验、停用、最短路
- 层级编辑器、顺序调整、停用
- 版本摘要、最新标记、回滚
- 智能预填 dryRun 不写库、apply 幂等
- 全局开关写入与热更

### 8.6 回归时机（重要）

当前版本**没有 M3 软校验与漂移联动**：物理 Schema 改名/删列后，本体不会自动告警，绑定与关系会静默指向旧名字。因此：

| 触发事件 | 必做回归 |
|---|---|
| 数据源表/列重命名、删除 | 逐项核对绑定、值域、关系、层级列名 |
| 新增宽表/维表 | 评估是否新增实体与关联路径 |
| 指标口径变更 | 检查是否与本体值域冲突 |
| 升级版本 | 跑一遍《业务本体维护测试案例》核心用例 |
| 问数质量下降 | 先查 trace 注入是否正常，再查 Schema 漂移 |

## 9. 排障与常见问题

### Q1：问了含实体名的问题，但 trace 显示实体命中 0

**原因**：名称/别名不含问题中的词；别名被截断（>50 字）；问题用了简称。
**处理**：把用户实际说法加为别名；用面板搜索确认别名已保存；换一个含完整实体名的问题验证。

### Q2：实体命中了，但加权表数为 0

**原因**：实体没有绑定；绑定表名与 Schema 大小写/前缀不一致；绑定被整组替换清空。
**处理**：展开「维护绑定」核对；保存后看计数是否变化；用 Schema 联想选择表名，避免手输错。

### Q3：注入了，但 SQL 没用绑定表

**原因**：本体是软提示，模型可能因问题本身不需要该表、或该表不在白名单而放弃；也可能铁律/指标给出了更强约束。
**处理**：确认问题确实需要该表；检查表是否在白名单；查看 trace 上下文仲裁是否把本体裁掉；必要时在问题中明确提及实体。

### Q4：注入 token 为 0，但开关是开的

**原因**：没有任何实体命中（不会构造本体段）；或读了空快照（DB 异常降级）；或数据源选错。
**处理**：先确认问题含实体词；查后端日志是否有本体加载失败；确认提问的数据源与面板选的数据源一致。

### Q5：提示词被截断，重要资产没进去

**原因**：资产数量超过注入上限（实体 8/值域 40/关系 12/层级 5），或本体段 1500 token 预算用尽。
**处理**：停用低价值资产；精简说明与用途；必要时调大 `ONTOLOGY_TOKEN_BUDGET`（注意总预算 6000 的挤压效应）。

### Q6：智能预填生成 0 项或很少

**原因**：Schema 没有中文描述；表名/列名不符合规则（无编号-名称列对、无分级列族）；数据源 Schema 未提取。
**处理**：先在「数据源与 Schema」补中文描述并保存；确认接口不是返回 400；预填只是起点，剩余项手工补。

### Q7：智能预填报 400 / 404

**原因**：400 = Schema 未提取或为空；404 = 数据源不存在。
**处理**：重新提取 Schema；确认 `dataSourceId` 正确；刷新页面后重试。

### Q8：点开关没反应 / 提示读取失败

**原因**：`GET /api/ontology/settings` 失败（网络、权限、后端异常），开关被置为不可操作。
**处理**：确认是 ADMIN；刷新页面；检查后端日志；资产维护不受影响，可先继续配置。

### Q9：回滚了，但页面没变化

**原因**：回滚生成新版本，子面板需要刷新；或回滚的是实体定义，绑定不在版本内。
**处理**：回滚成功后子面板会自动重挂载；若只改了绑定，版本回滚不会恢复绑定，需要手动改回。

### Q10：路径预览查不到刚登记的路径

**原因**：起点/终点表名与登记不一致（大小写、前缀）；路径超过 3 跳；关系被停用。
**处理**：核对表名；拆成多跳或补登记直达路径；确认状态为 ACTIVE。

### Q11：停用后概览计数没变

**原因**：计数只统计 ACTIVE，停用后应该减少；若没变，可能是缓存未刷新或停用的是另一数据源。
**处理**：点「刷新概览」；确认数据源；确认操作的是该行资产。

### Q12：多人同时维护，绑定被覆盖

**原因**：绑定整组替换，后保存者覆盖先保存者。
**处理**：约定维护窗口与责任人；保存前点「刷新」拉取最新；重要变更前记录当前绑定（截图或接口导出）。

### Q13：本体会影响问数性能吗

**原因**：本体加载与匹配是轻量查询 + 内存计算；embedding 精排会额外调用 embedding（问题向量 + 候选文档批量），可关闭。
**处理**：本地无 embedding 模型时设 `ONTOLOGY_EMBEDDING_ENABLED=0`；本体读取失败会降级，不拖垮问数。

### Q14：非管理员能做什么

**原因**：读接口登录可读，写接口一律 ADMIN。
**处理**：分析师只读浏览；需要修改请联系管理员。A/B 的 `disableOntology` 也仅 ADMIN 生效，非管理员传了会被忽略。

## 10. 权限、安全与审计

### 10.1 权限矩阵

| 操作 | ADMIN | ANALYST | VIEWER/未登录 |
|---|---|---|---|
| 查看概览/实体/值域/关系/层级 | 是 | 是 | 否（未登录 401） |
| 新建/编辑/删除/停用 | 是 | 否（403） | 否 |
| 绑定整组替换 | 是 | 否 | 否 |
| 版本查看/回滚 | 是 | 否 | 否 |
| 开关读取/写入 | 是 | 否 | 否 |
| 智能预填 dryRun/apply | 是 | 否 | 否 |
| A/B `disableOntology` | 是 | 静默忽略 | 否 |

### 10.2 安全边界

- 本体不参与鉴权、不改变数据范围、不放开白名单；
- 注入内容是「说明性文本」，最终 SQL 仍过安全执行层（只读、表白名单、行数上限、超时）；
- 路径只是推荐，未登记时提示词明确要求「不得臆造 JOIN」；
- 本体读取失败按空处理，不会把异常信息拼进提示词；
- 前端所有写操作按钮仅 ADMIN 可见，但后端仍独立校验（前端隐藏不等于授权）。

### 10.3 审计与留痕

- 实体/关系/层级的创建、更新、删除、回滚都会写入 `ontology_versions`，含版本号、动作、操作者、时间、快照；
- 值域没有版本表，只有 `created_by` 与行的增删改；重要变更需自行留痕；
- 接口层写操作进入统一请求日志；需要更细审计时以日志中的用户与请求为准。

### 10.4 内容安全

不要在实体说明、别名、关系用途中写入：

- 数据库连接串、账号密码、Token；
- 个人敏感信息（身份证、手机号、住址）；
- 未脱敏的业务机密。

这些内容会进入提示词并可能被模型复述到回答中。说明文字应只描述业务含义与粒度。

## 11. 能力边界与后续演进

### 11.1 当前已上线（M1 + M2 + 配套）

- 实体/别名/类型/说明 + 表列绑定（角色、表级/列级、整组替换）
- 值域释义（单条、批量、停用、按命中表注入）
- 关联路径（方向、JOIN、基数、用途、BFS 最短路、血缘声明边）
- 业务层级（逐级编辑、顺序调整、按上限注入）
- 版本快照与回滚（实体/关系/层级）
- 智能预填（dryRun + 幂等写入）
- 全局开关（`ONTOLOGY_ENABLED`，热更）
- 圈表加权 + 四段提示词 + 上下文仲裁
- A/B（`disableOntology`、评测 `--ontology on/off`）

### 11.2 尚未上线（M3 规划，不要按已上线使用）

依据《业务本体M3软校验与演化闭环设计》（规划稿）：

| 规划能力 | 当前状态 | 影响 |
|---|---|---|
| 软校验（表/列缺失检测） | 未上线 | Schema 变更后绑定/关系可能静默失效，需人工回归 |
| 漂移联动（结构变更关联本体资产） | 未上线 | 漂移事件不会自动标记本体失效 |
| 审批流（PENDING/REJECTED） | 未上线 | 管理端只能 ACTIVE/DISABLED；状态字段为预留 |
| 影响面分析 | 未上线 | 改一个实体前无法自动评估影响多少问题/SQL |
| 失败样本回流 | 未上线 | 问数失败不会自动建议补本体 |

### 11.3 图库接入结论

截至 2026-10-22 的评估：8 个数据源单源最大 7 表、本体 12 实体/31 绑定/5 关系、近 30 天问数 SQL 含 JOIN 7.3%、无跨源联邦需求——**五项触发条件均未触发，结论为暂不接入图库**。当前 BFS 在 MySQL/内存中完成，满足规模需求；后续按「MySQL 递归 CTE → `ontologyGraph` 抽象层 → 图库」分级演进，并以资产规模、JOIN 占比、路径延迟作为量化门槛。

### 11.4 升级注意

- M3 上线后，`PENDING/REJECTED` 才会真实出现，届时写操作可能多一步审批；
- 图库接入不会改变管理端操作，但路径检索的延迟与跳数上限可能调整；
- 任何版本升级后，先跑《业务本体维护测试案例》核心用例，再检查 trace 注入是否正常。

## 附录 A：术语表

| 术语 | 含义 |
|---|---|
| 业务本体 | 本项目中指「业务实体 + 绑定 + 值域 + 关联路径 + 层级」的登记式治理资产，不是 OWL/RDF 形式化本体 |
| 实体 | 业务概念（机构、客户、项目），带名称、类型、别名、说明 |

| 关联路径 | 两表之间的 JOIN 声明（列、类型、基数、用途） |
| 业务层级 | 由粗到细的分组列序（集团 > 分公司 > 项目） |
| 软注入 | 只作为提示词建议，不强制、不拼 SQL、不改变权限 |
| 圈表加权 | 命中实体的绑定表在 Schema 表选择中获得加分 |
| 上下文仲裁 | 按优先级与预算对各上下文块排序、去重、裁剪 |
| declared 边 | 由治理声明（而非血缘解析）产生的血缘边，如 joins |
