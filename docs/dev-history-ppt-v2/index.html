一、项目是什么

一句话查数：不良资产经营分析的 NL2SQL 助手

定位与场景

  • 定位：业务人员用一句自然语言直接查数、出图、得结论
  • 场景：不良资产经营分析——「各机构本年投放金额排名」「长龄业务 TOP8」「同比增减变化」
  • 数据：业务宽表 127 万行 + 财务宽表 1139 万行，20 个月末快照报告期

三种角色

角色权限
ADMIN全权：数据源、知识库、系统管理
ANALYST问数 + 知识沉淀（个人 few-shot）
VIEWER只读查看报表与看板

行级权限 AST 强制注入，问数直达生产库也放心

这一页回答「项目是什么」。

一句话：让业务人员用自然语言直接查数。用户输入「各机构本年投放金额排名」，系统自动生成 SQL、在真实数据库执行、出图表、给 AI 解读和建议追问。

场景聚焦不良资产经营分析：底层是 127 万行业务宽表加 1139 万行财务宽表，覆盖 20 个月末快照。

权限分三角色：管理员全权、分析师可问数可沉淀、查看者只读。行级权限通过 AST 强制注入 SQL，不是前端过滤，是数据库层面的硬约束。
一、项目是什么

技术底座：本地优先、双模型、轻量可控

层选型为什么
前端React + Vite + Tailwind v4 + Recharts主流轻量，模板起步即具备
后端Node.js + Express（Vite 一体化）单进程启动，部署简单
AI 引擎本地 Ollama 双模型分工
qwen3.8:27b 生成 SQL · deepseek-r1:8b 解读		数据不出内网；可选百炼云端引擎
数据库MySQL（元数据库 + 业务库）兼容 PostgreSQL / Greenplum 三源矩阵
向量检索nomic-embed-text · JSON 落 MySQL · 应用层余弦轻量方案，无独立向量库依赖
关键取舍：数据不出内网——主引擎本地 Ollama，金融数据场景下的安全底线；向量检索不引入独立向量库，百级千级规模下 JSON + 余弦足够。
技术底座讲三个关键取舍。

第一，AI 引擎本地优先：主引擎是本地 Ollama，金融数据不出内网；同时保留百炼云端引擎可切换。

第二，双模型分工：27B 大模型负责生成 SQL，8B 小模型负责数据解读，各司其职，生成环节提速一倍。

第三，轻量可控：向量检索没有引入 Milvus 这类独立向量库，embedding 以 JSON 存 MySQL、应用层算余弦——知识库就几百条，够用且省运维。数据库层 MySQL 起步，已兼容 PostgreSQL 和 Greenplum。

开发历程分五个阶段，我先把地图展开。

阶段零是数据地基，这个阶段最重要的决定是：真数据先行；阶段一完成系统正名和 AI 引擎接入；阶段二是最密集的框架建设期，两天落地六大能力；阶段三做体验和生态，对话历史、自主学习、外部知识库；阶段四进入口径治理深水区，六个版本每个都在修真实业务暴露的问题。

接下来逐个展开，重点讲阶段四的几个事故。
阶段 0 → 1

起步：真库真数先行，引擎奠基

阶段 0 · 数据地基

  • 从 AI Studio 本地模板起步（Vite + Express 骨架）
  • Greenplum 宽表 DDL 转译 MySQL：94 列业务宽表 + 204 列财务宽表
  • LOAD DATA 灌入 127 万 + 1139 万行真实口径数据
确立验证基准：任何改动都能用真实业务问题回归

阶段 1 · v0.1 正名与引擎

  • 系统正名「智能问数分析系统」，版本归零 v0.1
  • 引擎三连：百炼接入 → 用户自选模型 → 主引擎切换
  • 踩坑：Coding Plan Key 禁用于自建后端 → API Key 与端点严格配套成为规范
起步阶段最重要的决定是真库真数先行。

我们没有用演示数据开发，而是第一周就把 Greenplum 的两张宽表转译成 MySQL，灌入 1266 万行真实口径数据。这个决定后来被反复证明值得：所有「看似正确」的口径错误，都会在真实数据上现形。

阶段一完成系统正名和 AI 引擎三连——接入百炼、上线用户自选模型、完成主引擎切换。这里踩了一个坑：百炼 Coding Plan 的 Key 禁止用于自建后端，由此确立「API Key 与端点严格配套」的团队规范。
阶段 2 · v0.2 ~ v0.3

框架成型：两天落地六大核心能力

① 推导留痕

query_trace 全链路记录 + 时间线回放，每个结论可追溯

② 知识库 RAG

宽表元数据 8 sheet 670 行 → 326 知识块，向量/词法混合检索注入 prompt

③ SQL 自纠错

多候选生成 + 择优投票，执行失败自动重试

④ 语义指标层

权威口径固化：8 个语义指标 + 16 条 SQL 样例，防模型幻觉

⑤ 评测与权限

NL2SQL 评测集 16 用例基准；行级权限 AST 强制注入

⑥ 技能库与图表

不良资产 8 大专业场景技能；图表扩至 9 种

同期打磨：全界面中文化 · 索引优化（长龄查询 4×、快照聚合 20×+ 提速）· 标杆问题 105s → 68s
阶段二是框架建设最密集的两天，借鉴 DB-GPT 的工程化思路落地六大能力。

挑三个重点讲：推导留痕——SQL 怎么来的、模型想了什么，全程记录可回放，这是「可信问数」的基础；知识库 RAG——把 670 行宽表元数据切成 326 个知识块，让模型真正「懂」宽表口径；语义指标层——把「本年投放」「长龄业务」这些权威口径固化成配置，防止模型自由发挥。

同期还做了性能优化：标杆问题从 105 秒降到 68 秒，靠的是复杂度预门控、上下文并行化和结果缓存。
阶段 3 · v0.4.0 ~ v0.4.1

体验与生态：从能用走向好用、可接入

v0.4.0 · 对话历史与自主学习

  • 对话服务端落库：跨设备共享、搜索/重问/删除、Markdown 导出
  • 自主学习双通道：成功问答自动沉淀个人 few-shot；点踩进反面教材库
  • 对话按数据源隔离，盖源戳防跨源串味

v0.4.1 · 外部知识库接入

  • POST 检索协议 + Bearer 认证，四容器响应容错解析
  • API Key AES-256-GCM 加密落库
  • 知识库从「内置」走向「可接入企业既有知识平台」
同期：Greenplum 全链路打通（pg 协议双引擎连接池 + 方言感知 SQL 校验），数据源矩阵扩展为 MySQL / PostgreSQL / Greenplum
阶段三的主题是从「能用」走向「好用、可接入」。

v0.4.0 做了对话历史落库和自主学习双通道：用户的成功问答会自动沉淀为个人 few-shot 样例，下次类似问题优先参考；点踩的案例进反面教材库，告诉模型「别这么答」。系统越用越懂用户。

v0.4.1 把知识库从内置扩展为可接入企业既有知识平台：标准检索协议、Key 加密落库、响应容错解析。同期打通 Greenplum 全链路，数据源矩阵扩到三种数据库。
阶段 4 · 口径治理深水区

标志性事故：本年投放被虚增 17 倍

事故现象（v0.4.3）

「本年投放 2318 亿」被算成 39204 亿，虚大 17 倍。根因：财务宽表是月末快照表，20 个报告期重复累计；语义指标 filters 缺报告期锁定，且「权威口径禁止变更」指令压制了知识库中的正确规则。

修复方式：配置层优先

修复 8 个语义指标 filters + 4 个知识块口径说明，不改一行代码。修复后 2318.28 亿与手工 SQL 精确一致，29 机构逐一核对。

同期 v0.4.2：同/环比维度错配修复——新增时间序列轴判定（格式解析 + 单调性校验），消灭「把前一机构当历史基线」的伪同环比。
阶段四进入口径治理深水区，先讲最典型的事故。

「本年投放金额」被算成 39204 亿——虚增 17 倍。根因在数据模型：财务宽表是月末快照，本年投放是年内累计列，20 个报告期直接 SUM 就重复累计了。

更值得说的是修复方式：一行代码没改，全部在语义指标配置和知识库口径层修复——报告期锁定写进指标 filters。这确立了我们一条重要经验：配置层优先于代码层。修复后 2318.28 亿与手工 SQL 精确一致。

同版本还修了伪同环比：只有真时间轴才启用同环比计算，杜绝「把前一家机构当成历史基线」。
阶段 4 · v0.4.4 ~ v0.4.7

收尾打磨：每一版都修真问题

v0.4.4 · 白名单误拒修复 + 双模型分工

同比类子查询 SQL 被正则防线误判；修正后确立 27B 生成 + 8B 解读路由，生成提速一倍

v0.4.5 · 金额单位自选

亿元/百万元/万元/元随提问生效；单位进缓存键防口径互串；展示层千分位统一

v0.4.6 · 解读失败规则化降级

LLM 解读异常不再输出空壳文案，基于真实列统计生成有信息量的降级解读，trace 可追溯

v0.4.7 · 拒答契约 + 统一话术

无关问题不再用演示数据托底：「抱歉，我是数据分析助手，仅协助处理数据分析相关工作，无法处理XXXX」，REFUSED 审计留痕

最后四个版本，每个都在修真问题。

v0.4.4 修 SQL 白名单误拒——同比对比的子查询被安全防线误杀，修复同时确立双模型分工，SQL 生成提速一倍。

v0.4.5 金额单位自选，亿元万元随提问切换；v0.4.6 解读失败时不再给空壳文案，而是基于真实列统计做规则化降级解读。

最后 v0.4.7 是拒答契约：用户问天气、让写诗、让写代码，系统不再硬编演示数据糊弄，而是如实说「抱歉，我是数据分析助手，仅协助处理数据分析相关工作，无法处理天气查询」——并且拒答也会进审计日志留痕。这是「降级不撒谎」原则的终点。

四、经验沉淀

六条可复制的经验

① 真库真数是质量底线

17 倍虚增、维度错配同环比——所有「看似正确」的口径错误都逃不过与手工 SQL 的比对

② 配置层优先于代码层

报告期锁定、口径固化全部在语义指标与知识库修复，不动核心代码、零回归风险

③ 全链路留痕

推导回放、审计八态（含 CLARIFY/REFUSED）、对话落库——每个结论可追溯可复盘

④ 优雅降级是一等公民

LLM 失败→规则化解读；embedding 缺失→词法检索；无法回答→如实拒答——降级不撒谎

⑤ 文档即产品

《系统功能说明书》单一事实源，系统内帮助实时读取，功能变更必同步文档

⑥ 安全纵深防御

SELECT-only 白名单 + AST 双校验、行级权限注入、敏感列剔除、Key 加密落库

经验沉淀六条，都是可以复制到下一个项目的。

我认为最重要的三条：第一，真库真数是底线——演示数据会骗人，真实数据不会；第二，配置层优先——口径问题用配置修，不动代码就没有回归风险；第三，降级不撒谎——LLM 会失败，系统不能装没事：解读失败给规则化解读，无法回答就如实拒答，绝不编造数据。

另外两条工程习惯也值得带走：文档即产品、安全纵深防御。
