# 需求收集与反馈基线接口设计

> 日期：2026-10-08　状态：**已实施**　目标版本：v0.9.98
> 需求原文：增加一个需求收集及意见反馈功能，并且提供标准接口提供给智能运维平台进行主动进行需求分析。收集到需求或意见反馈时，经过管理员进行评估分析后纳入基线管理在提供给智能运维平台进行主动分析。
> 关联文档：《系统功能说明书》3.9（面板）/ 3.23（接口与数据模型）；《自动运维智能体接入手册》§10（面向智能体）；配套 AIOps 侧：《AIOps 被监控系统标准接口改造方案》（AIOps Agent 仓库，Manifest v1.0）

## 一、背景与设计目标

### 1.1 背景

系统已具备面向自动运维智能体的运维事件流（v0.9.93 `/api/ops/events`）与告警触达（v0.9.94）能力，但「用户侧的功能诉求与使用意见」仍靠口头 / 即时通讯传递，存在三个断点：

| # | 断点 | 后果 |
|---|------|------|
| 1 | 用户意见无沉淀渠道 | 提出后无记录、无跟踪、易遗失 |
| 2 | 管理员评估无台账 | 采纳 / 不采纳的决策与理由不可追溯 |
| 3 | AIOps 平台无法消费需求数据 | 「需求 → 主动分析 → 迭代验证」链路缺失 |

### 1.2 设计目标

1. **闭环化**：用户提交 → 管理员评估分析 → 纳入基线管理 → 标准接口供 AIOps 主动分析，四段全部落库、可追踪；
2. **标准化**：导出接口自带 `spec_version` 与 `/.well-known/requirements.json` 自描述，Manifest（`aiops.json`）新增 `requirements_path` 供自动发现——与《AIOps 被监控系统标准接口改造方案》口径一致；
3. **零新增依赖**：复用既有 `requireOpsAccess` 双通道鉴权（`OPS_API_TOKEN` 或 ADMIN JWT）、MySQL 元数据库、`writeAudit` 审计通道；
4. **向后兼容**：`app_manifest.py` 校验器对未知字段宽容，老客户端不受 Manifest 新字段影响；导出接口默认仅暴露「已纳入基线」条目（最小暴露面）。

### 1.3 范围边界

- **做**：提交（四类型）、我的反馈跟踪、管理端评估三动作（纳入基线 / 不予采纳 / 退回待评估）、统计摘要、删除、标准导出、能力自描述、前端两处入口；
- **不做**：通知推送（邮件 / IM）、附件上传、多轮评论、AIOps 侧自动排期决策（属平台侧职责，本系统只提供数据）。

## 二、总体设计

### 2.1 链路架构

```
┌──────────┐   提交/查看     ┌────────────────────────────┐
│  用户     │ ─────────────► │  POST /api/requirements     │
│(任意角色) │ ◄───────────── │  GET  /api/requirements/mine│
└──────────┘   进度+评估意见  └──────────────┬─────────────┘
                                            │ feedback_entries（MySQL）
┌──────────┐   列表/评估/删除 ┌──────────────▼─────────────┐
│  管理员   │ ─────────────► │  GET /api/requirements      │
│ (ADMIN)  │                │  GET /summary               │
└──────────┘                │  POST /:id/review           │
                            │  DELETE /:id                │
                            └──────────────┬─────────────┘
                             PENDING ──评估──► BASELINED / REJECTED
                                            │
┌─────────────────┐   标准导出   ┌──────────▼─────────────┐
│ AIOps 智能运维平台│ ◄────────── │ GET /api/requirements/  │
│ （主动需求分析） │  Bearer 令牌 │     export（默认基线）   │
└─────────────────┘             └────────────────────────┘
```

### 2.2 角色与权限矩阵

| 能力 | VIEWER | ANALYST | ADMIN | OPS_API_TOKEN |
|------|--------|---------|-------|---------------|
| 提交需求 / 意见 | ✅ | ✅ | ✅ | — |
| 查看「我的反馈」 | ✅（仅本人） | ✅（仅本人） | ✅（仅本人） | — |
| 管理列表 / 摘要 / 评估 / 删除 | — | — | ✅ | — |
| 导出基线条目 | — | — | ✅ | ✅ |

### 2.3 状态机

```
              ┌────────────┐   纳入基线（必填评估分析意见）  ┌─────────────┐
  提交 ────►  │  PENDING   │ ─────────────────────────────► │ BASELINED  │
              │  待评估     │ ────────── 不予采纳 ──────────► │ 已纳入基线   │
              └─────▲──────┘                                └──────┬──────┘
                    │           REJECTED（未采纳）                   │
                    │           ┌────────────┐                      │
                    └───────────┤ 退回待评估  │◄──── 退回待评估 ──────┘
                     保留评估笔记└────────────┘
```

- 退回 `PENDING` 时清空 `priority` / `baseline_version` / `reviewer` / `reviewed_at`，但**保留 `assessment`**（评估笔记不丢，便于再评估）；
- 导出接口默认只输出 `BASELINED`（管理员的「评估分析」是暴露给平台的必要前置）。

## 三、数据模型

`feedback_entries`（`server/infra/schema.ts`，随 `initSchema` 幂等建表）：

```sql
CREATE TABLE IF NOT EXISTS feedback_entries (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  kind VARCHAR(20) NOT NULL DEFAULT 'REQUIREMENT',   -- REQUIREMENT/SUGGESTION/BUG/OTHER
  title VARCHAR(200) NOT NULL,
  content TEXT NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'PENDING',     -- PENDING/BASELINED/REJECTED
  priority VARCHAR(10) NOT NULL DEFAULT '',          -- P0-P3（纳入基线时写入，默认 P2）
  baseline_version VARCHAR(50) NOT NULL DEFAULT '',  -- 基线版本标注（可选）
  assessment TEXT,                                   -- 评估分析意见（BASELINE 必填）
  user_id INT NOT NULL,                              -- 提交人快照
  username VARCHAR(50) NOT NULL,
  department VARCHAR(100) NOT NULL DEFAULT '',
  reviewer VARCHAR(50) NOT NULL DEFAULT '',          -- 评估人快照
  reviewed_at TIMESTAMP NULL DEFAULT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_feedback_status (status),
  INDEX idx_feedback_user (user_id),
  INDEX idx_feedback_updated (updated_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
```

设计要点：提交人 / 评估人采用**快照**字段（不随用户改名、删号漂移）；`idx_feedback_updated` 支撑导出接口的 `since` 增量。

## 四、接口规范

### 4.1 用户侧（`server/routes/requirements.ts`）

| 端点 | 鉴权 | 说明 |
|------|------|------|
| `POST /api/requirements` | 登录任意角色 + rateLimiter | 提交。body `{ kind?, title, content }`；kind 默认 REQUIREMENT（枚举校验）；title ≤200 / content ≤5000（超长截断）；成功 201 `{ success, id }` |
| `GET /api/requirements/mine` | 登录 | 本人最近 100 条，含评估状态与评估意见 |

### 4.2 管理员侧（仅 ADMIN）

| 端点 | 说明 |
|------|------|
| `GET /api/requirements?status=&kind=` | 全量列表（非法枚举值忽略），待评估优先 + id 降序，上限 500 |
| `GET /api/requirements/summary` | `{ byStatus, byKind, byPriority }` 三组计数（priority 仅统计 BASELINED） |
| `POST /api/requirements/:id/review` | body `{ action, priority?, baselineVersion?, assessment? }`；action ∈ BASELINE / REJECT / PENDING；**BASELINE 必填 assessment**、priority 默认 P2（枚举校验）；三类动作均 `writeAudit(endpoint=admin)`；返回 `{ success, id, status }` |
| `DELETE /api/requirements/:id` | 先查后删（404 兜底）+ 审计留痕 |

### 4.3 AIOps 标准导出接口

`GET /api/requirements/export`（`requireOpsAccess` 双通道，与 `/api/ops/*` 同款令牌）：

| 参数 | 取值 | 默认 | 校验 |
|------|------|------|------|
| `status` | BASELINED / PENDING / REJECTED / ALL | BASELINED | 非法 400（ALL 不带条件） |
| `kind` | REQUIREMENT / SUGGESTION / BUG / OTHER | 不限 | 非法 400 |
| `since` | `YYYY-MM-DD[ HH:MM[:SS]]`（按 `updated_at >=`） | 不限 | 格式白名单，非法 400 且**不触库** |
| `limit` | 1-500 | 200 | `clampInt` 越界钳制 |

响应（**无 `success` 字段**，以 HTTP 状态码为准）：

```json
{
  "spec_version": "1.0",
  "service": "nl2sql",
  "system": "智能问数据分析系统",
  "exportedAt": "2026-10-08T12:00:00.000Z",
  "filter": { "status": "BASELINED", "kind": null, "since": null },
  "returned": 2,
  "entries": [
    {
      "id": 12, "kind": "REQUIREMENT", "title": "…", "content": "…",
      "status": "BASELINED", "priority": "P2", "baselineVersion": "v0.9.99",
      "assessment": "…", "submitter": "analyst01", "department": "运营部",
      "reviewer": "admin", "reviewedAt": "…", "createdAt": "…", "updatedAt": "…"
    }
  ]
}
```

- 错误码：401（无凭据 / 令牌错误或未配 `OPS_API_TOKEN` 时的非 ADMIN）、400（`{ error: 中文说明 }`）、500；
- 字段映射统一走 `rowToEntry`（与前端列表同构，时间为 ISO 8601）；
- 排序 `updated_at DESC, id DESC`——增量轮询取「上次 `exportedAt` / 已消费最大 `updatedAt`」作为下次 `since`。

### 4.4 自描述与 Manifest

- `GET /.well-known/requirements.json`（匿名只读，`server.ts` 常量 `REQUIREMENTS_CAPABILITY`）：`spec_version` / `export_path` / `auth`（令牌环境变量与回退规则）/ `query`（参数与默认值）/ `status_flow` / `entry_fields`；
- `GET /.well-known/aiops.json` 的 Manifest 新增 `requirements_path: '/api/requirements/export'`（`app_manifest.py` 的 `_STR_FIELDS` 白名单同步收录该字段，未知字段宽容保证向后兼容）。

## 六、安全与审计

- 用户提交走 `authMiddleware + rateLimiter`（全局限流桶）；标题 / 正文按上限截断；
- 导出接口默认最小暴露（仅 BASELINED），`since` / `status` / `kind` 全部白名单校验，非法输入不触库；
- 令牌比对复用 `requireOpsAccess`：SHA256 摘要 + `timingSafeEqual` 恒时比较，不触碰 users 表；
- 评估与删除全部 `writeAudit`（endpoint=`admin`），机器导出为只读不加审计。

## 八、AIOps 侧配套（同批交付）

AIOps Agent 仓库（`aiops-agent/`）：

- `aiops_agent/requirements_client.py`：标准库零依赖客户端（`fetch_requirements()` 永不抛异常，返回含 `ok` / `error` / `entries`（及 `exported_at` / `returned` 等元信息）的结果字典；支持 status / kind / since / limit / token 注入）；
- `analyze_requirements.py`（CLI，仿 `check_aiops_interface.py` 风格）：拉取基线条目 → 本地分析汇总（类型 / 优先级 / 版本分布、P0/P1 高优提示）→ Markdown 报告与 `--json` 输出；`--url`（默认 `http://localhost:3000`）/ `--token` 或环境变量 `NL2SQL_OPS_TOKEN` / `--status` / `--kind` / `--since` / `--limit` / `--out`；
- `tests/test_requirements.py`：客户端契约与模型单测；
- `app_manifest.py`：`_STR_FIELDS` 收录 `requirements_path`。
