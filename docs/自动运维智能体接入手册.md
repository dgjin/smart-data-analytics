# 智能问数分析系统 · 自动运维智能体接入手册

> 版本：v0.9.98 ｜ 面向：自动运维智能体 / 运维工具开发方 ｜ 配套：《系统功能说明书》3.21 / 3.22 / 3.23 节
>
> 本手册所述能力由 v0.9.93（结构化日志 + 运维事件流 + 运维 API）与 v0.9.94（告警旁路 / 前端错误回流 / 可选 Loki 采集栈 / 日志对账）交付；v0.9.98 追加需求基线条目接口（§10，供智能体做主动需求分析）。

## 1. 接入全景

智能体与系统的四条接触面（推拉互备、观测增强 + 需求基线分析）：

| 通道 | 方向 | 载体 | 用途 |
|------|------|------|------|
| **拉（主动查询）** | 智能体 → 系统 | REST `/api/ops/*`（本手册 §3、§4） | 事件流拉取 / 态势摘要 / 日志尾读 |
| **推（告警触达）** | 系统 → 智能体 | Alertmanager webhook 旁路（§5） | critical / warning 告警即时触达 |
| **观测（可选）** | 系统 → Loki | promtail 采集（§6） | 全量日志集中查询（Grafana LogQL） |
| **需求分析（拉，v0.9.98）** | 智能体 → 系统 | REST `/api/requirements/export`（§10） | 需求 / 意见基线条目增量拉取（管理员评估纳入基线后） |

**推荐闭环**：告警触达（§5）或摘要轮询发现 NEW → 拉取事件明细（§3.1）→ 受理 ack（§3.3）→ 执行处置（期间用 §3.5 关联字段 + §4 / §6 定位根因）→ 关闭 resolve 并写处置摘要（§3.4）。全部动作自动留痕审计，机器通道归属 `ops_agent`、人工管理面板归属 `admin`，可区分检索——这是「发现 → 决策 → 执行 → 验证」证据链的落账点。

## 2. 认证

- 在 `.env.local` 配置 `OPS_API_TOKEN=<随机长令牌>`（建议 ≥32 位）并重启应用；**未配置时智能体通道关闭**（请求回退 JWT 校验，无登录态将 401）。
- 请求头：`Authorization: Bearer <OPS_API_TOKEN>`。
- 令牌匹配采用 SHA256 摘要 + `timingSafeEqual` 恒时比较；匹配成功注入 `ops-agent` 身份（id=0，ADMIN 角色，**不触碰 users 表**）。
- `/api/ops/*` 全部端点（事件流 / 摘要 / ack / resolve / 日志）均受该双通道鉴权保护；前端错误上报端点除外（匿名可报，见 §7.4）。

## 3. 事件流 API

### 3.1 事件列表 `GET /api/ops/events`

| 参数 | 说明 |
|------|------|
| `status` | `NEW` / `ACK` / `RESOLVED` |
| `severity` | `CRITICAL` / `ERROR` / `WARN` / `INFO` |
| `source` | `audit` / `task` / `patrol` / `drift` / `fatal` / `client` |
| `category` | 分类精确匹配（见 §3.5，最长 24 字符） |
| `since` / `until` | 时间过滤（`YYYY-MM-DD` 或 `YYYY-MM-DD HH:mm[:ss]`） |
| `cursor` | 游标：上一页响应中的 `nextCursor`（取 `id < cursor`） |
| `limit` | 每页条数 1–200，默认 50 |

响应：`{ "success": true, "events": [...], "nextCursor": <number|null> }`——按 `id` 倒序；`nextCursor` 为 `null` 表示已到底。

```bash
curl -H "Authorization: Bearer $OPS_API_TOKEN" \
  "http://127.0.0.1:3000/api/ops/events?status=NEW&severity=ERROR&limit=50"
```

事件行字段：`id` / `severity` / `source` / `category` / `entity_type` / `entity_id` / `message` / `detail`(JSON) / `trace_id` / `status` / `dedup_count` / `handled_by` / `handled_at` / `created_at` / `last_seen_at`。

### 3.2 态势摘要 `GET /api/ops/events/summary`

响应：`{ "success": true, "byStatus": [{status, cnt}], "last24h": [{category, severity, cnt}] }`——适合智能体高频轻量轮询（每秒几次也无负担，均为单表聚合）。

### 3.3 受理 `POST /api/ops/events/{id}/ack`

- 状态流转 `NEW → ACK`；body 可选 `{ "note": "…" }`（≤200 字，记入审计留痕）。
- 幂等：已处于 ACK/RESOLVED 时返回 `{ success: true, status, already: true }`，不重复变更、不重复留痕。
- 不存在 404、非法 id 400。

### 3.4 关闭 `POST /api/ops/events/{id}/resolve`

- 状态流转 `NEW|ACK → RESOLVED`；body 同上（**建议将处置摘要写入 note**，形成完整证据链）。
- 幂等语义同 3.3。

### 3.5 事件语义

| source | category | 默认严重级 | 触发场景 |
|--------|----------|-----------|---------|
| `audit` | `NL2SQL` | ERROR | 问数接口失败（审计落账 ERROR） |
| `task` | `TASK` | ERROR | 异步后台任务失败 |
| `patrol` | `PATROL` | ERROR | 数据源巡检执行失败 |
| `drift` | `DRIFT` | WARN | 知识库漂移提醒 |
| `fatal` | `PROCESS` | CRITICAL | 进程级未捕获异常（进程刻意不自杀，重启决策交智能体） |
| `client` | `FRONTEND` | ERROR | 前端全局错误上报（window.onerror / unhandledrejection） |

- **去重合并**：`event_key = source:category:entityType:entityId`（不含消息文本），15 分钟窗口内同键事件仅 `dedup_count+1` 并刷新 `last_seen_at`，不重复插行——智能体按 `dedup_count > 1` 识别高频复发。
- **链路串线**：`trace_id` 与日志行的 `requestId`（HTTP 请求）/ `taskId`（后台任务）可直接用于 `GET /api/ops/logs` 过滤（§4），亦可作为审计检索键。
- 事件写入全程 fail-open，绝不影响业务链路；`query_audit_log` 的 DENIED/FALLBACK 终态刻意不进事件流（防噪声）。

## 4. 日志查询 `GET /api/ops/logs`

按 `LOG_FILE` 环境变量指向的 JSONL 日志文件**尾读**（默认窗口尾部 2MB，可调），返回窗口内尾部 N 行、按时间正序（tail 语义：最新在底部）。

| 参数 | 说明 |
|------|------|
| `level` | `debug` / `info` / `warn` / `error` |
| `q` | 行内关键字（子串匹配；非 JSON 历史行同样参与） |
| `requestId` / `taskId` | 按链路字段精确过滤 |
| `limit` | 1–1000，默认 200 |
| `maxBytes` | 尾读窗口 64KB–16MB，默认 2MB |

- 响应：`{ success, file, windowTruncated, returned, lines }`；`windowTruncated=true` 表示窗口外还有更早内容。
- 非 JSON 行以 `{ "raw": "…" }` 原样返回（兼容历史日志与第三方输出）。
- 未配置 `LOG_FILE` 返回 501；文件不存在/不可读返回 404。**文件路径仅取服务端环境变量，不接受请求参数**（从机制上杜绝任意文件读取）。

## 5. 告警 webhook 旁路（推通道）

让 Prometheus/Alertmanager 告警**即时触达**智能体，同时保持原有人工 webhook 主通道不变：

1. 配置环境变量 `OPS_AGENT_WEBHOOK_URL`（如 `http://host.docker.internal:8090/agent-alerts`）后重建 Alertmanager：
   ```bash
   OPS_AGENT_WEBHOOK_URL=... docker-compose -f docker-compose.monitoring.yml up -d --force-recreate alertmanager
   ```
2. 路由语义（`deploy/alertmanager.yml` 中【BEGIN-OPS-AGENT】标记段，由 `deploy/alertmanager-entrypoint.sh` 渲染/裁剪）：
   - `severity =~ "critical|warning"` 且 `aiops_demo != "true"` 的告警旁路推送至 `ops-agent` receiver（`continue: true`——**不影响**后续路由匹配）；
   - 显式兜底路由保证所有告警继续投递原 webhook 主通道（旁路绝不吸走主通道，已用 `amtool config routes test` 实测验证）；
   - `aiops_demo = "true"` 的演示告警仍走既有 `aiops-agent` 通道，不进 ops-agent。
3. **未配置 `OPS_AGENT_WEBHOOK_URL` 时**：两段标记被自动裁剪，行为与旧版完全一致（零影响）。
4. 载荷为 Alertmanager v4 webhook JSON（`version` / `groupKey` / `status` / `alerts[].labels|annotations|startsAt` …）；`send_resolved: false`——仅激活告警触达，恢复通知不推送（可按需改为 true）。

## 6. 日志集中查询（可选，Loki profile）

默认不启动（默认仅本地文件兜底 + `/api/ops/logs` 尾读）；需要全量日志集中查询时：

```bash
docker-compose -f docker-compose.monitoring.yml --profile loki up -d
```

- 组件：`loki`（宿主 **:3200** → 容器 3100；3100 已被 Grafana 占用）+ `promtail`（采集宿主 `LOG_DIR`（默认项目 `logs/`）下 `app_server*.log` → 推送 `loki:3100`）。
- Grafana 已预置数据源「**Loki**」（uid=`Loki`，`http://loki:3100`）——直接在 Explore 查询，或按 uid 在仪表盘中引用。
- LogQL 示例：
  ```logql
  {job="nl2sql-app"} | json | level="error"
  {job="nl2sql-app"} | json | requestId="<trace 串线用>"
  {job="nl2sql-app"} | json | module="Patrol"
  ```
  （采集端纯收集不做 pipeline；字段解析交给查询端 `| json`，规避采集管线出错丢行。）
- 保留 168h（`deploy/loki-config.yml` 的 `retention_period`，compactor 清理）；数据存 `loki-data` 卷。
- 已知取舍：`mv` 式归档轮转的文件首次被发现时会从头部补采（与已采内容重复），查询端可用时间序去重；`promtail-positions` 卷持久化避免容器重启重采。
- 注意：`LOG_DIR` 必须位于 Docker VM 共享范围内（compose 默认 `./logs` 满足；macOS + colima 仅共享 `$HOME`，**勿指向 macOS `/tmp`**）。

## 7. 日志保留、降噪与对账

### 7.1 保留策略
`start.sh` 每次启动归档旧日志为 `app_server-<时间戳>.log`（追加写防历史丢失）并按双条件清理：`LOG_KEEP_MIN`（默认 5）份最近归档**保底永不作年龄清理**；其余超 `LOG_KEEP_DAYS`（默认 14）天删除。两者均可在 `.env.local` 调整。

### 7.2 降噪
`LOG_QUIET_PATHS`（默认 `/api/health,/api/system/models`）指定的高频轮询端点前缀，其访问日志降为 `debug` 不落盘（置空 = 关闭降噪）；`LOG_LEVEL=debug` 可临时全量诊断。

### 7.3 日志域对账（一致性巡检）
```bash
npm run logs:reconcile                 # 默认窗口 120 分钟
npm run logs:reconcile -- --window=60  # 自定义窗口（分钟）
```
对账「Prometheus 计数器 `ops_events_recorded_total` 增量」与 `ops_events` 表行变化：以严格下界 `L = 窗口内新增行 SUM(dedup_count) + 窗口前旧行窗口内被合并次数`，判定 `P ≥ L − max(2, L×5%)` 为一致。退出码：`0` 一致 / `1` 背离（有行写入漏计数）/ `2` 环境失败（Prometheus 或数据库不可达）。`PROMETHEUS_URL` 可覆盖默认 `http://localhost:9090`。

### 7.4 前端错误上报（来源说明）
前端经 `POST /api/ops/client-errors`（**匿名可报**，登录页错误也回流；IP 分钟窗口限流 20 条，字段全量截断）上报全局错误，自动归集为 `source=client` 事件并参与 §3 全流程。智能体无需调用该端点，但应在事件处理时识别该来源（同页面同键 15 分钟合并）。

## 9. 指标与告警参考

- Prometheus 指标：`ops_events_recorded_total{severity,category}`（每次事件记录/合并计数，含智能体自身的 ack/resolve 无关联——本指标只记事件入库）。
- 内置告警规则 `OpsEventHighSeverity`（`deploy/prometheus-alerts.yml`）：10 分钟窗口内出现 CRITICAL/ERROR 事件即告警——该告警同样会经 §5 旁路触达智能体，形成「事件入库 → 告警触达 → 智能体拉取处置」的完整自动化链路。

## 10. 需求基线条目接口（v0.9.98；v0.9.102 评估历史）

用户在系统内提交的需求 / 建议 / 缺陷经管理员评估分析、纳入「需求基线」后，经标准接口开放给智能体做主动需求分析（优先级研判 / 实现建议 / 排期参考）。**认证与 §2 完全一致**（`OPS_API_TOKEN` Bearer；未配置时该端点仅接受 ADMIN JWT）。被监控系统侧「继续评估」后的最新结论与完整评估历史（`revisions`）随导出实时更新。

### 10.1 拉取基线条目 `GET /api/requirements/export`

| 参数 | 说明 | 默认 |
|------|------|------|
| `status` | `BASELINED`（仅基线）/ `PENDING`（待评估）/ `REJECTED`（未采纳）/ `ALL`（全量；非法值 400） | `BASELINED` |
| `kind` | 类型过滤：`REQUIREMENT` / `SUGGESTION` / `BUG` / `OTHER`（非法 400） | 不限 |
| `since` | 增量起点（按 `updated_at >=` 过滤），格式 `YYYY-MM-DD` 或 `YYYY-MM-DD HH:MM[:SS]`（非法 400） | 不限 |
| `limit` | 返回条数上限 1-500（越界自动钳制） | 200 |

响应（200。**注意：本端点响应无 `success` 字段**，以 HTTP 状态码为准）：

```json
{
  "spec_version": "1.0",
  "service": "nl2sql",
  "system": "智能问数据分析系统",
  "exportedAt": "2026-10-08T12:00:00.000Z",
  "filter": { "status": "BASELINED", "kind": null, "since": null },
  "returned": 2,
  "entries": [
    {
      "id": 12, "kind": "REQUIREMENT", "title": "……", "content": "……",
      "status": "BASELINED", "priority": "P2", "baselineVersion": "v0.9.99",
      "assessment": "管理员评估分析意见", "submitter": "analyst01", "department": "运营部",
      "reviewer": "admin", "reviewedAt": "2026-10-08T11:00:00.000Z",
      "createdAt": "2026-10-08T09:00:00.000Z", "updatedAt": "2026-10-08T11:00:00.000Z",
      "revisions": [
        { "id": 1, "entryId": 12, "action": "BASELINE", "priority": "P2", "baselineVersion": "v0.9.99",
          "assessment": "管理员评估分析意见", "reviewer": "admin", "createdAt": "2026-10-08T11:00:00.000Z" },
        { "id": 2, "entryId": 12, "action": "BASELINE", "priority": "P1", "baselineVersion": "v0.9.102",
          "assessment": "继续评估：优先级上调", "reviewer": "admin", "createdAt": "2026-10-09T08:00:00.000Z" }
      ]
    }
  ]
}
```

### 10.2 增量轮询与边界

- 记录上次响应的 `exportedAt`（或已消费条目的最大 `updatedAt`）作为下次 `since`（`>=` 语义）；条目按 `updated_at` 降序返回，若 `returned == limit` 说明本次窗口内更新条目超过上限（需求条目量级低、正常运行不会触达，可缩短轮询间隔规避）。
- 状态流转（供分析时理解条目语义）：`PENDING`（待评估）→ 管理员动作 → `BASELINED`（已纳入基线，默认导出口径）/ `REJECTED`（未采纳）；支持退回 `PENDING`。优先级 `P0-P3`（纳入基线时默认 `P2`）。
- 能力清单（匿名只读）：`GET /.well-known/requirements.json`——`export_path` / `auth` / `query` / `status_flow` / `entry_fields`；服务清单 `GET /.well-known/aiops.json` 的 Manifest 含 `requirements_path` 字段。
- **评估历史（v0.9.102）**：条目附 `revisions`（时间升序、每条目至多 20 条，超限取最近）——每次评估（纳入基线 / 不予采纳 / 退回待评估）的完整留痕（`action` / `priority` / `baselineVersion` / `assessment` / `reviewer` / `createdAt`）；主表字段（`priority` / `baselineVersion` / `assessment` / `reviewer` / `reviewedAt` / `updatedAt`）为最新结论。「继续评估」使主表 `updatedAt` 刷新（`since` 增量可感知），新结论经 `revisions` 与主表变化一并到达——消费方可据此同步最新内容并按需重新分析（快照未变化时建议幂等处理，避免重复分析）。
- 无凭据 / 令牌错误返回 401；`status` / `kind` / `since` 非法值返回 400（错误体 `{ error: 中文说明 }`）。

### 10.3 参考实现

AIOps Agent 仓库内置参考消费端：`aiops_agent/requirements_client.py`（标准库零依赖客户端，永不抛异常）与 `analyze_requirements.py` CLI（拉取基线条目 → 本地分析汇总 → 报告 / JSON 输出；`--url` / `--token` 或环境变量 `NL2SQL_OPS_TOKEN`）。
