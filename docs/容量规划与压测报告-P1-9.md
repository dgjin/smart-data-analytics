# P1-9 连接池容量规划与压测报告

生成时间：2026-08-22｜版本：v0.6.x（P1 阶段）｜环境：MacBook Pro（Apple Silicon）、Node 22、MySQL 8 @ 127.0.0.1:3306

## 一、容量模型（公式化）

### 1.1 数据源连接池（`server/sqlExecutor.ts` → `dsPoolMax()`）

**容量模型**：每次问数仅在 SQL 执行阶段持有数据源连接（秒级，`QUERY_TIMEOUT_MS=10s` 兜底），端到端延迟由 LLM 生成主导（本地 27B 模型数十秒/问）。因此数据源连接并发 ≈ 并发用户数 / 4。

```
DS_POOL_MAX = DS_POOL_MAX 显式配置（1-100，优先）
            = clamp(ceil(EXPECTED_CONCURRENT_USERS / 4), 3, 20)   # 公式推导
```

| EXPECTED_CONCURRENT_USERS | 生效 DS_POOL_MAX |
|---|---|
| ≤12 | 3（下限保底，不逊于原硬编码水位） |
| 20（默认） | 5 |
| 40 | 10 |
| ≥80 | 20（上限，防打爆数据源端 max_connections） |

MySQL 数据源走 `connectionLimit`，PostgreSQL/Greenplum 走 `pg.Pool max`，同一公式。

### 1.2 应用元数据库连接池（`server/db.ts` → `appPoolMax()`）

**容量模型**：应用库承载鉴权 / 审计 / 缓存 / 知识库 / 指标等随请求发生的短查询（每问数次、毫秒级），容量 ≈ 并发用户数 / 2。

```
APP_POOL_MAX = APP_POOL_MAX 显式配置（1-200，优先）
             = clamp(ceil(EXPECTED_CONCURRENT_USERS / 2), 10, 50)  # 公式推导
```

| EXPECTED_CONCURRENT_USERS | 生效 APP_POOL_MAX |
|---|---|
| ≤20（默认） | 10（与原硬编码一致） |
| 60 | 30 |
| ≥100 | 50（上限） |

## 二、压测方法与工具

脚本：`server/eval/loadTest.ts`（`npm run loadtest -- --ds <id> --levels 20,50,100 --rounds 5`）

- 以 `executeSafeSql` 全链路施压：SELECT-only 白名单校验 → AST 复核 → 行级权限注入 → 数据源池执行
- 探针 SQL：`SELECT COUNT(*) AS cnt FROM ai_query_history`（轻量聚合，聚焦连接池排队而非查询本身）
- 每并发档 C：C 个 worker 各跑 5 轮，共 C×5 次执行，统计 P50/P95/P99/max 与错误率
- 预热：先按 poolMax 建满连接，消除建连开销干扰

## 四、结论与容量建议

1. **池配置生效且无连接耗尽**：两档水位下 850 次执行零错误，mysql2 池内排队正常（100 并发 / pool=5 时 P95 仅 18ms，排队等待可忽略）。
2. **轻量探测查询下池容量不是瓶颈**：本地 MySQL 对 COUNT(*) 级查询处理能力 ≫ 100 并发；pool=5 → pool=20 的 P95 差异（18ms → 16ms）在噪声范围内。
3. **真实瓶颈在 LLM 生成而非数据库**：问数端到端 73s（单候选）/113s（3 候选分档），其中 SQL 执行占比 <0.1%。连接池公式的意义在于**防雪崩兜底**（上限 clamp）与**合理预分配**（下限保底），而非提升吞吐。
4. **生产建议**：
   - 20 人以内团队：默认值即可（DS=5 / APP=10）。
   - 50-100 并发：设 `EXPECTED_CONCURRENT_USERS=100`（DS=20 / APP=50），同时确认数据源端 `max_connections` 余量（MySQL 默认 151，单实例 20 连接安全）。
   - 数据源端 `max_connections` 紧张时：显式 `DS_POOL_MAX` 压到公式值以下（显式配置优先）。
