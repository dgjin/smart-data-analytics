# 评测集标注规范（P0-1）

> 适用：`server/eval/evalCases.json` · 运行器 `server/eval/evalRunner.ts` · CLI `server/eval/runEval.ts` · 种子 `server/eval/seedEvalDatasource.ts`
> 目的：用规模化、分层的真实问题集量化 NL2SQL 执行准确率，替代"体感"，支撑 CI 门禁与准确率承诺。

## 一、评测指标定义

- **执行准确率（Execution Accuracy）** = 生成 SQL 与 golden SQL 执行结果集一致的用例占比。
- 结果集比较为「关系等价」：行内取值排序 + 行间排序（`ordered=true` 的 Top-N 用例按行序比较），对列别名/列序/等价写法（`COUNT(1)` vs `COUNT(*)`）天然宽容。
- 除总准确率外，按 **category 分类分层统计**，定位薄弱环节（`summary.byCategory`）。

## 二、分类分层（category）

| category | 含义 | 评测方式 |
|---|---|---|
| `single_agg` | 单表聚合（COUNT/SUM/AVG + GROUP BY/WHERE） | 结果集等价 |
| `join` | 多表 JOIN（`clientId`/`ownerId`/`departmentId`/`roleId` 关联） | 结果集等价 |
| `time` | 时间对比（按 `LEFT(date,7)` 年月分组/对比） | 结果集等价 |
| `subquery` | 嵌套子查询（IN/NOT IN/EXISTS/标量） | 结果集等价 |
| `clarify` | 需澄清（问题歧义，模型应返回澄清而非猜测） | 期望 `needClarification=true` |
| `refuse` | 应拒答（不存在表/敏感字段/写操作/超出数据源范围） | 期望 `refused=true` |
| `permission` | 行级权限（受限数据源，行过滤注入后结果与 golden 等价） | 结果集等价（golden 含同口径谓词） |

## 三、用例字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 语义化编号，按分类前缀：`sa`单表聚合 / `jn`多表 / `tm`时间 / `sq`子查询 / `cl`澄清 / `rf`拒答 / `pm`行级权限 |
| `category` | 是 | 七类之一（缺省按 `single_agg`，但应显式标注） |
| `expect` | 澄清/拒答必填 | `result`（默认）/ `clarify` / `refuse` |
| `question` | 是 | 自然语言问题，贴近真实用户提问 |
| `goldenSql` | 是 | 标准答案 SQL；`clarify`/`refuse` 类仅占位（`SELECT 1`），不执行 |
| `ordered` | 否 | Top-N（`ORDER BY ... LIMIT`）用例置 `true`，按行序比较 |
| `dataSourceId` | permission 类必填 | 覆盖评测集默认数据源，指向受限数据源（`ds_eval_crm_dept1`） |

**permission 类标注要点**：问题用普通问法（不透露过滤条件，过滤由数据源 `scope.rowFilters` 注入）；golden SQL 手写与该数据源行过滤谓词同口径的 WHERE（如业务一部源：`clients.ownerId IN (...)` / `visits.ownerName IN (...)`），验证生成 SQL 经 AST 谓词注入后与 golden 结果等价——专测行级权限链路的端到端正确性。

## 四、golden SQL 编写要求

1. **仅用基础表名**：与 Schema `name` 一致（`clients`/`visits`/`users`/`departments`/`roles`），不带 `tbl_` 前缀。
2. **JOIN 关联键**：`visits.clientId=clients.id`、`clients.ownerId=users.id`、`users.departmentId=departments.id`、`users.roleId=roles.id`。
3. **时间维度**：`visits.date` 为 ISO 字符串，取年月用 `LEFT(\`date\`,7)`（如 `'2026-07'`），取年用 `LEFT(\`date\`,4)`；`date` 为保留字需反引号。
4. **结果确定**：golden SQL 必须在真实数据源可执行且结果确定；新增后先经「执行验证」（见下）再入库。
5. **避免脏数据陷阱**：维度列含空值/组合值（如 `team` 的 `一部二团队/二部三团队`），取值以真实 `DISTINCT` 为准。
6. **Top-N 无并列**：涉及「最多/第 N 多」的用例，种子数据已保证关键维度计数唯一（种子脚本自检强制）；新增此类用例须确认无并列，否则判定歧义。

## 五、评测数据源（可复现）

评测集默认数据源 `ds_eval_crm` 与受限源 `ds_eval_crm_dept1`（业务一部行级过滤）由种子脚本一键重建：

```bash
npm run eval:seed   # 建库 smart_eval_crm + 5 表确定性数据 + 注册两个数据源 + 自检 + golden 全量执行验证
```

- 数据确定性：纯模运算分配（无随机数），任何环境重建结果完全一致。
- 唯一性自检：拜访人/行业/月度/客户拜访次数唯一最大（Top-N 用例无并列）、无拜访客户数、行级过滤域口径锚点，违反即报错。
- 脚本内置 golden SQL 执行验证：新增用例合并后跑 `npm run eval:seed` 即完成「执行验证」环节。

## 六、如何新增用例

1. **来源**：真实用户问题、`query_trace` 差评记录、历史审计里的高频/易错问题；点踩用例自动进入待标注队列。
2. **定类**：判断属于七类中的哪一类，赋予对应 `id` 前缀与 `category`。
3. **标注 golden SQL**：手写标准 SQL 并在真实数据源执行验证结果正确。
4. **澄清/拒答类**：只需给出能触发对应行为的问题，`goldenSql` 写 `SELECT 1` 占位，`expect` 置 `clarify`/`refuse`。
5. **权限类**：问题普通问法，`dataSourceId` 置 `ds_eval_crm_dept1`，golden 带同口径部门谓词。
6. **执行验证**：`npm run eval:seed` 批量验证 golden 可执行；`npm run eval -- --case <新用例id>` 单跑确认端到端。

## 七、运行评测

```bash
npm run eval:seed                     # 前置：重建评测数据源（幂等，含自检与 golden 验证）
npm run eval                          # 全量（耗时长，本地 LLM 单问 1-5 分钟，注意配额）
npm run eval -- --limit 20           # 仅前 20 条（分批跑）
npm run eval -- --case sa01,pm01     # 指定用例
npm run eval -- --min-accuracy 85    # 阈值门禁：总准确率 <85% 时退出码非零（CI 阻断）
```

输出：逐条状态 + 总准确率 + 分类分层准确率 + 报告文件 `eval-report-<时间戳>.json`。

## 八、阈值与 CI 门禁

- `runEval` 在「存在失败/错误用例」或「总准确率低于 `--min-accuracy`」时以非零码退出，供 CI 阻断合并。
- CI 结构门禁：主集 ≥100 条且 `single_agg/join/time/subquery/clarify/refuse/permission` 七类全覆盖（`checkEvalSet.ts --require ...`）。
- 阈值初期按基线设定（如 80%），随评测集扩充与模型优化逐步收紧至 85%+。
- Prompt 文件变更应强制触发全量评测（见 CI 配置）。
