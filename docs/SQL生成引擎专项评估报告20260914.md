## 二、引擎能力全景盘点

### 2.1 上下文层（9 类注入，全部有 token 预算控制）

| # | 注入源 | 机制 | 预算/上限 | 落点 |
|---|---|---|---|---|
| 1 | Schema 圈表 | 关键词粗排 + embedding 语义精排（权重 ×12），表多时先粗排 2×N 再精排 | ≤8 张表 | `schemaLinking.ts` |
| 2 | 宽表列裁剪 | >50 列宽表按相关性保留 top-30，主键与指标引用列强制保留 | 30 列 | `schemaLinking.ts` |
| 3 | 表级业务口径 | 管理员登记 businessNote，逐表注入 | 无硬限 | `liveQueryPrompts.ts` |
| 4 | 语义指标层 | 命中指标名/同义词才注入 expr + filters + dimensions（dbt 语义层思路） | 命中制 | `metrics.ts` |
| 5 | 铁律规则 | 数据源全部 ACTIVE 规则**全量恒注入**，优先级最高 | ≤100 条/源 | `ironRules.ts` |
| 6 | 业务知识库 RAG | embedding 检索 topK=6 块 | 2700 tokens | `knowledgeBase.ts` |
| 7 | Few-shot 样例 | sql_examples 表（MANUAL/FEEDBACK_UP/IMPORT 三来源）bigram+embedding 召回 | 3600 tokens | `queryFeedback.ts` |
| 8 | 反面教材 | 用户点踩 → 只注入"错误问题 + 错误涉及表"，不提供错误 SQL | — | `queryFeedback.ts` |
| 9 | 多轮历史 | 从新到旧贪心截断 | 1500 tokens | `promptBudget.ts` |

**评价**：注入面覆盖了学术界总结的全部主流增强手段（schema linking、value grounding 除外、few-shot、知识 RAG、负例、指标语义层），且全部做了预算控制，工程规范度高。**风险点见 §5.5：9 类注入之间无冲突仲裁机制。**

### 2.2 生成层（5 项机制）

1. **模板匹配前置（v0.4.15 C2）**：LLM 做"模板选择 + 参数填充"，命中则确定性拼装 SQL（零偏差兜底），失败自动回退自由生成。
2. **多候选 Self-Consistency（P1-7）**：复杂问题并行生成最多 3 个候选（复杂度分档 1/2/3），候选间差异化引导（换聚合思路/简化 JOIN/最直接表）。
3. **阶段级模型路由（P1-2）**：简单单表问题走快速模型（`LLM_SQL_ROUTE_MAX_TABLES` 阈值控制），复杂/多表强制主模型。
4. **数据自省（Vanna intermediate_sql）**：过滤条件取值不确定时先执行 `SELECT DISTINCT ... LIMIT 30`，真实取值回喂后再生成最终 SQL；每问仅一次、防递归。
5. **计划模式（M2）**：LLM 先生成分析计划，用户批准后按计划生成 SQL（approvedPlan 注入 prompt）。

### 2.3 校验层（4 道）

- **JSON 契约校验**（parseStage1）：非契约输出直接丢弃重试（最多 3 attempt）。
- **澄清/拒答判定**：首个成功候选竞速判定，命中即返回（不等待其余候选）；仅首次尝试的首候选接受，防重试期反复澄清。
- **结果集多数表决**：多候选全部执行，按结果集规范化签名分组，**过半数**才采纳多数派（平票取首个成功候选）。
- **结果合理性校验**：空结果集 / 全列为 NULL → 回喂原因再生成一轮。

### 2.4 安全层（6 道，工业级）

| 防线 | 机制 |
|---|---|
| SELECT-only | 40+ 禁用关键词正则（insert/update/drop/explain/outfile 等） |
| 表白名单 | 全量 schema 校验（**与圈表解耦，圈表遗漏不会误杀合法 SQL**，设计克制） |
| 行级权限 | 受限数据源自动注入行过滤谓词 |
| EXPLAIN 防线 | 预估扫描 >100 万行（`SQL_EXPLAIN_MAX_ROWS` 可调）拦截，LLM 获一次"收窄条件"自纠错机会，二次拦截终止并以拒答形态返回（不给演示数据托底） |
| 敏感列剔除 | dlp.ts 脱敏后进 schema / 中间表 |
| LIMIT 强制 | 默认 ≤500 行 |

### 2.5 数据链与分析层

- **M3 清洗链**：复杂分析先在源库跑 SELECT 落到应用库物理中间表（ait_*，最多 3 步、5000 行/步、TTL 24h、每用户 10 张），与源表严格隔离。
- **分析层**：专家 persona 路由（财务/不良/客户/风险）+ 金额单位口径强制对齐（v0.9.41）。

### 2.6 治理与反馈闭环（差异化亮点）

```
用户点赞 → FEEDBACK_UP 样例入库 → 检索注入 few-shot
用户点踩 → 反面教材注入（仅问题不注入错 SQL）
管理员审批采纳 → injectFewShotSamples → few_shot_examples 表（独立表，不污染业务知识 RAG）
指标提议（ANALYST）→ 管理员审批 ACTIVE → metric_versions 版本快照可回溯
评测集 CI 门禁（minAccuracy）→ 低于阈值阻断
```

**这一层是竞赛级 SOTA 系统普遍缺失的能力**（它们通常没有权限、审批流、审计、版本快照）。

## 三、实测准确率数据

### 3.1 评测资产

| 评测集 | 规模 | 分类分布 |
|---|---|---|
| 主集 `evalCases.json`（CRM ds_eval_crm） | 148 条 | single_agg 36 / join 26 / time 26 / subquery 22 / clarify 14 / refuse 14 / permission 10 |
| 业务机创集 `evalCases.jichuang.json` | 54 条 | 含 multi_dim 12（主集缺口） |

**评测口径（严谨度高于多数公开基准）**：执行准确率 = 生成 SQL 与 golden SQL **执行结果集关系等价**（行内取值排序 + 行间多重集对齐 + 数值容差 max(0.005, 1e-9)），对别名/列序/等价写法天然宽容，只关心数值正确性；Top-N 用例支持 ordered 行序比较；评测强制 `refreshCache=true` 旁路缓存（防止测量失真）。

### 3.2 最新实测结果（2026-08-30，54 条业务机创集，全链路 HTTP 端到端）

| 分类 | 准确率 | 解读 |
|---|---|---|
| **总体** | **75.9%**（41/54） | 距手册验收目标（20 题抽测 ≥85%）有 9 个百分点缺口 |
| single_agg | 94.4%（17/18） | 已近人类水位（BIRD 人类 92.96%），说明基础链路完全可靠 |
| clarify | 100%（4/4） | 歧义澄清机制有效 |
| refuse | 100%（4/4） | 拒答边界把握准确 |
| subquery | 75.0%（6/8） | 嵌套子查询（快照期锚定等）基本可用 |
| time | 62.5%（5/8） | 时间对比弱，主要败在相对时间锚定 |
| **multi_dim** | **41.7%**（5/12） | **最大短板**：多维度组合（交叉分析/多指标并列） |

### 3.3 稳定性观察（需重点关注）

| 运行时间 | 同集（54 条） | 平均耗时 |
|---|---|---|
| 2026-08-29 09:05 | 68.5% | 172.8s |
| 2026-08-29 11:45 | 44.4% | 72.0s |
| 2026-08-30 00:51 | 70.4% | 629.2s |
| 2026-08-30 04:01 | **75.9%** | 161.9s |

**同集波动 44.4% ~ 75.9%（31 个百分点）**，耗时波动 72s ~ 629s（8.7 倍）。工程视角这是比准确率均值更危险的问题：用户体验不可预期，且单点评测无法作为质量依据。

## 五、差距归因（按影响度排序）

### 5.1 模型能力差距（根本约束）
本地 Qwen3.8-27B（主）+ 8B（快速档）与云端旗舰存在代差。实测证据：8-29 两次运行中"简化 SQL 快速档"比例增高时准确率掉 24 个百分点（44.4% 那次平均耗时仅 72s），说明快速模型在多表/多维度场景下产生系统性偏差——注释中已明确记录"快速模型在多表 JOIN 时易漏 COUNT(DISTINCT) 造成重复计数"。

### 5.2 值级检索（value grounding）缺失
BIRD/业务实测中的高频错误类型是"**枚举值/字面值猜错**"（如快照期 BB='1'、BBRQ 锁错期、状态机取值）。系统目前只有**事后自省**（生成中一次 SELECT DISTINCT），没有**事前值索引**（列值 → 注入 schema 上下文）。项目自己的《数据源配置与问数质量保障指导手册》第 472 行也把"枚举值猜错"列为"NL2SQL 最常见的准确率杀手之一"。

### 5.3 时间语义锚定弱（time 62.5%）
相对时间（"本年/上期/最新"）在业务库需锚定到**业务日期列 + 快照期过滤**（如 `BB='1' AND BBRQ=(SELECT MAX(BBRQ) ...)`）。当前依赖 LLM 自由发挥，无结构化的"业务日期列注册表"，也未对时间类问题强制走自省链。

### 5.4 多维度组合缺范式（multi_dim 41.7%）
多维度交叉（如"各机构各产品线的投放金额分布"）需要条件聚合/交叉表/多维 GROUP BY 范式引导。虽然 prompt 已注入"复杂分析范式"（CTE/RANK/条件聚合），但 multi_dim 类**未进入主评测集**（仅机创集 12 条），治理上缺少持续的失败归因输入源。

### 5.5 上下文无仲裁机制
9 类注入源在 prompt 中**线性拼接**，冲突时无优先级仲裁（仅铁律声明了"优先级高于样例与知识片段"，但指标/业务口径/知识/样例之间无仲裁规则）。预算截断按各自配额独立执行，极端情况下可能整体超过模型有效注意力区间（本地模型上下文窗口是硬约束）。

### 5.6 稳定性与延迟
- 波动来源：LLM 温度/采样随机性 + 多候选并行竞速路径差异 + 快速模型路由阈值边界案例。
- 延迟瓶颈：本地推理 + 最多 3 候选串行执行 + 自省链（自省后二次生成）叠加；629s 那次为最差路径（复杂问题 + 首选失败重试）。

## 六、优化建议（P0-P3）

### P0（准确率杠杆最大，建议 1-2 周内启动）

**P0-1 multi_dim 专项攻坚（目标 41.7% → 60%+）**
1. 对机创集 12 条 multi_dim 全部失败 case 做归因分类（漏维度/聚合口径错/排序错/表选错），产出《multi_dim 失败模式清单》；
2. 利用已建成的**指标层 dimensions 字段**（P2-14 语义资产）：multi_dim 问题命中指标时，把可切分维度清单显式注入 prompt，约束 GROUP BY 范围；
3. 在 SQL 样例库补充 8-12 条复杂交叉分析样例（场景标签召回，参照 v0.4.15 复杂样例扩充的先例）；
4. multi_dim 类问题强制 3 候选 + 结果表决（当前复杂度分档只看表数与 multi-step，未覆盖 multi_dim）。

**P0-2 业务日期列注册表 + 时间锚定强制范式（time 62.5% → 75%+）**
1. 数据源配置增加结构化"时间维度注册"（业务日期列 / 快照期列 / 口径列及其固定取值），复用 businessNote 的注入通道；
2. 生成阶段一 prompt 对已注册时间列强制注入锚定范式：`WHERE 口径列=<登记值> AND 日期列=(SELECT MAX(...) ...)`；
3. 时间类问题检测命中时，**强制先走数据自省链**（复用现有机制，把"不确定才自省"升级为"时间类必自省"），让 MAX(BBRQ) 类真实取值先落 ground。

**P0-3 值级检索（value grounding）落地（"枚举值猜错"是头号杀手）**
1. 复用现有 SELECT DISTINCT 自省能力，为高频枚举列构建**列值索引**（定期离线采样 top 值 + 问题文本命中即注入 prompt schema 上下文）；
2. 建议做成数据源级开关（手册 §6 已建议"在取值敏感业务源上开启"），并与 dlp.ts 脱敏管线联动（值样本过敏感列过滤）；
3. 索引重建调度挂在现有巡检调度器上（`startPatrolScheduler` 模式）。

**P0-4 稳定性治理（先可度量，再优化）**
1. 评测增加**双跑对比**（同集连跑 2 次取均值），CI 门禁改为"均值 + 单跑跌幅上限"双指标，消除 44% vs 76% 级波动对质量判断的干扰；
2. SQL 生成阶段强制 `temperature=0`（如有可配项），减少采样随机性；
3. 多数表决当前"无多数（各候选互不相同）取首个成功候选"——建议改为无多数时选**与其余候选结果集交并集最相近**者，或追加一次生成再表决（针对 ≤3 候选的小样本投票，过半数阈值偏苛）。

### P1（工程增强，建议 1 个月内）

**P1-1 上下文仲裁器**：为 9 类注入定义显式优先级（铁律 > 指标 > 业务口径 > 知识 > 样例 > 历史），并提供冲突检测（同名字段口径冲突时高优先级截断低优先级内容），防上下文稀释与口径互斥。

**P1-2 评测集扩充**：主集补充 multi_dim 类（当前缺口）；总规模建议扩至 300+ 条；把手册要求的"业务方 20 题抽测 ≥85%"固化为独立 CI 用例集。

**P1-3 延迟优化（目标 P50 < 90s）**：
- few-shot / 知识库 embedding 检索与 schema 圈表并行预取（当前链路存在可并行的串行段）；
- 快速模型路由阈值 `LLM_SQL_ROUTE_MAX_TABLES` 调优实验（在准确率不回归前提下放宽）；
- 结果缓存（L1/L2 已有）结合语义近邻命中率提升，重复问题不重跑 LLM。

**P1-4 SQL 阶段模型升级 A/B**：`LLM_SQL_ENGINE/LLM_SQL_MODEL` 阶段路由已就绪——建议对 SQL 生成阶段单独接入更强模型（云端旗舰或 32B 级专用模型如 OmniSQL 开源方案），用评测集做严格 A/B（准确率 + 延迟双指标），把"模型差距"从根本约束降级为可调参数。

**P1-5 评测集 golden SQL 反哺样例库**：把 202 条评测集的 golden SQL 批量导入 sql_examples（标注场景标签），立即提升 few-shot 召回质量——零模型成本、一天可完成。

### P2（长期能力建设）

**P2-1 微调闭环（Q4 计划沿革）**：以 sql_examples（评测 golden + 点赞沉淀 + 审批采纳样本）为语料做 LoRA 微调；**同步建设"错误 SQL 负样本库"**（当前点踩只记录问题与涉及表，不记录错 SQL——建议完整留存错 SQL + 错误类型标注，这是微调与 DPO 的必要语料）。

**P2-2 生成-批判-修正多体架构**：现有 EXPLAIN + 结果校验是两层浅校验；可增加 SQL 语义审查体（AST 等价性检查、JOIN 基数膨胀警告、聚合误用检测），对齐 BIRD-Critic 的自修正范式。

**P2-3 JOIN 路径推荐**：主集 join 类占 26/148（17.6%），schema 已有主键标记——建议扩展外键关系登记，构建 lightweight schema graph，在圈表后对多表问题注入推荐 JOIN 路径（含基数提示），降低 LLM 组合搜索难度。

**P2-4 值一致性回归**：把"快照期锚定"（锁定最新 BBRQ 等）做成可断言的口径契约，加入评测 ordered 类断言，防口径漂移回归。

## 七、结论

1. **架构定位准确**：本引擎的技术路线（工程增强 + 执行反馈 + 多候选投票 + 治理闭环）与 BIRD 榜单上 82% 级系统的路线完全同构——它们把原生 72.55% 的模型推到 82.39%，靠的正是本系统已在做的一切。差距不在方向，在**深度与算力**。

2. **当前水位**：75.9%（54 条业务集，含权限/澄清/拒答混合口径）对标 BIRD 中游水位；single_agg 94.4% 与 clarify/refuse 双 100% 证明基础链路已"可用"；time 62.5% 与 multi_dim 41.7% 是通往"可信"的两块拼图。

3. **投资优先级**：不建新功能。P0 四件事（multi_dim 攻坚、时间锚定、值级检索、稳定性治理）预计可把总体准确率推至 82-85%，恰好跨过手册验收线并进入 BIRD 榜单前列区间。

4. **最大风险**：稳定性（±15 分波动）而非均值。在稳定性问题解决前，一切准确率数字都应标注置信区间。

5. **差异化护城河**：行级权限、EXPLAIN 防线、审批治理流、审计留痕——这些竞赛系统没有的能力，是本系统在企业场景的真实壁垒，应继续保持并在对外材料中突出。
