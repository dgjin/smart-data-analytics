# 图库（图数据库）接入评估结论

> 评估日期：2026-10-22 ｜ 对应版本：v0.9.115 ｜ 触发条件来源：《业务本体 M3 软校验与演化闭环设计》1.3 / 8 节
> **结论：暂不接入。** 现有规模与查询形态均在 MySQL 原生方案的经济区间内，图库带来的能力增量不足以覆盖其组件、一致性、运维与备份成本。本结论附可复现的核查方法与自动复核门槛，条件成立时再启动选型。

## 1. 预先约定的触发条件

| # | 条件 | 阈值 | 依据 |
| --- | --- | --- | --- |
| T1 | 跨源联邦 | 单次问数涉及 ≥ 2 个数据源 | 图库最擅长跨源实体连通；单源场景用 MySQL 即可 |
| T2 | 单源表数 | > 100 张表 | 圈表与多跳路径在百表内可被关键词 + embedding 覆盖 |
| T3 | 本体资产规模 | 实体 > 500 或绑定 > 2000 | 超过后关系表递归查询延迟开始显著 |
| T4 | JOIN 类问题占比 | ≥ 30%，且 ≥ 3 表多跳 ≥ 10% | 图遍历收益随跳数上升 |
| T5 | 路径查询延迟 | 两表最短路 P95 > 200ms | 直接的用户体感门槛 |

T1 / T2 为原始约定，T3~T5 为本次补充的量化补充项（可监控、可告警）。

## 4. 成本收益分析

### 4.1 图库能带来什么

- 多跳关联的一次查询完成（Cypher 可变长路径），替代应用层 BFS。
- 图算法（中心度、社区发现）用于本体健康度与冗余关系识别（M3 的"待复核"可复用）。
- 天然表达跨源实体连通（若将来做联邦）。

### 4.2 需要付出什么

| 成本项 | 具体影响 |
| --- | --- |
| 组件 | 新增 Neo4j/AGE 实例：部署、升级、备份、监控、权限、多实例一致性 |
| 双写一致性 | 本体资产主存 MySQL（事务/版本快照/审批状态机），需同步到图库；失败回滚与补偿链路复杂 |
| 查询路径 | 图库只解决"选表 / 路径 / JOIN 口径"，**SQL 执行仍在业务库**；需新增图查询层并对提示词生成链路适配 |
| 迁移风险 | M3 刚上线（软校验/漂移联动/审批），叠加存储迁移会放大故障面 |
| 收益有限 | 当前关系 5 条、跳数 ≤ 2、最短路成本可忽略；百表以下圈表已能命中 |

### 4.3 更便宜的替代（优先做）

1. **递归 CTE**：MySQL 8+ `WITH RECURSIVE` 可在关系表上做多跳查询（当前 MySQL 9.6 支持），无需新组件。
2. **索引与缓存**：`ontology_relations(source_table, target_table)` 复合索引 + 最短路结果短 TTL 缓存。
3. **抽象接口**：把"图查询"收敛为 `ontologyGraph.findPaths()` 等 3~4 个函数，底层先 MySQL 实现，为将来切换保留缝。

## 5. 触发后的选型对比（预研，不落地）

| 方案 | 优势 | 代价 | 适用 |
| --- | --- | --- | --- |
| **Neo4j 社区版** | Cypher 成熟、图算法库全、生态好 | 独立 JVM 服务、内存占用高、社区版集群能力弱 | 资产规模大、需要图算法 |
| **PostgreSQL + Apache AGE** | 复用现有 PG、SQL 与 Cypher 混合 | 扩展版本绑定 PG 大版本、运维需 DBA 熟悉 | 已有 PG 且不想多组件 |
| **MySQL 递归 CTE** | 零新组件、与本体表同库同事务 | 深路径性能随跳数下降、无图算法 | **当前及 T2/T3 未触发前** |

选型前置条件：先用 `ontologyGraph` 抽象层跑通 MySQL 递归实现并测得 T5 指标，再按瓶颈决定是否引入图库。

## 6. 分阶段演进路线

| 阶段 | 触发信号 | 动作 |
| --- | --- | --- |
| A（当前） | — | MySQL 原生本体 + 关系表；最短路应用层 BFS；本结论归档 |
| B | 单源表数 > 50 或关系 > 500 或最短路 P95 > 100ms | 抽 `ontologyGraph` 接口 + 递归 CTE + 路径缓存，补压测 |
| C | T1~T5 任一成立 | 按第 5 节选型接入图库，`ontologyGraph` 换实现，业务代码零改动 |

## 7. 复核机制

- **频率**：每季度一次；M3 上线后追加一次；任一数据源表数 > 50 时立即复核。
- **自动化**：把 2.1~2.3 的统计做成 `npm run ontology:scale`（读 `data_sources.schema_json`、本体五表与 `query_audit_log`），输出一行判定（触发/未触发）。
- **告警**：Prometheus 侧可对 `ontology_entities` / `ontology_relations` 计数做季度采集；表数变化由数据源保存时记录。
- **结论更新**：任一条件触发时，在本文件追加「复核记录」小节并重开选型评审。

## 附录 A：核查 SQL（可复现）

```sql
-- 数据源表数：解析 schema_json（数组或 {tables}）
SELECT id, name, type, status, schema_json FROM data_sources ORDER BY created_at ASC;

-- 本体资产规模
SELECT 'entities' t, COUNT(*) c FROM ontology_entities
UNION ALL SELECT 'bindings', COUNT(*) FROM ontology_bindings
UNION ALL SELECT 'relations', COUNT(*) FROM ontology_relations
UNION ALL SELECT 'hierarchies', COUNT(*) FROM ontology_hierarchies
UNION ALL SELECT 'value_notes', COUNT(*) FROM ontology_value_notes;

-- 近 30 天 JOIN 占比（真实列名为 executed_sql）
SELECT COUNT(*) total,
       SUM(UPPER(executed_sql) LIKE '%JOIN%') with_join
FROM query_audit_log
WHERE created_at >= DATE_SUB(NOW(), INTERVAL 30 DAY)
  AND endpoint = 'query'
  AND executed_sql <> '';
```
