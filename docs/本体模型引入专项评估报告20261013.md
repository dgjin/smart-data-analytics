## 二、概念界定：本报告讨论的「本体模型」是什么

| 层级 | 形态 | 代表 | 对本系统的适配性 |
|---|---|---|---|
| 形式化本体 | OWL/RDF + 三元组库 + 推理机 | 语义网 / 学术 | **不适配**：LLM 消费提示词文本而非公理体系，需全新基建与技能栈，收益不可量化 |
| 业务本体（语义层） | 实体 + 关系 + 指标 + 维度 + 层级 + 术语绑定 | dbt Semantic Layer、Palantir Ontology、Cube | **推荐**：与现有「登记→命中→软注入」架构同构，可直接扩展现有指标层 |
| 知识图谱（实现手段） | 图数据库存储上述实体关系 | Neo4j / NebulaGraph | **可选手段**：当前规模下 MySQL 原生即可承载，图库按阈值后置（见 §六） |

本报告以第二层级（业务本体）为评估与实施口径；第三层级仅作为实现选型讨论。

## 四、差距分析：离「完整本体」差哪四块

| # | 缺口 | 现状证据 | 对应的实测痛点 |
|---|---|---|---|
| 1 | **实体层缺失** | 无业务对象抽象（如「机构」「项目」「报告期次」）；实体身份散落在 JGMC 等物理列里，别名归并依赖 markdown 知识库 | 术语理解不稳定；同一概念多表称呼（如 JGMC / 机构名称）无统一身份 |
| 2 | **关系层缺失（最大缺口）** | 全库无 JOIN 路径登记（grep 外键/关系建模仅 1 处注释）；`sqlExecutor.ts` 仅校验 FROM/JOIN 表名在白名单内，**JOIN 如何连接、连得对不对完全由 LLM 推断，无任何语义校验** | join 类占主集 26/148（17.6%）；multi_dim 41.7% 的组合分析依赖多表组合搜索 |
| 3 | **层级层缺失** | 组织层级（集团→分公司→项目）、时间层级（年→期次 BBRQ/BB）、指标上卷路径均无结构化登记；下钻（`query/drill.ts`）只是「维度值等值筛选」，无层级导航 | time 62.5% 的时效锚定问题；下钻无法按层级展开 |
| 4 | **值域语义无登记位** | `BB='1'`（本期）/'2'（上期）、状态码含义等只能写进铁律或知识文本（自然语言），非机器可读 | SQL 报告判定「枚举值猜错是头号杀手」（P0-3 值级检索）；快照期锚定（MAX(BBRQ)+BB 固定值）靠模型记忆 |
| 5 | **语义校验层缺失**（派生缺口） | 执行安全层只有「表列白名单 + 只读 + EXPLAIN 防线」，无「JOIN 合法性 / 指标口径一致性 / 值域契约」语义校验 | SQL 报告 P2-2 建议的「生成-批判-修正」中缺少语义审查体 |

## 五、可行性评估

| 维度 | 判定 | 证据 |
|---|---|---|
| 基建复用 | 全部就绪 | ① 建表迁移模式（`infra/schema.ts` 40 表 + migration.ts）；② 治理状态机与版本快照（metric_definitions + metric_versions 先例）；③ prompt 注入模板（buildMetricPrompt / buildIronRulesPrompt）；④ embedding 检索（`callEmbedding`，schemaLinking 已在用）；⑤ token 预算（`llm/promptBudget.ts`）；⑥ 评测 A/B（evalRunner + minAccuracy 门禁）；⑦ 血缘可视化（lineage 视图）；⑧ autoConfig 预填（知识骨架 + 铁律模板先例） |
| 架构契合 | 天然同构 | 全链路本质是「静态资产登记 → 问题命中 → 软注入 prompt → 执行层白名单兜底」——指标层（P1/P2-14）已验证该模式生产可用 |
| 规模适配 | 无需图库 | 单数据源表规模在数十张量级，prompt 最多注入 8 张表；关系查找用 MySQL 递归 CTE 足够。引入 Neo4j 将破坏零外部依赖部署链且带来运维成本 |
| 风险封闭 | 可控 | 本体只作 prompt 软约束 + 告警（不拼 SQL），生成结果仍过 `executeSafeSql` 白名单；新表独立，不触碰核心链路与安全层 |
| 团队适配 | 无新技能栈 | 纯 TypeScript + MySQL，治理/注入/评测全部沿用现有工程模式；不需要 NER 模型训练、SPARQL、图查询语言 |

**综合判定：可行性高（86/100）。** 唯一需要权重考量的不是「能不能做」，而是「先做哪块、做到什么强度」——建议以 §七 三期路线控制节奏。

## 七、推荐方案：三期落地路线

### M1 实体与术语层（约 3-5 人日）

- **新增表**：
  - `ontology_entities`：id / data_source_id / name（实体名，如「机构」）/ entity_type（主体·客体·时间·地理）/ aliases(JSON) / description / status / version / created_by
  - `ontology_bindings`：id / entity_id / table_name / column_name（可空=表级）/ role（identity 标识列 · attribute 属性列 · relation_key 关联键）
  - `ontology_value_notes`：id / data_source_id / table_name / column_name / value_code / meaning（如 BB=1 → 本期）
- **治理**：创建/变更写版本快照（对齐 metric_versions 先例）；初期 ADMIN 直建（权威性对齐 iron_rules），后续开放 ANALYST 提议-审批
- **解析器**：问题 → 实体/术语命中（子串 + embedding 精排，复用 `matchMetrics` / schemaLinking 模式）
- **集成点**：① `schemaLinking.ts` 打分增加实体命中权重；② 新增 `server/query/ontology.ts`（仿 metrics.ts 结构）；③ `buildOntologyPrompt` 注入命中实体段（仿 buildMetricPrompt）；④ 管理面板复用指标治理 UI 模式
- **验收**：术语命中召回、表选择准确率（圈表 top8 含 golden 表比例）A/B 提升

### M2 关系与层级层（约 4-6 人日）

- **新增表**：
  - `ontology_relations`：id / data_source_id / from_table / from_columns / to_table / to_columns / join_type / cardinality（1:1·1:N·N:1）/ purpose / status / version / created_by
  - `ontology_hierarchies`：id / data_source_id / name（如「机构层级」）/ levels(JSON 列序)
- **能力**：① 注入「已登记关联路径」段（措辞强度对齐铁律：跨表查询必须经由登记路径，无路径时注入候选提示）；② 递归 CTE 最短路查找（表规模小，无需图库）；③ 血缘视图融合本体关系边（lineage graph 扩展 edge kind）
- **集成点**：liveQueryPrompts 新增注入段；analysisChain 多步查询路径校验；DataLineageView 展示关系分级
- **验收**：join 类子集与 multi_dim 通过率相对提升（建议目标 ≥20%，以双跑均值口径衡量）

### M3 语义校验与闭环（约 5-8 人日）

- **软校验器**（`ontology_validation.ts`）：AST 分析——引用未登记 JOIN 路径 / 指标口径偏离登记 expr / WHERE 硬编码值与值域注释矛盾 → query_trace 告警 + 接入现有自纠错（fallback 三层自救）给一次修复机会；**先告警不拒答**，稳定后按评测数据收紧
- **漂移联动**：物理 schema 比对 → 本体绑定项标记 stale（复用血缘 stale 模式 + kb_drift 基建）
- **演化闭环**：用户反馈/失败样本 → 自动提议新实体/关系（PENDING→审批，复用指标治理流）；autoConfig 扩展「本体预填」（对齐其知识骨架/铁律模板预填先例）
- **验收**：负面样例回归、口径一致性断言、端到端链路验收（口径遵循《AI 工程闭环完整化路径20260911》验收纪律：「提问失败→审核采纳→入库→下次相似问题一次成功」）

**汇总**：合计约 12-19 人日；如需压缩，可先做 M1 + M2（关系层是收益最大单项），M3 随下一版本滚动。

## 十、结论与建议

1. **可行性：高（A-，86 分）。** 系统已具备完成度约 60% 的「半本体」资产，其中指标语义层 + 治理闭环是最难的 20%，已经建成；缺口集中在实体/关系/层级/值域四块，每块都有现成模式与集成点可复用。
2. **靶向明确。** 四个缺口正对 SQL 报告标注的三大实测短板（multi_dim 41.7%、time 62.5%、枚举值猜错）与 join 类 17.6% 的主集占比——本体不是「为架构而架构」，是当前准确率短板的直接解药。
3. **路径明确、成本可控。** M1→M2→M3 三期共约 12-19 人日，零新增外部依赖、零新技能栈；关系层（M2）是收益最大单项，建议与 M1 打包立项。
4. **与既有规划的关系已对账。** 本报告承接 20260914 P2-3（JOIN 路径推荐）并系统化；Q4 图库方案降级为阈值触发项（触发条件：跨源联邦问数 / 单源表数 > 100 / 多跳检索占比显著），M2 数据结构与其图模型字段兼容、可平移。
5. **启动建议**：① 立项 M1+M2，先行修订 Q4 文档方向三口径；② 同步落地「上下文仲裁器」与「评测双跑」（两项前置配套，均为既有报告已列事项）；③ 以本报告 §九 指标体系作为验收标准。

**一句话总述：本体模型不是推倒重来，而是把「登记 → 命中 → 软注入 → 治理 → 评测」这条已被指标层跑通的生产线，从「指标」复制到「实体、关系、层级、术语值域」。**
