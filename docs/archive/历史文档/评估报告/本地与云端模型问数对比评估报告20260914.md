# 本地模型与云端模型问数能力对比评估报告

> 评估对象：智能问数据分析系统 NL2SQL 双引擎通道
> - **本地通道**：Ollama `qwen3.8:27b-mlx`（18.2GB，MLX 量化，常驻本机）
> - **云端通道**：DeepSeek 官方 API `deepseek-flash`（DeepSeek-V4.1-Flash，思考模式默认开启）
> 评估日期：2026-09-14 · 系统版本：v0.9.61 · 评估方式：同一批 60 条分层抽样用例双引擎实跑，走真实问数 HTTP 全链路（防御层→圈表→生成→校验→执行）
> 证据来源：`server/eval/reports/eval-report-2026-09-14T14-19-11-281Z.json`（云端）、`eval-report-2026-09-14T16-51-09-698Z.json`（本地）、服务端 `llm_tokens_total` 监控计数、服务端运行日志

## 二、评测方法

### 2.1 用例集

从 148 条主评测集（`server/eval/evalCases.json`）按类别配额**确定性抽样 60 条**（类内均匀间隔，非随机可复现，两个引擎使用完全相同的用例），文件：`server/eval/evalCases.compare60.json`：

| 类别 | 全量 | 抽样 | 说明 |
|---|---|---|---|
| single_agg 单表聚合 | 36 | 14 | COUNT/SUM + GROUP BY/WHERE |
| join 多表关联 | 26 | 10 | clientId/ownerId/部门等关联 |
| time 时间对比 | 26 | 11 | 年月分组 / 区间 / 季度 |
| subquery 嵌套子查询 | 22 | 9 | IN / EXISTS / 派生表 |
| clarify 需澄清 | 14 | 6 | 歧义问题应澄清而非猜测 |
| refuse 应拒答 | 14 | 6 | 不存在表 / 敏感字段 / 写操作 |
| permission 行级权限 | 10 | 4 | 受限数据源行过滤注入正确性 |

### 2.2 公平性设计

1. **同批用例、同一服务进程**：通过评测器新增的请求级引擎参数（`--engine/--model`，即问数接口 `model` 字段）在同一服务进程内分别实跑，基础设施、schema 注入、知识库检索链路完全一致，仅切换 LLM；
2. **旁路缓存**：`refreshCache=true`，杜绝 L1/L2 结果缓存命中导致的测量失真；
3. **模型预热**：本地模型评测前预热常驻（消除冷加载首问偏差）；
4. **生产配置**：本地超时取实际部署值 `OLLAMA_TIMEOUT_MS=300000`（5 分钟），评测器逐条上限 600s；云端无超时截断；
5. **指标口径**：执行准确率 = 生成 SQL 与 golden SQL **结果集关系等价**（忽略列别名/列顺序，数值容差比较）；clarify/refuse 类按行为返回判定。

### 2.3 口径说明

- 云端 `deepseek-flash` 默认开启思考模式（响应含推理链），延迟已包含推理时间；
- 评测只自动校验**执行结果正确性**；数据解读文案、图表配置等主观质量未纳入自动口径（两者均正常返回解读）；
- 本地 12 条失败为**超时截断**（非答案错误），在统计中单列 `error` 与 `fail` 区分。

## 三、质量对比

### 3.1 分类准确率

| 类别 | 云端 | 本地 | 差异 |
|---|---|---|---|
| single_agg 单表聚合 | 78.6%（11/14） | 71.4%（10/14） | 云端 +1 条 |
| join 多表关联 | **80.0%（8/10）** | 60.0%（6/10） | 云端 +2 条 |
| time 时间对比 | 63.6%（7/11） | **72.7%（8/11）** | **本地 +1 条** |
| subquery 嵌套子查询 | **44.4%（4/9）** | 22.2%（2/9） | 云端 +2 条 |
| clarify 澄清 | 100%（6/6） | 100%（6/6） | 打平 |
| refuse 拒答 | 100%（6/6） | 100%（6/6） | 打平 |
| permission 行权 | 100%（4/4） | 100%（4/4） | 打平 |

**解读**：两者在**安全边界行为**（澄清/拒答/权限）上完全一致——说明这些能力主要由确定性工程层（判定规则、AST 行过滤）保障，与模型强弱无关。质量差距集中体现在 join 与 subquery 两类结构化语义上。

### 3.2 胜负案例剖析

**（1）本地胜出的 3 条：云端的"输出形态过度扩展"（tm01/tm03/tm05）**

问题："2026年4月的拜访次数是多少？"（期望纯标量）

| 引擎 | 生成 SQL | 结果集 |
|---|---|---|
| golden | `SELECT COUNT(*) FROM visits WHERE LEFT(\`date\`,7)='2026-04'` | `[5]` |
| 云端 | `SELECT LEFT(\`date\`,7) AS ym, COUNT(*) ... GROUP BY ym` | `['2026-04', 5]` |
| 本地 | `SELECT COUNT(*) AS visit_cnt FROM visits WHERE LEFT(\`date\`,7)='2026-04'` | `[5]` |

云端**数值完全正确**，但将隐含维度（月份）显式化为分组列，行内取值多元组与 golden 不等价而判 fail。三条同型案例说明：严格等价口径下，强模型"更完整作答"反而失分——**这是口径与直觉的偏差，不代表云端信息错误**（对用户而言多一列月份信息并无损失）。

**（2）本地超时的 7 条（云端全部按时答对）：存在性/值匹配类复杂语义**

| 用例 | 问题 | 云端 | 本地 |
|---|---|---|---|
| sa13 | 积极情感的拜访有多少条？ | 11.1s ✓ | **629.5s ✗**（超评测上限） |
| jn11 | 积极情感拜访涉及多少个客户？ | 8.4s ✓ | 301s ✗ |
| jn16 | 没有拜访记录的客户有多少个？ | 11.0s ✓ | 301s ✗ |
| tm17 | 2026年8月各团队客户的拜访次数？ | 12.2s ✓ | 301s ✗ |
| tm24 | 2026年第三季度的拜访次数是多少？ | 13.7s ✓ | 301s ✗ |
| sq01 | 有拜访记录的客户有多少个？ | 8.0s ✓ | 301s ✗ |
| sq10 | 存在拜访记录的客户有多少个？ | 11.6s ✓ | 301s ✗ |

共同特征：涉及**值过滤不确定性**（`sentiment='积极'`）、**存在性/非存在性**（IN / EXISTS / LEFT JOIN IS NULL）、**多值时间列表**（季度 → 3 个月份）。此类问题在链路上触发更多上下文注入与自省/修复重试，本地推理的 prompt 处理时间翻倍放大，单次调用即触及 300s 上限（服务端日志记录超时 19 次，含重试）。云端同等 prompt 只需 8-14s。

**（3）双方都失败的 5 条（sa24/sa34/jn01/sq18/sq20）：评测集共难点**

- sa24"央国企客户有多少个"：两引擎均将 `listCategory='央国企客户'` 误用为 `clientType='央国企'`——**领域值绑定（value grounding）是双方共同短板**；
- jn01"每个客户的拜访次数"：两引擎均返回 LEFT JOIN 全量 60 行（含 0 次拜访客户），golden 为 INNER JOIN 52 行——语义边界模糊（"每个客户"是否含无拜访客户存在合理解读空间）；
- sq18/sq20：子查询改写的等价性判断，两者均错。

这三类失败中，sa24 类（值绑定）可通过**业务知识库补充字段取值样例**系统性修复，属于运营可解问题而非模型能力天花板。

### 3.3 行为差异

- **sa29"产业客户有多少个"**：云端触发澄清（要求用户明确"产业客户"定义），本地直接给答案（值猜错）——**云端更谨慎、本地更"敢答"**。对歧义问题，云端行为更符合安全设计预期；但也可能带来"该答不答"的过度澄清（本次仅 1 条）。
- **双引擎的 39 条共同通过（65%）**构成基本盘：常规单表聚合、明显关联、明确时间过滤类问题，本地与云端完全等效。

## 六、结论与建议

### 6.1 场景选择矩阵

| 场景 | 推荐引擎 | 理由 |
|---|---|---|
| 日常问数（默认） | **云端 deepseek-flash** | 快 14.7 倍、准 6.7pp、零超时，成本约 2 分/问 |
| 数据不出内网 / 断网环境 | 本地 | 唯一可用选项（安全合规场景） |
| 简单单表统计、看板固定口径 | 本地可用 | 与云端等效率 65%，单表类 71% 可用 |
| 复杂关联 / 子查询 / 存在性判断 | **云端** | 本地 20% 直接超时，质量差距最大区 |
| 澄清 / 拒答 / 权限敏感 | 两者均可 | 安全行为完全一致（工程层保障） |

### 6.2 落地建议

1. **默认引擎已正确**：当前配置 `AI_ENGINE=deepseek`（v0.9.60 起支持云端主引擎 + 缺 Key 自动转移本地），建议保持；本地作为兜底通道的定位与实际能力匹配；
2. **本地超时治理**：若需提升本地兜底体验，可将 `OLLAMA_TIMEOUT_MS` 下调至 120s 快速失败（避免 5 分钟空等），让用户尽早改走云端重试；
3. **值绑定共同短板**：两引擎均在"央国企客户/产业客户"等领域值上错配字段——在数据资源库**业务知识库补充字段取值样例**（sentiment/listCategory/clientType 等）可同时提升两个引擎，是最高杠杆的运营动作；
4. **混合路由（可选增强）**：后续可对 subquery/join 复杂度问题自动路由云端、简单单表问题允许本地，兼顾成本与体验；本次评测的请求级引擎切换能力（`--engine/--model`）已具备路由实验基础；
5. **口径建议**：评测集可对"输出形态过度扩展"（多带分组列）类案例评估宽容度，或在 golden 校验中容忍"golden 列为生成列子集且值一致"的场景，减少强弱模型误判差。
