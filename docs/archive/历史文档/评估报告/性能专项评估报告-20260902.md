## 二、重大结论修正

### 2.1 缓存机制：正常工作（之前结论有误）

**验证证据链**：
1. 第一次真实查询后，Redis 出现 qc:ds_1786620486498::各机构本年投放金额排名 键
2. 第二次相同查询 11ms 返回，fromCache: true
3. 同义改写问题 27ms 命中语义缓存，返回 matchedQuestion 与相似度 0.9992
4. 历史审计中已有 23 次 CACHE 命中记录（平均 28.8ms）

**之前误判的原因**：测试使用 ds_csv_upload（CSV 类型）。代码中 canRunLive = ['mysql','postgresql','greenplum'].includes(dsType)（routes/query.ts:179），CSV 数据源走演示模式，而演示模式路径**设计上就不写缓存**。

### 2.2 真实暴露的新问题：演示模式无缓存

CSV/Demo 数据源的演示模式（runSimulatedQuery）每次查询都要调用 LLM 编造数据（56~69 秒），但成功后**不写入任何缓存**（routes/query.ts:326-337 的 sim 路径无 setCachedQuery 调用）。使用 CSV 数据源的用户反复提问相似问题时，每次都要等待约 1 分钟。

## 三、真实性能瓶颈分析（按严重度排序）

### 瓶颈 1：LLM 推理耗时是绝对的性能瓶颈 【严重度：极高】

- **现象**：真实查询平均 249 秒（4 分钟），单次实测 121 秒
- **根因**：主模型 qwen3.8:27b-mlx（270 亿参数）本地 MLX 推理，每次查询至少 2 次大模型调用（SQL 生成 + 结果分析），每次 30~60 秒
- **模型路由现状**：.env.local 已配置 LLM_SQL_MODEL=qwen3:8b 小模型路由，但 liveQuery.ts:678 的复杂度判定 isComplexQuery = assessment.complexity === 'multi-step' || promptSchema.length >= 2 过于保守——**涉及 2 张表即判为复杂查询走大模型**，小模型路由实际命中率估计 <10%
- **影响**：几乎所有查询都走 27B 大模型

### 瓶颈 2：缓存命中率过低 【严重度：高】

- **现象**：历史命中率仅 3.5%（23/648）
- **根因**：
  - TTL 仅 10 分钟（CACHE_TTL_MS = 10 * 60 * 1000），超出后重复问题重新走 LLM
  - 用户问法多样，L1 归一化精确匹配覆盖有限
  - L2 语义缓存阈值 0.95 极保守（为防止误命中的正确取舍），同域近似问题落在 0.85~0.95 区间不命中
  - 无缓存预热机制

### 瓶颈 3：SSE 流式为伪流式 【严重度：高】

- **现象**：阶段进度条在动，但首字节时间（TTFT）仍是完整 LLM 生成时间
- **根因**：liveQuery.ts 分析阶段用 callLLMJson **阻塞等待完整 JSON 生成**（60s+），然后用 setTimeout(50) 循环推送 0%→100% 的假进度（代码自带 TODO: 未来支持流式输出 callLLMSegmentStream）
- **现状**：llmClient.ts 已实现真流式 callLLMSegmentStream，但 liveQuery 未接入
- **影响**：用户感知的"进度"是虚假的，真实等待时间无任何改善

### 瓶颈 4：FALLBACK 降级率 7.9% 且耗时长 【严重度：中高】

- **现象**：73 次降级，平均耗时 200 秒——用户等 3 分钟拿到的是演示假数据
- **根因方向**：需分析降级 detail（LLM 超时 / SQL 执行失败 / JSON 结构校验失败）
- **体验问题**：200 秒等待 + 假数据，比直接报错更伤害信任

### 瓶颈 5：前端图表组件无渲染优化 【严重度：中】

- QueryChat.tsx：1871 行巨型组件，仅 7 处 memo 化
- DynamicChart.tsx：927 行，**0 处** React.memo/useMemo——SSE 阶段事件高频触发 QueryChat setState 时，图表组件全量重渲染（recharts 重绘成本高）
- DataTable.tsx：有分页（pageSize=10），正常

### 瓶颈 6：演示模式无缓存 【严重度：中】

见 2.2 节。CSV 数据源用户每次相似提问都需等 56~69 秒。

## 四、优化建议（按 ROI 排序）

### P0：高收益、低风险（建议立即实施）

**4.1 放宽小模型路由的复杂度判定**
- 位置：server/liveQuery.ts:678
- 方案：isComplexQuery 增加更细的维度——仅单表 + 无多步推理的简单聚合查询走 qwen3:8b（速度快 3~5 倍），预计 60~70% 的日常查询可从 120s 降到 30~40s
- 风险：小模型 SQL 准确率略降，已有 FALLBACK 兜底 + 安全执行器校验，风险可控
- 验证：对历史 SUCCESS 问题集做离线准确率对比评测后再上线

**4.2 演示模式补充缓存**
- 位置：server/routes/query.ts:326-337（sim.ok === true 分支）
- 方案：演示模式成功结果同样调用 setCachedQuery（复用同一缓存键机制），CSV 用户相似提问从 60s → 30ms
- 风险：极低，纯增量逻辑

**4.3 缓存 TTL 延长 + 失效联动确认**
- 位置：server/queryCache.ts:11
- 方案：TTL 从 10 分钟延长到 30~60 分钟；确认数据源结构变更/数据更新时 invalidateQueryCache 被正确调用（该函数已实现，需验证调用点）
- 风险：数据时效性略降，分析型场景可接受；保留 refreshCache=true 用户强制刷新入口

### P1：高收益、需开发（建议排期实施）

**4.4 分析阶段接入真实流式输出**
- 位置：server/liveQuery.ts 分析阶段 + llmClient.ts
- 方案：callLLMJson → callLLMSegmentStream（已实现未启用），TTFT 从 60s+ → 2~5s，AI 解读文字逐 token 真实呈现
- 工作量：中（需处理流式 JSON 累积与校验）

**4.5 LLM 调用并行化**
- 方案：Schema Linking 与历史对话分析可并行；SQL 执行与"图表建议生成"可并行
- 预期：链路总耗时降低 20~30%

**4.6 FALLBACK 根因治理**
- 方案：统计 73 次降级的 detail 分布，针对 Top 原因修复（LLM 超时则调超时/降模型；SQL 失败则增强自愈重试；JSON 校验失败则增强 prompt 约束）

### P2：体验优化（可后置）

**4.7 前端渲染优化**
- DynamicChart.tsx 加 React.memo + chart option useMemo，阻断 SSE 高频更新引发的图表重绘
- QueryChat.tsx（1871 行）拆分阶段面板/消息列表为独立 memo 组件

**4.8 阶段进度真实化**
- 用真实事件驱动进度（Schema 链接完成 → SQL 已生成 → SQL 已执行 N 行 → 分析中），替代固定 50ms 假进度

**4.9 SQL 结果限量保护**
- 生成 SQL 自动包裹 LIMIT 200（无 LIMIT 时），防止大结果集撑爆缓存（200KB 上限）与前端渲染

### 注意事项

- 演示模式缓存命中返回的是模拟数据（dataProvenance: simulated），与首次查询口径一致，前端标注不变。
