## 二、本次实测发现的红灯问题（企业级不可接受，全部可复现）

### 🔴 R1：`npm run lint` 失败——CI quality 门禁必然红灯

`vite.config.ts` 两处类型错误：

- `base: '/'` 被错误放进 `build`（Vite 的 `base` 是顶层配置，`build.base` 不存在）——这不止是类型错误，**打包资产路径配置实际未生效**；
- `watch: null` 与 `UserConfig` 类型不兼容。

CI 第一步就是 `npm run lint`，意味着**当前 main 分支推上去 CI 必红**。而它已经带病通过了最近数次提交——说明提交时没有跑（或没有看）门禁。

### 🔴 R2：`pdfExport.ts` 的 `__dirname` TDZ 自引用 bug——测试文件加载失败 + 运行时隐患

```ts
const __dirname = typeof __dirname !== 'undefined' ? __dirname : path.dirname(__filename);
```

`const` 声明的变量在自己的初始化表达式里 `typeof` 自己会命中**暂时性死区（TDZ）直接抛 ReferenceError**。实测后果：`pdfExport.test.ts` 整个文件加载失败（60 个测试文件 1 失败），**且开发态（tsx/ESM）任何 import 该模块的链路都会崩**——PDF 导出功能当前在 dev 模式下大概率不可用。

### 🔴 R3：`lint:strict` 失败——新增的 ErrorBoundary 未过自家门禁

`src/components/ErrorBoundary.tsx` 3 个 TS2339（`state`/`props` 不存在）——类组件缺泛型声明。讽刺的是这正是为修"整页白屏"加的保护组件，自己却没过 strict 检查。

### 🟠 R4：OpenAPI 漂移 39 个端点

实测 `npm run docs:check`：**代码 99 个端点 vs 文档 60 个**。此前建立的"端点 OpenAPI 校验"资产已经失守——API 文档从"单一事实源"退化为"历史快照"。

### 🟠 R5：回归模式——近 15 个提交中 5 连 `fix(critical)`

`修复白屏 → 修复 API 404 → 修复 JSON 报错 → 修复知识库面板空白 → 恢复被删的 CRUD 路由`。这个序列说明：某次大变更（知识库导入导出）**破坏了既有功能后靠用户发现倒逼修复**，而不是被测试/CI 拦截。配合 R1（门禁红灯无人处理），指向同一个根因：**流程上允许跳过门禁直接进 main**。

### 🟡 R6：文档可信度受损

功能说明书 v0.8.8 变更记录声称"全量 690 单测通过、tsc 零错误"——实测为 **683 通过 + 1 文件加载失败 + tsc 三档全红**。这违背了项目自己最重要的工程决策"降级不撒谎"：**对用户不撒谎的系统，文档对开发者也不能撒谎**。

### 🟡 R7：仓库卫生

- `scripts/` 混入 **18 个一次性交付报告 MD**（COMPLETION_DELIVERY_REPORT.md、FINAL_DELIVERY_REPORT.md 等），工具目录变成了报告堆放区；
- `server/eval/` 提交了 **15 个 eval-report/load-report JSON** 历史产物，应入 `.gitignore` 只留基线。

## 三、相对 v0.5.3 评估的实质进步（应予肯定）

1. **评测体系补齐**：19→114 用例、六类分层覆盖、数值容差比较（吸收 ROUND 假阴性）、CI 结构门禁 `--min-count 100`、`--min-accuracy 85` 本地全量评测——上次评估的第一大短板已系统性解决；
2. **CI/CD 基建落地**：GitHub Actions 双作业（质量门禁 + 评测门禁）、Dockerfile、多实例部署指南、容量压测报告——高可用短板从"无"到"有方案"；
3. **LLM 弹性层**：`llmResilience.ts` 独立模块（含测试），上次"LLM 调用无重试熔断"的批评已响应；
4. **自纠错环统一基建**（v0.8.8）：清洗链自愈、计划自愈之上抽象了 `RetryStrategy` + `buildRetryPrompt` 统一出口，不侵入校验层——架构方向正确；
5. **知识库治理闭环**：CRUD + 导入导出 + 编辑自动重建向量切片（实测验证 346/346 切片全部有向量）；
6. **用户/开发双文档体系**：《用户使用指南》（帮助入口）与《功能说明书》（开发评审）分工 + 回退机制。

## 四、优化建议（P0-P3）

### P0 — 恢复门禁绿灯（半天内可完成，不做则 CI 资产等于零）

| # | 动作 | 修复点 |
|---|------|--------|
| P0-1 | 修 vite.config.ts | `base` 移到顶层；`watch` 用 `undefined` 替代 `null` |
| P0-2 | 修 pdfExport.ts TDZ | 改用 `fileURLToPath(import.meta.url)` 或 `globalThis.__dirname` 探测，恢复第 60 个测试文件 |
| P0-3 | 修 ErrorBoundary 泛型 | `class ErrorBoundary extends React.Component<Props, State>` |
| P0-4 | 同步 OpenAPI | 补齐 39 个缺失端点，让 `docs:check` 回绿 |
| P0-5 | 修正说明书 v0.8.8 记录 | 按实测数据改写"690/零错误"表述 |

### P1 — 堵住流程漏洞（1 周）

- **提交前本地门禁强制化**：husky pre-push 跑 `lint + test`（CI 红灯 5 连 critical 的根因是门禁可绕过）；
- **分支保护**：main 要求 CI 绿 + 禁止直推（当前双远程都是直推 main）；
- **仓库清卫生**：18 个报告 MD 归档到 `docs/archive/`，eval-report JSON 入 `.gitignore`；
- **E2E 补齐关键回归路径**：当前仅 7 个 E2E 用例，近期三次 critical（白屏/404/知识库空白）恰好都是 E2E 能拦住的 UI 集成层缺陷——各补一条冒烟用例。

### P2 — 企业级纵深（1 个月）

- **准确率在线度量**：评测集是离线的，生产环境需要"点踩率/自省触发率/拒答率"周报视图（数据已在 audit/feedback 表中，缺聚合看板）；
- **宽表评测集扩容**：核心数据源仅 10 用例，建议对齐主集分层扩到 50+；
- **知识库漂移检测**：已确认"实库维度取值变化不会自动同步知识库"——对低基数维度做定期取值快照比对，漂移时提醒管理员更新知识文档（保存后向量化自动完成）；
- **strict 全量化**：`tsconfig.strict.json` 目前是增量白名单，逐步扩到全前端。

### P3 — 战略项（按需）

- 单体拆分评估（问数引擎 vs 管理面）、读写分离、语义缓存持久化（当前进程内 Map 重启即失）、多 Agent 编排预研（与演进路线对齐）。

## 五、结语

这个项目的**能力建设曲线是健康的**——每次评估指出的短板下个版本都有系统性回应（评测、CI、弹性、自愈）。但本次实测暴露的问题性质不同：**不是能力缺失，而是纪律松弛**——门禁建好了却红着灯继续开发，说明书写着"零错误"而实际三档全红。企业级软件的分水岭恰恰在这里：**护栏存在且任何人不能例外**。P0 五项半天可清零，P1 的 pre-push 钩子和分支保护才是防止复发的关键。
