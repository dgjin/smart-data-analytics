## 二、亮点（值得肯定的工程实践）

### 2.1 七道质量门禁（业内少见）

`.husky/pre-push` 强制执行，红灯代码无法进入远程仓库：

1. tsc 主 tsconfig
2. tsc server strict
3. tsc 前端 strictNullChecks
4. OpenAPI 同步校验（`docs:check`）
5. 进程内状态巡检（`state:check`）
6. ESLint（error 级）
7. vitest 全量单测

这是多数团队做不到的纪律，属于业内前 10% 的工程化水平。

### 2.2 架构分层清晰

```
server/
├── routes/    # 30 个路由，纯 HTTP 层
├── query/     # 26 个 NL2SQL 核心（26 src : 27 test，测试超过源码）
├── llm/       # 8 个 LLM 客户端（熔断/重试/并发信号量/自适应超时）
├── infra/     # 16 个基础设施（db/stateStore/logger/monitoring）
└── auth/      # 鉴权 + 行级权限
```

路由层不直接拼 SQL、统一走 `executeSafeSql` 安全执行层——边界感很好。

### 2.3 安全实践扎实

- **275 处数据库调用**，密码用 scrypt + AES-256-GCM 加密落库
- 密钥硬编码扫描为 **0**
- 统一错误码体系（`errorCodes.test.ts` 强制扫描禁止裸 `res.status().json({error})`）
- LLM 韧性层：熔断器 + 指数退避重试 + 并发信号量 + 自适应超时

### 2.4 测试密度高

`server/query/` 模块 26 个源文件对应 27 个测试文件（>100%），1123 用例全过。

### 2.5 技术债务意识好

全项目 TODO/FIXME 仅 **5 处**，`@ts-ignore` / `@ts-nocheck` 为 **0**——团队有"不留烂摊子"的习惯。

## 三、问题与风险（按优先级排序）

### P0 — 超长文件与上帝组件（可维护性风险）

| 文件 | 行数 | 问题 |
|---|---|---|
| `src/components/query/QueryChat.tsx` | **1445** | **24 个 useState + 10 个 useEffect**，典型上帝组件 |
| `src/components/flexquery/FlexQueryBuilder.tsx` | 1404 | 同上 |
| `server/seedDataResources.ts` | 1323 | 种子数据应拆分为 JSON/SQL |
| `src/components/reports/ExecutiveReportCard.tsx` | 1083 | 报表组件过厚 |
| `server/routes/datasources.ts` | 970 | 路由层过厚，业务逻辑应下沉 |

**`QueryChat.tsx` 是最危险的单点**：24 个状态意味着状态组合爆炸（理论 2^24 种），任何改动都可能引发回归。

**建议拆分方向**：
- `useQueryChatState()` 自定义 Hook 收敛状态
- 按职责拆出 `ChatInput` / `MessageList` / `StreamHandler` / `SkillMenu` 子组件
- 目标：单文件 < 400 行

### P1 — 类型纪律松动（488 处 `any`）

`any` 集中分布 TOP5：

| 文件 | any 数 |
|---|---|
| `server/infra/db.ts` | 18 |
| `server/routes/query.ts` | 16 |
| `server/routes/fallbackApproval.ts` | 14 |
| `server/routes/metrics.ts` | 13 |
| `server/query/metrics.ts` | 12 |

虽然有三档 tsc strict，但 488 处 `any` 等于在类型安全网上戳了 488 个洞。

**建议**：
- 新增代码 ESLint 禁 `any`（`@typescript-eslint/no-explicit-any` error 级）
- 存量按文件清零（每周 2-3 个文件，一个季度可清完）

### P1 — 测试分布不均

| 模块 | src:test | 评价 |
|---|---|---|
| server/query | 26:27 | 优秀 |
| server/routes | **30:8** | **薄弱**——30 个路由仅 8 个测试 |
| server/infra | 16:9 | 中等 |
| src 组件 | 22 个测试 | 前端覆盖偏低 |

**路由层是集成风险最高的地方**（鉴权+限流+参数校验+错误码），30:8 的比例偏低。建议为路由层补契约测试（supertest）。

### P2 — console 直用残留（34 处）

虽有统一 `logger` 门面，仍有 34 处 `console.*` 散落在 `query.ts`、`abTest.ts`、前端组件中。生产环境这些日志无法分级、无法采集。建议 ESLint 加 `no-console` 规则（error 级，eval 脚本豁免）。

### P2 — 依赖版本滞后

| 依赖 | 当前 | 最新 | 风险 |
|---|---|---|---|
| `@types/node` | 22 | 26 | 类型定义滞后 |
| `express` | 4 | 5 | 主版本滞后 |
| `lucide-react` | 0.546 | 1.46 | 跨主版本 |
| `motion` | 12 | 13 | 主版本滞后 |

主版本滞后意味着安全补丁缺失风险。建议每季度做一次依赖升级窗口。

## 四、架构层面的两个观察

### 4.1 `server/routes/query.ts`（815 行）承担了过多编排职责

从 import 看，它依赖了 **28 个内部模块**——问数主链路的所有编排（六层防护、缓存、审计、追踪、SSE、计划模式、反馈闭环）都堆在一个文件里。

**建议**：引入应用服务层（Application Service）——`queryService.ts` 承接编排逻辑，路由只做 HTTP 适配。

### 4.2 `server/infra/db.ts`（926 行）同时是连接池 + 建表 + 种子 + 迁移

**建议拆分**：
- `db.ts`（连接池）
- `schema.ts`（DDL）
- `seed.ts`（种子）
- `migration.ts`（迁移）

单一职责后每个文件 < 300 行。

## 六、一句话总结

> 这是一套"工程纪律优秀、架构骨架健康，但存在局部肥胖（超长文件）和类型松弛（any 存量）"的企业级代码库。七道门禁和测试密度证明团队有质量意识；当前最大的风险不是"写得差"，而是**少数核心文件长得太大、类型网有洞**——这两件事都是可规划、可量化、可清零的债务，不涉及架构返工。整体处于"健康但需减脂"的状态。
