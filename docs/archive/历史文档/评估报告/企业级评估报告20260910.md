## 三、值得肯定：达到或超过业界水准的设计

### 3.1 安全纵深是全项目最硬的资产

- `server/query/sqlExecutor.ts` 实现三道防线：注释/字符串剥离 + 危险关键字词表 → `node-sql-parser` AST 语句类型复核 → 行级权限**递归注入 CTE/UNION/子查询**且 fail-closed；外加 EXPLAIN 预估扫描量拦截（防 LLM 生成大查询拖垮业务库）。这套设计在企业 NL2SQL 场景中达到教科书级。
- 场景化连接池配额（交互 10 / 分析链 5 / 导出 2）确保大导出不挤占交互问数，有实测证据（导出池打满时交互 32ms 零排队）。
- JWT + 每次请求回查 users 表（禁用/改角色即时生效）+ 生产缺 `JWT_SECRET` fail-fast + 数据源凭据 AES-256-GCM 加密 + 密码 scrypt+pepper。

### 3.2 AI 工程闭环完整

`server/query/queryGuard.ts` 注入检测（L1-L4）→ 语义缓存 → 自纠错 → Fallback 三层自救（规则修正/精简 schema/复用审核样例）→ 失败采集 → 人工审核队列 → Few-Shot 注入的自学习闭环（v0.9.44-46），配合 A/B 实验框架与主动学习排序，构成完整的"对抗训练"机制。

### 3.3 质量门禁体系扎实

pre-push 7 道 + CI 双作业 + `state:check`（AST 扫描拦截白名单外进程内状态）+ OpenAPI 契约校验（144 端点）+ strictNullChecks 全量开启（前端 src/** 全覆盖）。strictNullChecks 全量开启在同类项目中极少见，是类型纪律的硬约束。

### 3.4 可观测性运维化

13 条告警规则（应用存活/MySQL/Redis/查询成功率/P95/缓存命中/Fallback 率/内存/磁盘/Prometheus 基数与规则评估/抓取耗时/Alertmanager）配合 Grafana 4 看板与 Alertmanager 路由，属于真正的生产级配置。

### 3.5 文档资产丰富且诚实

部署手册、多实例指南、容量压测报告、评测标注规范、实操手册、培训材料齐备；历史评估报告敢于暴露自身短板（R1-R7 全部销账并有提交哈希可查）。

## 四、本次实测发现的问题（按优先级）

> 本轮无红灯级问题。以下均为改进项，按企业级交付影响度分级。

### P1 — 建议 2 周内处理

#### P1-1 依赖安全：7 个漏洞（2 high），且 CI 无依赖扫描门禁

`npm audit --omit=dev` 实测结果：

| 依赖链 | 严重度 | 问题 | 修复路径 |
|--------|:---:|------|----------|
| `pptxgenjs → image-size` | high | ICNS/JXL/HEIF 解析无限循环 DoS | 跟踪上游修复版本升级 |
| `express → qs` | moderate | 数组上限绕过 / isBuffer DoS | `npm audit fix` 即可（非破坏性） |
| `exceljs → uuid` | moderate | v3/v5/v6 缓冲区边界检查缺失 | 评估上游升级（不可盲目 downgrade） |

pptxgenjs 可达性分析：`server/report/reportExport.ts:182` 的 `addImage({ data: chart.imageBase64 })` 中 base64 来自前端请求体（认证用户可控），理论上认证用户可构造恶意图片载荷触发挂起。**缓解成本极低**：`addImage` 前对图片做 PNG/JPEG 魔数白名单校验即可阻断。

同时 CI 无 `npm audit` 门禁、无 dependabot/renovate 自动依赖更新。

#### P1-2 无优雅停机

全仓库无 `SIGTERM/SIGINT/server.close` 处理（grep 验证零命中）。Docker/PM2 滚动更新、重启时会硬断在途 SSE 流与问数请求。缓解资产已有（任务心跳孤儿恢复 90s、SSE 重放缓冲），但缺口仍在。

建议实现 drain 序列：停止接收新请求 → `httpServer.close()` → task worker 停止领取 → 连接池关闭 → 超时强杀。

#### P1-3 健康检查语义不足 + /metrics 默认开放

- `server.ts:190` 的 `/api/health` 恒返回 `ok`，不探测 MySQL/Redis/LLM——编排器无法摘除"进程活着但依赖死了"的坏实例；且无 liveness/readiness 区分。
- `/metrics` 默认无鉴权（`METRICS_TOKEN` 为可选保护，见 `server/infra/monitoring.ts:137-141`）。

建议：新增 `/api/health/ready`（DB + Redis ping，失败返回 503）与 `/api/health/live`（浅检查）分级；`/metrics` 默认加锁或文档明确要求仅内网绑定。

#### P1-4 E2E 未进 CI，且注释与事实不符

pre-push 注释宣称"E2E 由 CI 承担"，实际 `.github/workflows/ci.yml` 不跑 Playwright（10 个用例 3 个 spec 仅本地可跑）。这是上次报告 R6"文档声明与实测不符"的同类苗头，应在流程层面根治。

建议：CI 增加 e2e 作业（nightly schedule 起步，或 PR 触发最小 smoke 集 + MySQL service 容器）。

#### P1-5 版本与文档追溯断链

代码已含 v0.9.44/45/46（Fallback 对抗训练 / 主动学习 / A/B Test），但：

- `package.json` 版本停留在 `0.9.43`；
- `docs/更新日志.md` 最新条目为 v0.9.43（v0.9.44-46 零命中）；
- `docs/系统功能说明书.md` 零处提及 v0.9.44-46；
- 三个版本的功能仅存在于 `docs/FALLBACK_ABTEST_ANALYTICS_V0.9.46.md` 独立文档。

用户端入口文档滞后 3 个版本，追溯性受损。建议补齐更新日志与说明书变更记录（数据以实测为准），并明确版本发布流程（功能合并即同步版本号）。

| # | 问题 | 建议 |

## 六、结论

该项目从 v0.5.3 的"原型达标"到如今 v0.9.46："**门禁全绿、strict 全量、双 CI 作业、安全八层纵深、AI 对抗训练闭环**"——工程素养已高于一般企业项目水准，历史两轮评估的红灯问题（R1-R7）全部销账且本轮**未发现任何红灯级问题**。

剩余缺口集中在两点：**运维韧性**（优雅停机/健康检查分级/依赖安全）与**文档追溯一致性**（版本滞后 + E2E 注释失实）。这两类问题不影响功能正确性，但正是"准生产"与"企业级"之间的最后一段路。建议按第五章行动清单顺序收口，预计 2-4 周即可完整达标。
