## 一、总体评价

**结论先行：这是一个工程完成度显著高于典型 Demo 的准生产级系统，安全纵深与反馈闭环设计达到了商用产品水准，但在评测规模、高可用架构、准确率在线度量三个方面与真正的企业级落地还有明确差距。**

对标业界（Databricks Genie、Snowflake Cortex Analyst、阿里析言 GBI、Vanna、DB-GPT），本项目的**架构理念是先进的**——四契约输出（拒答/澄清/自省/生成）、双阶段真实数据回喂、行级权限 AST 强制注入，这三点甚至优于多数开源方案。**短板集中在"规模化验证"环节**。

## 二、亮点：达到或超过业界水准的设计

### 1. 四契约输出——诚实性设计优于多数商用产品

`server/liveQuery.ts` 中的拒答契约要求统一话术模板、禁止强行编造 SQL；自省契约借鉴 Vanna 的 intermediate_sql（探查 DISTINCT 取值回喂、限一轮防递归）；澄清契约仅首次首候选接受，避免重试环节死循环。**"宁可拒答不可胡答"是企业级 ChatBI 的第一信任基石**，很多产品到今天都没做到。

### 2. 行级权限 AST 强制注入（fail-closed）

`server/sqlExecutor.ts` 将 `FROM t` 重写为 `FROM (SELECT * FROM t WHERE 谓词) AS t`，递归覆盖子查询/UNION/JOIN，注入失败直接拒绝执行。这比"在 Prompt 里告诉 LLM 别查某些数据"的伪安全方案高出一个量级，与 Snowflake 行访问策略的思路等价。

### 3. 双阶段真实数据回喂——从机制上杜绝数据幻觉

阶段一只产 SQL 不产数据，阶段二用真实 rows（15 行采样+列统计）生成解读；LLM 失败时 `buildFallbackAnalysis` 基于真实列统计做规则化降级。**解读永远有真实数据背书**，这是对"AI 编数字"这一 ChatBI 最大信任杀手的正面回答。

### 4. 反馈闭环工程化落地

点赞 → auto_train 入 sql_examples 团队库；点踩 → 反面教材注入 Prompt（只给错误案例不给错误 SQL，防止污染）；个人对话沉淀按 userId+dataSourceId 隔离。这是 DAIL-SQL 论文思想的完整工程化，形成了**数据飞轮的雏形**。

### 5. 可观测性超配

11 类 trace 步骤（linking/knowledge/introspection/sql_gen/execution/analysis 等）+ traceId 回放 + 审计十态（SUCCESS/CACHE/FALLBACK/ERROR/CLARIFY/REFUSED/DENIED_INPUT/DENIED_AUTH/DENIED_RATE/DENIED_SWITCH）+ 慢查询审计（>3s 或 >10 万行）+ token 用量按用户/引擎/模型三维统计。出了问题能在时间线上精确定位到哪一步，**这是运维接受度的关键**。

## 三、关键差距与风险（按严重度排序）

### 🔴 风险 1：评测体系规模不足以支撑生产承诺

- **现状**：`server/eval/evalCases.json` 仅 **19 条用例**（16 正常 + 3 差评回流）。
- **问题**：企业客户会问"准确率多少？"——19 条样本的执行准确率置信区间宽到没有统计意义。Spider/BIRD 等学术基准动辄千条；Cortex Analyst 内部评测集是持续增长的数百条业务问题。
- **连带风险**：Prompt 每次调整（项目迭代非常频繁，8 天 27 个版本）都可能引入准确率回退，19 条用例根本测不出来。

### 🔴 风险 2：无 CI/CD 门禁，回归靠人工自觉

项目无 `.github/workflows`，569 条单测和评测集都没有强制运行的关口。以当前的迭代速度（单日多版本），**没有自动化门禁等于在高速上不系安全带**。

### 🟠 风险 3：高可用与横向扩展能力不足

- LLM 调用**无重试、无熔断、无排队降级**（`server/llmClient.ts` 失败直接抛异常）；Ollama 超时 180s，一个慢请求占住并发槽。
- 数据源连接池仅 **max=3**，主库 connectionLimit=10 —— 30 人以上团队并发使用会排队。
- 语义缓存、表 embedding 缓存默认进程内存，多实例部署时命中率坍塌（虽有 Redis StateStore 抽象，但缓存未全部外置）。
- 单体架构 + SSE 长连接，无负载均衡粘性方案说明。

### 🟠 风险 4："语义缓存"名不副实

`server/queryCache.ts` 实际是**归一化后精确匹配**（小写+去标点），不是 embedding 相似度。"今年各机构余额"和"2026年每个机构的余额"不会命中同一缓存。命名会误导使用方预期，实际命中率也远低于真语义缓存。

### 🟠 风险 5：超宽表场景的列级裁剪缺失

目标场景有 **204 列宽表**，但 schemaLinking 表摘要只取**前 20 列**，且 linking 只做表级不做列级。对宽表，LLM 收到的 schema 上下文要么截断（漏字段致错答）要么全量（token 爆炸）。这与"1139 万行 204 列财务宽表"的实际数据规模是矛盾的。

### 🟡 风险 6：企业权限模型偏薄

三级 RBAC（ADMIN/ANALYST/VIEWER）+ 表/列/行三级 scope 对中小团队够用，但企业落地通常需要：组织架构/部门维度授权、数据域（Domain）划分、权限申请审批流、与 AD/LDAP/OAuth 统一身份对接。目前均缺失。

### 🟡 风险 7：语义层缺治理流程

指标层（`server/metrics.ts`）有定义结构（name/aliases/expr/filters），但**指标口径谁提议、谁审批、如何版本化、冲突如何仲裁**没有流程。企业里"口径之争"是 BI 项目失败的头号原因，语义层没有治理等于没有权威性。

### 🟡 风险 8：工程质量缺口

- `strictNullChecks` 未开启——NL2SQL 链路大量处理 LLM 返回的不确定结构，空值缺陷风险偏高。
- 无重放攻击防护、无导出水印/脱敏展示等数据防泄漏（DLP）措施——审计能追责但不能阻止截屏级泄露。

## 四、改进建议路线图

### P0（上生产前必须，约 2-4 周）

| # | 建议 | 具体做法 |
|---|------|---------|
| 1 | **评测集扩容至 100+ 条** | 按难度分层（单表聚合/多表 JOIN/时间对比/嵌套子查询/需澄清/应拒答六类），从真实用户问题 + query_trace 里挖掘；每次点踩自动生成候选评测用例进入待标注队列 |
| 2 | **建 CI 门禁** | GitHub Actions/Gitee Go：`tsc + eslint + vitest + 评测集执行准确率阈值检查`（如 <85% 阻断合并），Prompt 文件变更强制触发全量评测 |
| 3 | **LLM 调用韧性** | 指数退避重试（1-2 次）+ 引擎级熔断（Ollama 连续失败自动切 Qwen）+ 并发排队上限，超时从 180s 收敛到分位数驱动的值 |
| 4 | **在线准确率度量** | 建立生产北极星指标：`点赞率、点踩率、澄清率、拒答率、自纠错触发率、缓存命中率` 周报看板——没有在线度量，离线评测再好也不知道真实水位 |

### P1（规模化推广前，约 1-2 月）

| # | 建议 | 具体做法 |
|---|------|---------|
| 5 | **列级 Schema Linking** | 对 >50 列宽表，先表级圈定再做列级相关性排序（embedding），只注入 top-N 相关列 + 被指标层引用的列，解决 204 列宽表截断问题 |
| 6 | **真语义缓存** | 归一化精确匹配保留为 L1，增加 embedding 相似度 ≥0.95 的 L2 语义命中（结果标注"来自相似问题缓存"允许用户刷新）；缓存全部外置 Redis |
| 7 | **开启 Self-Consistency 默认值** | SELF_CORRECT_CANDIDATES 默认从 1 → 3（复杂问题分档触发），配合评测集验证收益；这是准确率最便宜的提升手段 |
| 8 | **指标层治理流程** | 指标提议→ADMIN 审批→生效版本化（沿用技能库已有的"分享-审核流"模式复制到指标层即可，改造成本低） |
| 9 | **连接池与容量规划** | 数据源池 max=3 → 按并发用户数公式化配置；补充压测报告（20/50/100 并发下 P95 延迟） |
| 10 | **strictNullChecks 分模块开启** | 先 server/ 新文件强制，存量渐进迁移 |

### P2（企业级深化，3 个月+）

| # | 建议 |
|---|------|
| 11 | 统一身份对接（OAuth2/LDAP）+ 组织架构维度授权 + 权限申请审批流 |
| 12 | DLP：查询结果脱敏展示规则（手机号/身份证掩码）、导出水印、下载审批 |
| 13 | 多实例部署方案：SSE 粘性会话或改用轮询降级、缓存全外置、无状态化验证 |
| 14 | 成本治理：token 预算告警、按部门配额、贵模型自动降级策略 |
| 15 | 语义层升级为独立资产：考虑对齐 dbt Semantic Layer / MDX 思路，让指标定义可被报表/看板/问数三端共享消费 |

## 五、落地性结论

**当前状态适合的落地路径：部门级试点（20-50 人，ADMIN 深度陪跑）→ 补齐 P0 → 事业部级推广。**

三个判断：

1. **信任基础已具备**：拒答不胡答、真实数据回喂、全链路可回放——这三点决定用户"敢不敢信"，本项目做得比多数同类产品好。试点期用户信任崩塌的风险较低。

2. **规模化验证是当前瓶颈**：19 条评测集 + 无 CI 意味着"目前的准确率是体感而非度量"。这不影响试点，但**在拿到 100+ 评测集的量化准确率之前，不建议对外承诺 SLA 或大范围推广**。

3. **架构天花板可控**：单体 + Redis 抽象的设计为后续拆分留了缝，不需要推倒重来；真正需要前置投入的是评测资产和治理流程——这两样是花钱买不来、只能靠业务积累的，越早启动越好。

一句话总结：**方法论一流、安全一流、工程完成度良好，差的是"用数据证明自己"的评测体系和"扛住规模"的韧性设计——这两块补上，就是一个可以对外输出的企业级产品。**
