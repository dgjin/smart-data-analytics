## 二、分阶段详细记录

### 阶段 0：项目启动与环境搭建（提问 1-7）

**关键需求**：
- 本地部署项目（MySQL + Ollama 环境）
- 整体评估项目并给出修改建议

**产出**：完成首次本地化部署，建立「评估 → 分级（P0-P3）→ 修复」的工作模式，该模式贯穿项目全程。

**经验**：项目初期即确立"先评估、分级、再动手"的节奏，避免无优先级的大杂烩式修改。

### 阶段 1：权限体系与安全基座（提问 8-17）

**关键需求**：
- 增加权鉴功能，设置管理员负责系统配置管理
- 曾讨论后端迁移 Spring Boot，提供过数据库凭据（已脱敏），**最终决策：暂不迁移，保留 Express 技术栈**
- 数据源表/字段级纳管：管理员配置哪些表和字段允许纳入智能问数范围
- 导入数据库时，根据用户选择的问数范围**自动推导指标和维度**，管理员可动态维护
- 按附件设计**八层纵深安全防御**

**核心产出**：
- RBAC 三角色（管理员/分析师/只读用户）+ 首登强制改密 + scrypt 密码加固
- Schema 白名单机制（未授权表不出现在 prompt，从源头防越权）
- 八层防御链：输入防护 → JWT 鉴权 → 限流配额 → Schema 白名单 → 敏感列过滤 → 只读执行 → 审计落账 → 可观测日志

**关键决策**：Express 保留不重写——避免大规模重写风险，把精力投向 AI 能力建设。

### 阶段 2：真实数据链路改造（提问 18-24）

**关键需求**：
- 问数提示和默认推荐内容必须基于**真实数据查询**，不用固定模板
- 修复 visitpro 库表提取不完整/不正确问题
- 结果表头中文化、问题可再次编辑和复制
- 表结构仅管理员可见、图表气泡提示中文化

**核心产出**：双阶段 NL2SQL 架构确立——阶段一只生成 SQL（不接触数据），阶段二基于真实查询结果生成解读。

**经验教训（演示数据陷阱）**：此阶段确立了项目第一原则——**真库真数**：演示数据曾导致"AI 编数字"的信任危机，此后所有链路强制真实数据背书。

### 阶段 4：模型引擎建设（提问 50-58、81、97-98、103、156-161）

**演进路线**：

```
Gemini（初期 Demo 遗留字样清理）
   → Qwen3.8-max 云端引擎（API Key 已脱敏）+ 用户自选模型功能
   → 全本地 Ollama（数据零出域合规要求驱动）
```

**关键教训**：
1. **推理模型禁用**：曾尝试 deepseek-r1:8b 做阶段二解读，思考链过长必超时——解读场景禁用纯推理模型

3. **内存要求**：27B 模型需 ≥64GB 统一内存，实测推理约 47s/复杂查询

**关键需求**：默认 27B 主模型；阶段二解读走快速模型路由；金额单位可选（亿/百万/万/元）；小数默认两位。

## 三、关键技术决策清单

| # | 决策 | 结论 | 理由与教训 |
|---|------|------|-----------|
| 1 | 真库真数 | 一切分析基于真实数据，禁止演示数据托底 | 演示数据曾致信任危机；不相关提问应拒答而非编造 |
| 2 | 配置层优先 | 语义/口径缺陷优先改配置（指标库/样例库），不打代码补丁 | 更快、更安全、可回滚、可测试 |
| 3 | 降级不撒谎 | LLM 失败时用真实列统计的规则化解读兜底 | 通用文案破坏用户信任 |
| 4 | 全本地 AI 引擎 | Ollama 本地部署，数据零出域 | 金融合规红线；接口兼容 OpenAI 协议可切公司平台 |
| 5 | 复杂度分档路由 | 简单走 8b 快速模型，复杂强制 27b 主模型 | 同源多候选无法纠正系统性偏差，复杂问题必须主模型保口径 |
| 6 | 推理模型禁用 | 解读/生成链路禁用纯推理模型 | 思考链过长必超时（实测教训） |
| 7 | 四契约输出 | 生成/澄清/自省/拒答 | 宁可拒答不可胡答，金融场景信任基石 |
| 8 | 行级权限 AST 注入 | 执行层强制注入，fail-closed | 比 prompt 约束安全量级更高，LLM 无法绕过 |
| 9 | 口径治理四层防线 | 知识库→指标库→样例库→红线硬编码 | 39204 亿事故后建立，同类错误归零 |
| 10 | 双阶段架构 | 阶段一不接触数据，阶段二不接触 Schema | 从机制上杜绝"AI 编数字" |
| 11 | 数据源名注入 prompt | 告知 LLM 数据源名是系统名称非数据值 | 根治库名被误判为 WHERE 过滤值（wt01） |
| 12 | 评测数值容差 | max(0.005, 相对 1e-9) | 吸收 ROUND(x,2) 假阴性，口径错误仍被抓 |
| 13 | 反例不给错误 SQL | 只给错误表名特征，防照抄污染 | 完整错误 SQL 会被 LLM 模仿 |
| 14 | Git 协作铁律 | 改前拉取、完提交、双远程同步 | 写入项目配置的强制要求 |

## 四、重大事故与修复案例

### 案例 1：39204 亿口径偏差事故（金额虚增近 17 倍）

- **现象**：累计投放金额查询结果虚增近 17 倍
- **根因**：快照型宽表跨期累加 + 未锁定核算版 + 未按业务编号去重
- **修复**：催生口径治理四层防线（L2 指标库补锁 + L3 样例修正 + L4 红线硬编码：快照期 MAX 子查询/版本过滤/COUNT DISTINCT/表路由）
- **教训**：宽表快照结构必须锁定快照期；同类错误修复后归零

### 案例 2：YJFL 列名幻觉事故（8b 模型能力边界）

- **现象**：「长龄业务笔数及占比」查询返回空，归因为`YJFL='收购处置类'`未匹配
- **根因**：D5 评测期间临时切换 8b 模型后未切回，8b 幻觉编造不存在的列名（正确应为"是否长龄"标志列）
- **修复**：切回 27b 主模型，查询验证通过（1824/3212，占比 56.79%，四红线全命中）
- **教训**：① 8b 模型不可用于生产 SQL 生成；② 临时切换模型必须有切回检查点；③ D5 prompt 变更本身无副作用，先怀疑环境变更再怀疑代码

### 案例 3：评测首轮 20% 假阴性

- **现象**：宽表评测首轮准确率仅 20%
- **根因**：评测器用字符串等值比较，系统生成的 `ROUND(x,2)` 与 golden SQL 全精度结果被判不等
- **修复**：数值容差比较 + generatedSql 捕获字段补齐 + 行规范化排序
- **教训**：评测工具本身的缺陷会制造"系统性假失败"，先校验评测器再归因模型

### 案例 4：package.json 尾逗号启动失败

- **现象**：v0.8.0 发布后启动报 `ERR_INVALID_PACKAGE_CONFIG`
- **根因**：版本号修改时 JSON 尾逗号缺失
- **教训**：配置文件修改后立即 `json.load` 校验再重启

### 案例 5：查询超时连锁治理

- **现象**：复杂追问超时 → 查询锁死 → 无法再次发起
- **治理**：并发槽 token 化释放 → LLM 韧性三件套 → 复杂度分档路由 → v0.8.1 根治
- **教训**：超时问题要分三层治——资源释放、调用韧性、路由分流

## 五、可复用方法论

1. **评估驱动开发**：每一轮大改前先出评估报告（P0-P3 分级），用户批准后执行，执行后回归验证
2. **评测门禁化**：准确率不是汇报数字，而是 CI 阻断条件（`--min-accuracy`）；差评自动回流评测集
3. **口径资产化**：口径不靠 LLM 自觉，靠指标库/样例库/红线三层资产锁定
4. **四红线思维**：凡快照型宽表，先问"锁定期了吗、防重了吗、去重了吗、走对表了吗"
5. **模型分工观**：主模型保正确性、快速模型保响应、推理模型不上生产链路
6. **文档同步机制**：功能说明书每次更新同步；手册记录真实执行记录（含数字证据）
7. **参赛叙事方法**：技术系统要翻译成赛道语言——NL2SQL 工具 → Data Agent 智能体；先论证赛道归属，再展示能力
