## 1. 背景与目标

### 1.1 现状

业务本体已完成两期落地，具备「登记 → 命中 → 软注入」闭环：

- **M1（v0.9.110）**：实体/别名 + 表列绑定 + 值域释义（`ontology_entities` / `ontology_bindings` / `ontology_value_notes`）。
- **M2（v0.9.111）**：已登记 JOIN 路径 + 业务层级（`ontology_relations` / `ontology_hierarchies`），版本快照统一落 `ontology_versions`。
- **配套（v0.9.112 / v0.9.113）**：智能预填草稿、管理员全局开关、写库事务（`withTransaction`）、zod 输入校验。

但本体资产一旦登记，与物理 Schema 之间**没有任何持续校验机制**，存在三类治理缺口：

| 缺口 | 具体表现 | 影响 |
|---|---|---|
| 软校验缺失 | 表/列重命名或删除后，绑定、关系、层级仍指向旧名字，无告警 | 提示词注入失效片段，命中率静默下降 |
| 漂移未联动 | `driftDetector` 只监测枚举取值变化，未覆盖结构变化，也未关联本体资产 | 漂移事件与受影响资产脱节，运维需人工比对 |
| 演化不闭环 | `status` 已预留 `PENDING/REJECTED`（`server/query/ontology.ts:191` 注释：由后续 M3 治理流程驱动）但未启用；无影响面分析；失败样本未回流 | 多人协作无审批，误停用无人拦，资产只增不治 |

### 1.2 目标

1. **可自检**：任一数据源的本体资产可一键校验，按「正常 / 待复核 / 失效」三级呈现，保存不阻断（软约束）。
2. **可联动**：物理 Schema 结构或取值漂移后，受影响的本体资产自动标记待复核，并与漂移事件互相跳转。
3. **可演化**：启用提议-审批状态机，提供影响面分析与失败样本回流，使本体从「人工一次性搭建」转为「持续演进」。

### 1.3 边界（不做的事）

- 不引入图数据库（P3 触发条件另行评估：跨源联邦或单源表数 > 100）。
- 不引入 OWL/RDF 形式化本体，不改变「软注入 + 执行层白名单兜底」的既有架构。
- 不做 LLM 自动审批或自动改写生产本体；自动能力仅限「生成 PENDING 候选草稿，人工采纳」。
- 不新增第五条资产类型的表结构（复用现有六张表 + 一张健康度表）。

## 2. 现状盘点（可复用资产）

| 能力 | 位置 | 复用方式 |
|---|---|---|
| 版本快照与回滚 | `ontology_versions` + `recordVersion`（CREATE/UPDATE/DELETE/RESTORE） | 审批通过/驳回同样写快照，动作扩展 `APPROVE` / `REJECT` |
| 状态字段预留 | 五张资产表 `status ENUM('ACTIVE','DISABLED','PENDING','REJECTED')` | 直接启用 PENDING/REJECTED 语义，零 schema 变更 |
| 枚举漂移检测 | `server/driftDetector.ts`：`diffValues`、`discoverEnumColumns`、`scanDataSource`、`startDriftSweeper`（默认 24h） | M3.2 在扫描末尾追加本体引用比对 |
| 漂移事件存储 | `kb_drift_watch` / `kb_drift_events`（`server/infra/schema.ts:706-726`） | 事件行扩展受影响资产数（返回时实时计算，不改表） |
| 血缘 stale 模式 | `server/lineage/graph.ts`：`edge.status='stale'`、`stats.staleEdges` | 健康度模型直接对齐该分级语义 |
| 指标审批流 | `server/query/metrics.ts`：approve / reject / repropose + `recordVersion` | 状态机与路由形态照搬，降低认知成本 |
| 失败样本 | `query_feedback`（赞踩/纠错）、`feedback_entries`、fallback 审计 | M3.3 候选提议的数据源 |
| 智能预填 | `server/query/ontologyAutoBuild.ts`（v0.9.112 草稿结构） | M3.3 候选提议复用 `OntologyDraft` 形状 |
| 事务与校验 | `withTransaction`（P1-1）、`server/infra/validate.ts`（zod，P0-2） | 审批多表写入走事务；新接口走 zod schema |

## 3. 触发条件与前置核查

评估报告给出的 M3 触发条件：**至少 1 个数据源登记完整四类资产，join 类问题占比可见**。实施前执行：

```sql
-- 资产规模（替换 :ds）
SELECT 'entity' AS kind, COUNT(*) c FROM ontology_entities WHERE data_source_id = :ds
UNION ALL SELECT 'binding', COUNT(*) FROM ontology_bindings WHERE data_source_id = :ds
UNION ALL SELECT 'value_note', COUNT(*) FROM ontology_value_notes WHERE data_source_id = :ds
UNION ALL SELECT 'relation', COUNT(*) FROM ontology_relations WHERE data_source_id = :ds
UNION ALL SELECT 'hierarchy', COUNT(*) FROM ontology_hierarchies WHERE data_source_id = :ds;

-- 命中情况（近 30 天）
SELECT COUNT(*) FROM query_trace WHERE created_at >= NOW() - INTERVAL 30 DAY;
```

- **达标**：四类资产齐全 → M3.1 → M3.2 → M3.3 顺序推进。
- **未达标**：M3.1（软校验）仍可先行——资产越少，校验器越容易验收；M3.2/M3.3 延后。

## 4. 总体设计

### 4.1 软校验（M3.1）

**定位**：只提示、不阻断。保存路径不变，校验结果仅用于展示与筛选。

**校验规则矩阵**：

| 规则 | 对象 | 判定 | 分级 |
|---|---|---|---|
| R1 表存在 | `bindings` / `relations` / `hierarchies` | `table_name` 不在当前 Schema 表集合 | **BROKEN** |
| R2 列存在 | `bindings.column_name`、`relations.from_columns/to_columns`、`hierarchies.levels_json` | 列不在该表列集合（空列=表级绑定，跳过） | **BROKEN** |
| R3 值域存在 | `value_notes.value_code` | 该列当前取值集合不含此 code（按需 `SELECT DISTINCT ... LIMIT 200` 采样） | **STALE** |
| R4 关系类型可比较 | `relations` | 两侧关联列类型不属于同一可比族（数值/字符串/时间） | **STALE** |
| R5 基数抽样一致 | `relations` | 声明 `1:1`/`N:1` 与实际抽样相反（观察期，默认关闭） | **STALE** |

**数据模型（唯一新增表）**：

```sql
CREATE TABLE IF NOT EXISTS ontology_asset_health (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  data_source_id VARCHAR(64) NOT NULL,
  asset_type ENUM('entity','binding','value_note','relation','hierarchy') NOT NULL,
  asset_id BIGINT NOT NULL,
  level ENUM('OK','STALE','BROKEN') NOT NULL DEFAULT 'OK',
  reason VARCHAR(300) NOT NULL DEFAULT '',
  checked_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uniq_ontology_health (asset_type, asset_id),
  INDEX idx_ontology_health_ds_level (data_source_id, level)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
```

**校验器**（`server/query/ontologyValidation.ts`）：

- `collectReferences(asset)`：纯函数，抽出资产引用的 `{table, column}[]`，便于单测与漂移复用。
- `classifyAsset(refs, schema)`：纯函数，按规则矩阵返回 `{level, reason}`。
- `validateDataSource(dataSourceId)`：读一次 Schema → 逐资产分类 → 事务内 upsert 健康表（先删后插，保证不残留）。
- 依赖方向：只读 Schema 与本体表，不触碰查询链路，零注入影响。

**API**：

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/ontology/health?dataSourceId=` | ADMIN | 汇总（OK/STALE/BROKEN 计数）+ 问题明细 |
| POST | `/api/ontology/validate` | ADMIN | 触发一次全量校验，body `{ dataSourceId }`（zod） |

**前端**（`OntologyPanel` 顶部）：

- 健康度条：三段计数 + 「一键校验」按钮（loading 复用现有按钮规范）。
- 四个子页签行内徽标：`BROKEN` 红点 / `STALE` 琥珀点，hover 显示 `reason`。
- 筛选开关「仅看问题资产」，默认关闭。

### 4.2 漂移联动（M3.2）

**触发点**（三条，均复用同一校验器）：

1. `startDriftSweeper` 周期扫描末尾，对发生结构或取值变化的库追加 `validateDataSource`。
2. 数据源 Schema 刷新成功后（`POST /api/datasources/:id/refresh` 与 autoConfig 落库路径）异步触发。
3. 管理端手动「一键校验」。

**事件联动**：

- `GET /api/ontology/drift-events` 包装现有漂移事件列表，为每条事件实时计算关联资产数（按 `data_source_id` + 事件涉及的表/列匹配健康表）。
- 前端漂移事件行增加「影响本体资产 N 项」链接，跳转 `OntologyPanel?filter=problem&table=xxx`。
- 不新增漂移表字段，避免历史事件回填成本。

**失败降级**：Schema 读取失败时校验整体跳过并在健康条显示「最近校验失败（原因）」，不写健康表，避免把瞬时故障记录成 BROKEN。

### 4.3 演化闭环（M3.3）

**状态机**（五类资产共用一个模型）：

```
(未登记) --提议--> PENDING --审批--> ACTIVE --停用--> DISABLED
                     |                   ^                |
                     +--驳回--> REJECTED |                |
                              |          +------启用------+
                              +--重新提议--> PENDING
```

- ADMIN 直建默认 `ACTIVE`（保持现状，不改变单人运维体验）。
- `ONTOLOGY_APPROVAL_ENABLED=1` 时，ANALYST 写入落 `PENDING`；未开启时 ANALYST 写入直接 `ACTIVE`（与现状一致，避免默认流程变重）。
- 审批通过/驳回复用 `recordVersion`，`ontology_versions.action` 扩展 `'APPROVE'` / `'REJECT'`。

**影响面分析**：

- `GET /api/ontology/impact?assetType=&id=` 返回引用清单：停用实体 → 受影响绑定/关系/层级数量；停用关系 → 引用该路径的层级。
- 前端在「停用 / 删除」确认弹窗内展示清单（只读，不可跳过），避免误停用。

**失败样本回流**：

- 数据源：`query_feedback` 纠错记录 + fallback 失败审计，按「同一数据源 + 近 30 天 + 同一表/术语反复出现」聚合。
- 产出：候选提议（`PENDING`）写入对应资产表，`created_by='system:proposal'`，`description` 标注来源与样本数。
- 入口：`OntologyPanel` 新增「候选提议」抽屉，支持采纳（补全必填项 → `PENDING`/`ACTIVE`）与忽略（记录忽略时间，不重复提示）。
- 复用 `OntologyDraft` 形状（`ontologyAutoBuild.ts`），候选提议与智能预填共用前端表单。

**API 汇总**：

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/api/ontology/:assetType/:id/approve` | ADMIN | PENDING → ACTIVE |
| POST | `/api/ontology/:assetType/:id/reject` | ADMIN | PENDING → REJECTED |
| POST | `/api/ontology/:assetType/:id/repropose` | ADMIN | REJECTED → PENDING |
| GET | `/api/ontology/impact` | ADMIN | 影响面清单 |
| GET | `/api/ontology/proposals` | ADMIN | 候选提议列表 |
| POST | `/api/ontology/proposals/:id/adopt` | ADMIN | 采纳（写资产 + 快照） |
| POST | `/api/ontology/proposals/:id/ignore` | ADMIN | 忽略 |

`assetType` 取值：`entity` / `relation` / `hierarchy`（值域释义与绑定随实体审批，不单独设审批）。

## 5. 分期实施计划

| 期次 | 内容 | 交付物 | 工时 |
|---|---|---|---|
| **M3.1** 软校验 | 健康表 + 校验器 + 两个 API + 健康条/徽标/筛选 | `ontologyValidation.ts` + 单测；路由测试；前端组件测试 | 2-3 人日 |
| **M3.2** 漂移联动 | sweeper 挂钩 + 事件关联计数 + 跳转 | `driftDetector` 扩展 + 测试 | 1.5-2 人日 |
| **M3.3** 演化闭环 | 状态机 + 审批 API + 影响面 + 候选提议 | `ontologyGovernance.ts` + 审批/提议测试；前端抽屉 | 3-4 人日 |
| 合计 | | | **6.5-9 人日**（与评估报告 5-8 人日基本一致） |

**顺序理由**：M3.1 产出健康表与校验器，M3.2 直接复用；M3.3 的审批与影响面独立，但建议在 M3.1 之后实施，使审批弹窗能展示健康度。

## 6. 验收标准

### 6.1 测试

- **单测**：`collectReferences`（四类资产 × 边界）、`classifyAsset` 规则矩阵（R1-R5 各正反例）、状态机合法/非法迁移。
- **路由测试**：`GET /health`、`POST /validate`、审批三接口、`impact`、`proposals`；权限（ANALYST 403）。

- **事务**：审批写入 + 快照在同一事务内，异常回滚（复用 P1-1 的 `withTransaction` 测试模式）。

## 7. 风险与回退

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 校验噪声（误报 BROKEN） | 中 | 管理员失去信任 | 只做结构/取值事实校验；R4/R5 默认关闭，观察期后再开 |
| 校验成本高（DISTINCT 全表） | 中 | 校验超时 | 每列 `LIMIT 200` 采样；单次校验 3s 超时即跳过并标记 STALE |
| 漂移联动误报 | 低 | 资产被错误标记 | Schema 读取失败时不写健康表；结构比对以 information_schema 为准 |
| 审批流增加运维负担 | 中 | 资产停滞在 PENDING | `ONTOLOGY_APPROVAL_ENABLED` 默认 0（直建 ACTIVE），按需开启 |
| 候选提议泛滥 | 中 | 管理端噪声 | 同表/术语 30 天内合并为一条；忽略后 90 天不重复提示 |

**回退**：

- 全部能力受 `ONTOLOGY_ENABLED` 与 `ONTOLOGY_APPROVAL_ENABLED` 双开关控制，关闭后回到 M2 行为。
- 健康表可 `TRUNCATE` 重建，不影响任何资产与注入链路。
- 审批动作只改 `status` 与版本快照，回退时按 `ontology_versions` RESTORE 即可。

## 8. 与后续规划的关系

- **P3 图库接入**：M3 完成后以「本体资产规模 + join 类问题占比」为触发条件评估（跨源联邦或单源表数 > 100）；M3 的健康度数据可作为选型输入。
- **P2 OpenTelemetry**：M3 的校验/审批操作建议补 span（`ontology.validate`、`ontology.approve`），与追踪体系一并落地。
