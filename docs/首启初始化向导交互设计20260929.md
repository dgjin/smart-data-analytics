# 首启初始化向导交互设计

> 日期：2026-09-29　状态：**待批准**　目标版本：v0.9.83
> 前置评估：《系统「开箱即用」能力评估报告》（确认 4 个关键断点）
> 关联设计：[数据源接入自动化配置设计20260927.md](./数据源接入自动化配置设计20260927.md)

## 一、背景与设计目标

### 1.1 背景

系统已具备成熟的启动初始化编排（建库建表 → 种子 → 专家角色）与数据源接入自动化配置（Schema 分析 → 能力配置 → 知识骨架），但「开箱即生产可用」仍有 4 个断点：

| # | 断点 | 后果 |
|---|---|---|
| 1 | 两套知识库表割裂：autoConfig 写 `knowledge_base_entries`，RAG 只读 `knowledge_base` | 自动生成的知识永远不被问数检索 |
| 2 | Schema 元数据（表/列/注释）未自动切片向量化 | 新数据源接入后 RAG 检索为空 |
| 3 | 样例库（few-shot）无种子、导入脚本硬编码数据源 ID | 冷启动问数准确率低 |
| 4 | 隐性前提（embedding 模型/待确认铁律/阈值）无引导 | 管理员漏配且无感知 |

本设计定义**首启初始化向导**的交互流程，把上述断点收敛为「登录后一条引导路径」。

### 1.2 设计目标

1. **显性化**：生产可用的隐性前提变成登录后可见、可执行、可验证的步骤；
2. **闭环化**：向导的自动初始化必须真正写入问数检索链路（`knowledge_base` 向量表），而非仅写结构化条目表；
3. **可恢复**：每步可跳过、可稍后、可断点续做，不阻断系统其他功能；
4. **零重复建设**：最大化复用既有模块（健康检查、LLM 探测、autoConfig、知识切块入库、异步任务）。

### 1.3 范围边界

- **做**：模型服务就绪、数据源接入、自动分析+向量入库、样例库种子、待办确认清单、首次问数引导；
- **不做**：组织架构 / 权限 / 监控 / 报告模板（属常规管理配置，不属于「开箱即用」关键路径）。

## 二、触发机制与生命周期

### 2.1 首启判定

- 新增单行状态表 `setup_wizard_state`（结构见 §6.1），随 `initSchema` 幂等创建；首次启动种子写入 `status='pending'`；
- 服务端计算「是否应向当前用户展示」：`status ∈ {pending, in_progress}` 且 `skipped_until` 未到期 且 用户角色 = ADMIN。

### 2.2 三级引导强度

| 级别 | 触发条件 | 形态 | 可关闭 |
|---|---|---|---|
| L1 自动弹出 | 管理员登录且向导未完成 | 全屏向导覆盖层（App 壳之上） | 是（"稍后配置"转入 L2） |
| L2 常驻横幅 | L1 被跳过 / 关闭 / 未完成 | 全局顶栏横幅：`初始化进度 N/5 · [继续配置] [7 天不再提醒]` | 是（7 天内不再显示横幅） |
| L3 常驻入口 | 始终存在 | 系统管理面板顶部卡片「初始化向导」 | 完成后变为「系统体检」 |

- 非管理员：不弹出、不显示横幅；向导完成后 L1/L2 永久消失，仅保留 L3 体检入口；
- 「跳过」与「完成」语义不同：跳过仅隐藏引导，状态仍保留 `in_progress`，随时可继续。

### 2.3 状态机

```
        首次启动
           │
           ▼
      ┌─────────┐  管理员完成全部步骤   ┌───────────┐
      │ pending ├──────────────────────►│ completed │
      └────┬────┘                       └─────┬─────┘
           │ 首次打开向导                     │ 面板入口
           ▼                                  ▼
     ┌────────────┐   稍后配置/关闭     ┌───────────┐
     │ in_progress├────────────────────►│  体检模式  │
     └─────┬──────┘   （L2 横幅提醒）    └───────────┘
           │ 任一步骤执行
           ▼
   步内子状态：未开始 → 执行中 → 成功 / 失败 / 跳过
```

全屏覆盖层（z-50，`bg-slate-950/80` 遮罩 + 居中等宽卡片 `max-w-5xl`，高度 `min(720px, 90vh)`），左右双栏：

```
┌──────────────────────────────────────────────────────────────────────┐
│  🧭 首启初始化向导                                   3/5      [稍后配置]│
├──────────────────┬───────────────────────────────────────────────────┤
│ ① 环境自检    ✅ │   自动初始化流水线                                 │
│ ② 模型服务    ✅ │   ─────────────────────────────────────           │
│ ③ 自动初始化  ●  │   ✓ Schema 元数据采集      42 表 / 613 列   1.2s   │
│ ④ 待办确认    ○  │   ✓ 画像与能力配置         时序 8 / 快照 3   2.4s   │
│ ⑤ 完成引导    ○  │   ● 知识骨架生成           生成中…                 │
│                  │   ○ 知识条目向量入库       待执行                  │
│                  │   ○ Schema 元数据向量入库  待执行                  │
│                  │   ○ 样例库种子             待执行                  │
├──────────────────┴───────────────────────────────────────────────────┤
│ [上一步]                            [跳过此步]        [下一步 →]      │
└──────────────────────────────────────────────────────────────────────┘
```

- 左栏（240px）：步骤轨，五步纵向排列，状态图标四态：`✅ 完成 / ● 进行中 / ○ 未开始 / ⏭ 已跳过`；
- 右栏：步骤内容区（独立滚动）+ 底部操作条；
- 视觉规范：沿用系统暗色主题（slate 层级 + indigo 主色），浅色主题同步适配。

### 3.2 响应式

- ≥1024px：左右双栏；
- <1024px：步骤轨折叠为顶部横向进度条（`当前步标题 · N/5` + 可点击展开），内容区单列全宽。

### 3.3 步骤导航规则

| 步骤 | 进入条件 | 「下一步」可用条件 | 可跳过 | 失败处理 |
|---|---|---|---|---|
| ① 环境自检 | — | 检测完成（允许存在 ❌） | 否（仅展示） | 单项 [重试] |
| ② 模型服务 | — | 对话模型探测通过 或 显式勾选「暂不配置」 | 是 | 探测失败显示错误+修复指引 |
| ③ 自动初始化 | 已有可用数据源 或 本步内完成接入 | 流水线全部子任务结束（成功或跳过） | 是（跳过=不执行） | 子任务级 [重试] |
| ④ 待办确认 | 步骤③完成 | 无硬门槛（「暂不处理」可继续） | 是 | 打开对应面板处理 |
| ⑤ 完成引导 | 步骤③完成 | —（终点） | 否 | — |

> 「跳过此步」按钮在 ①⑤ 不出现；②③④ 出现。

### 3.4 断点续做

- 每步完成/跳过即调用 `POST /api/setup/step` 持久化 `step_results`；
- 重新打开向导：定位到第一个未完成步骤；已完成步骤回显结果快照（可回看，[重跑] 可用）；
- 流水线运行中关闭向导：任务在服务端继续（async_tasks），L2 横幅显示「N/M 子任务完成」，重开向导自动挂载进度。

## 四、步骤详细设计

### Step ① 环境自检（进入即自动执行）

无需点击，进入步骤即并行发起探测（复用 `/api/health/ready` 分级探测机制）：

```
环境自检（自动执行中…）
┌────────────────────────────────────────────────────────┐
│ ✅ 数据库 MySQL          正常                    · 12ms  │
│ ✅ 状态存储 Redis         未启用（单实例模式）            │
│ ✅ 对话模型 Qwen          qwen3.8-max 连通       · 1.4s  │
│ ⚠️ Embedding 模型        未检测到可用模型                │
│    建议：ollama pull bge-m3（否则知识检索将退化为词法）   │
│ ○ 内置演示数据           未加载                          │
└────────────────────────────────────────────────────────┘
          [重新检测]                        [下一步 →]
```

| 检查项 | 探测方式 | 判定标准 |
|---|---|---|
| 数据库 MySQL | readiness 探针 | 必检；❌ 为阻断型（系统不可用） |
| 状态存储 Redis | readiness 探针（外置时必检） | 未启用=✅（单实例模式）；已配置但不可达=❌ |
| 对话模型 | `engineKind()` + 最小 chat 探测 | 连通=✅；无密钥且 Ollama 不可达=❌ |
| Embedding 模型 | `currentEmbedModelId()` + `callEmbedding('ping')` | 返回向量=✅；不可用=⚠️（可降级继续） |
| 内置演示数据 | 查询演示数据源是否存在 | 存在=✅；不存在=○ 信息态（Step③ 提供快速体验入口） |

- ⚠️/❌ 项不阻断「下一步」，但会记入完成页就绪判定与待办清单。

### Step ② 模型服务（LLM + Embedding）

**现状卡（只读，来自 env 探测）**：引擎 / 模型 / 地址 / 密钥状态（仅显示「已配置 / 未配置」，不回显密钥）。

**探测交互（两个独立按钮）**：
- [测试对话] → `POST /api/setup/probe {kind:'llm'}` → 显示：✅ 连通 · 返回「PONG」 · 首 token 1.4s；❌ 失败 → 错误原因 + 修复指引；
- [测试向量] → `POST /api/setup/probe {kind:'embedding'}` → 显示：✅ 可用 · 维度 1024 · 42ms；❌ → 降级警示。

**配置引导（未配置时展开）**：
- 给出可复制的 `.env` 片段（按引擎分模板：Qwen / DeepSeek / Gemini / Ollama）；
- 提示「修改后需重启服务生效」（当前配置体系为 env 驱动）；
- Ollama 场景给出 `ollama pull <模型>` 命令行指引（并提示后续版本将支持启动期自动拉取）。

**关键警示条**（embedding 不可用时常驻琥珀色横幅）：

> ⚠️ Embedding 模型不可用：知识向量检索将退化为词法匹配，问数准确率下降。可稍后在「系统设置」补齐并重跑向导第③步。

### Step ③ 自动初始化（核心步骤）

**前置：目标数据源**。两种路径：

```
选择数据源                     ← 若系统已有数据源，顶部显示「已检测到 N 个可用数据源」
┌─────────────────────────┐  ┌─────────────────────────┐
│  接入我的数据源           │  │  加载演示数据集（可选）    │
│  类型/主机/端口/库/       │  │  在应用库中创建演示表      │
│  账号/密码 → [测试连接]   │  │  并自动注册数据源         │
│  [保存并继续]             │  │  [一键加载]（Phase 2）    │
└─────────────────────────┘  └─────────────────────────┘
  ↑ 复用 POST /api/datasources/test-connection（现有）
  ↑ 复用 POST /api/datasources（现有，自动触发 autoConfig）
```

**流水线子任务（点 [开始执行] 后实时推进）**：

| # | 子任务 | 实现 | 产出 | 断点闭环 |
|---|---|---|---|---|
| 1 | Schema 元数据采集 | 复用 `extractDbSchema` / `schemaAnalyzer` | 表/列/注释/角色（指标/维度） | — |
| 2 | 画像与能力配置 | 复用 autoConfig（时序/快照/版本识别） | `anomaly_capabilities_json` | — |
| 3 | 知识骨架生成 | 复用 autoConfig → `knowledge_base_entries` | N 条结构化条目 | — |
| 4 | **知识条目向量入库** | 【新增】entries → `saveKnowledgeDoc`（确定性 doc_id 幂等） | `knowledge_base` M 切片 | ✅ 断点 1 |
| 5 | **Schema 元数据向量入库** | 【新增】每表切一块（表名+注释+列名+列注释+角色）→ embedding | `knowledge_base` K 切片 | ✅ 断点 2 |
| 6 | 样例库种子 | 【新增】写入通用 few-shot 语法范式样例（不绑定数据源） | `sql_examples` J 条 | ✅ 断点 3 |

**进度 UI（wireframe 见 §3.1 右栏）**：每子任务一行 — 状态图标 + 名称 + 计数摘要（`42 表 / 613 列`、`M 切片`）+ 耗时；失败行内联展开错误详情 + [重试该子任务]；embedding 不可用时子任务 4/5 标 ⚠️ 跳过（不阻断后续）并写入待办清单。

**技术机制**：
- `POST /api/setup/pipeline {dataSourceId}` → 创建 `async_tasks` 任务 → 返回 `taskId`；前端 2s 轮询 `GET /api/setup/pipeline/:taskId`；
- 幂等性：doc_id / entry_id 确定性生成（如 `ds:{dsId}:schema:{table}`），重复执行覆盖而非重复插入；
- 部分失败策略：单子任务失败不自动重试，等人工点 [重试]；已成功子任务不重跑。

### Step ④ 待办确认清单

动态清单（`GET /api/setup/checklist`），每项 = 状态 + 一句说明 + 一键深链：

| 待办项 | 数据来源 | 动作（深链） |
|---|---|---|
| 铁律模板待确认 N 条 | `iron_rules` status=PENDING | [去确认] → 系统管理 · 规则治理 |
| 语义指标阈值未启用 | `domainThresholds.enabled=false` | [去配置] → 指标治理面板 |
| Embedding 未就绪（若降级） | 环境探测结果 | [重新探测]（回 Step②） |
| 业务知识补充（可选） | `knowledge_base_entries` 计数 | [下载模板 / 导入] → 业务知识库面板 |
| 样例库为空（若跳过） | `sql_examples` 计数 | [去导入] → SQL 样例库面板 |

- 全部「已处理」或点 [暂不处理，稍后在系统管理中完成] → 可继续；
- 未处理项持续在 L2 横幅下拉与「系统体检」卡片中列出。

### Step ⑤ 完成引导

**就绪判定表**：

| 判定项 | 达标标准 | 未达标影响 |
|---|---|---|
| 对话模型 | 探测通过 | 🔴 问数不可用（阻断） |
| 数据源 | ≥1 个连通且已完成流水线 | 🔴 无数据可问（阻断） |
| 知识向量化 | `knowledge_base` 切片数 > 0 | 🟡 检索退化为词法（降质） |
| 样例库 | ≥1 条 few-shot | 🟡 冷启动准确率偏低（降质） |

**总结卡**：本次初始化成果数字 — 数据源 N 个 · 表 T 张 · 知识条目 E 条 · 向量切片 M 条 · 样例 J 条。

**CTA**：
- [试问第一个问题] → 关闭向导，跳转问数页并预填一条示例问题（演示数据场景用演示问题；自有数据源场景用「统计各表行数」类通用问题）；
- [进入系统] → 关闭向导。

任一 CTA → `POST /api/setup/complete` → `status='completed'`。

## 五、常驻引导

### 5.1 L2 横幅（未完成时）

位置：Header 下方（与现有 OfflineBanner 同层级），琥珀色：

```
⚙ 系统初始化进度 3/5 · 自动初始化流水线执行中（4/6 子任务）  [继续配置]  [7 天不再提醒]
```

- 流水线后台运行时，横幅实时显示子任务进度；
- 「7 天不再提醒」→ `POST /api/setup/skip {days:7}`，设置 `skipped_until`。

### 5.2 L3 入口（系统管理面板卡片）

- 未完成：「初始化向导」卡片（同 L2 信息 + [继续配置]）；
- 已完成：变为「系统体检」卡片 — 最近检查时间 + 各检查项三态 + [重新检测]（重跑环境自检与就绪判定，不自动重复执行流水线）。

## 六、状态与接口设计

### 6.1 状态表

```sql
CREATE TABLE IF NOT EXISTS setup_wizard_state (
  id TINYINT PRIMARY KEY,                          -- 恒为 1（单行表）
  status VARCHAR(20) NOT NULL DEFAULT 'pending',   -- pending | in_progress | completed
  current_step TINYINT NOT NULL DEFAULT 0,         -- 0..4
  step_results JSON NULL,                          -- 各步骤结果快照：{"0":{...},"2":{...}}
  pipeline_task_id VARCHAR(64) NULL,               -- 最近一次流水线任务 id
  skipped_until TIMESTAMP NULL,                    -- L2 横幅静默截止
  started_by VARCHAR(50) NOT NULL DEFAULT '',
  completed_at TIMESTAMP NULL,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
```

### 6.2 API 契约（全部 `requireRole('ADMIN')` + rateLimiter）

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| GET | `/api/setup/state` | — | `{status, currentStep, stepResults, env:{llm,embedding,datasources,health}}` |
| POST | `/api/setup/step` | `{step, result}` | `{ok}` |
| POST | `/api/setup/probe` | `{kind:'llm'\|'embedding'}` | `{ok, engine?, model?, latencyMs?, dims?, error?}` |
| POST | `/api/setup/pipeline` | `{dataSourceId}` | `{taskId}` |
| GET | `/api/setup/pipeline/:taskId` | — | `{status, subtasks:[{key,label,state,counters,error,ms}]}` |
| GET | `/api/setup/checklist` | — | `[{key,title,detail,status,link}]` |
| POST | `/api/setup/skip` | `{days}` | `{ok}` |
| POST | `/api/setup/complete` | — | `{ok}` |
| POST | `/api/setup/demo-data` | — | `{taskId}`（Phase 2） |

## 七、异常与边界

| 场景 | 处理 |
|---|---|
| 向导中刷新页面 | 从 `GET /api/setup/state` 恢复：回到 `current_step`，回显已存结果 |
| 流水线运行中断网 | 服务端任务继续；前端重连后按 taskId 续拉进度 |
| 多管理员并发 | 状态为全局单行；后来者见「向导最近更新于 …」，可接管继续 |
| Embedding 不可用 | 子任务 4/5 跳过 + 待办警示；系统按既有降级链（bigram 词法）运行 |
| LLM 未配置走完向导 | 允许完成，但完成页标红「问数不可用」；L2 横幅持续提示 |
| 重复执行流水线 | 幂等（确定性 ID 覆盖），界面提示「本次为增量刷新」 |
| 数据源在向导期间被删除 | 流水线子任务失败 → 提示回到数据源选择重新接入 |
| 向导完成后再接新数据源 | 不重新弹向导；新数据源仍走 autoConfig，体检卡片提示「可运行向量入库」（后续版本可自动化） |

## 八、与评估断点的闭环对应

| 断点 | 向导落地方式 |
|---|---|
| 1 两表割裂 | Step③ 子任务 4：entries → saveKnowledgeDoc → knowledge_base（确定性 doc_id 幂等） |
| 2 Schema 未向量化 | Step③ 子任务 5：每表一块（表名+注释+列+角色）embedding 入库 |
| 3 样例库无种子 | Step③ 子任务 6：通用语法范式 few-shot 种子；Step④ 可补充导入 |
| 4 隐性前提无引导 | Step①②④ 显性化 + L2 横幅 + 体检模式持续跟踪 |

## 九、分期实施建议

| **Phase 1（P0 闭环）** | 状态表 + `/api/setup/*` 路由 + 流水线子任务 4/5/6 后端改造 + 向导骨架（Step①②③⑤）+ L2 横幅 | 无（可先行） |

## 十、验收标准

1. 全新部署 → 管理员首登 → 向导自动弹出，环境自检 5 项正确反映实际状态；
2. 未配置 LLM 时：Step② 明确报错与修复指引；走完向导后完成页标红「问数不可用」；
3. 接入新数据源 → 流水线 6 子任务全部推进 → `knowledge_base` 出现该数据源的切片（SQL 可验证）；
4. 完成后再问数：`query_trace` 中 RAG 命中数 > 0（修复前为 0）；
5. 点 [稍后配置] → L2 横幅出现；点 [7 天不再提醒] → 横幅消失且 7 天后恢复；
6. 向导中途刷新页面 → 恢复到当前步骤且已存结果显示；
7. 流水线子任务失败 → 行内显示错误 + [重试] 仅重跑该子任务；
8. 向导完成后 → L1/L2 永久消失，系统管理面板显示「系统体检」卡片。
