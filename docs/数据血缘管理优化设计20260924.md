## 1. 背景与目标

### 1.1 现状

「数据源与 Schema」页的**血缘子视图**（DataLineageView）当前是一个**静态声明式**的三列展示：接入源层 → 逻辑提炼算子层（两个硬编码节点：NL2SQL 引擎、特征清洗算子）→ 终端导向层（决策简报、固化监控图表）。血缘依据仅为报表/图表绑定的 `dataSourceId`，中间算子层与真实数据加工无关，无法回答"哪张表被哪些报表消费""改一个字段会影响什么"等治理问题。

### 1.2 目标

按业界最新的血缘管理理念（见第 2 节），将血缘视图从"一张静态示意图"升级为**可查询、可操作的真实血缘系统**：

1. **真实采集**：从系统内已落库的 SQL（报表 `executedSqls`、图表 `sourceSql`、指标 `expr`）自动解析出表级血缘，替代人工推断。
2. **影响分析**：任何数据源/表节点一键得到下游"爆炸半径"清单（受影响的报表、图表、指标及数量）。
3. **可信度可视**：每条血缘标注来源类型（自动解析 / 人工声明）、验证时间与失效状态（引用的表已不存在）。
4. **业务血缘**：语义指标（`metric_definitions`）作为一等节点进入血缘图，连通"表 → 指标 → 消费物"。
5. **体验升级**：全景 / 聚焦双视图 + 搜索过滤，避免"全部视图"不可读（业界公认的血缘项目失败首因）。

### 1.3 技术选型与边界

**已确认选型**：引入 `@xyflow/react` v12（当前 12.11.6，兼容 React 19，内置深色模式）构建交互式血缘画布，替代现有静态三列布局；自定义节点与边复用项目主题体系。

**不做的事**：

- 不引入 dagre / elk 布局库（图固定四层结构，手写分层布局纯函数即可，且便于单测）；
- 不新建血缘持久化表（P0 采用服务端内存聚合，避免 schema 迁移与同步一致性问题）；
- 不改变现有权限模型（血缘视图维持仅 ADMIN 可见，同页其他子视图一致）；
- 不做 OpenLineage 事件级实时血缘流（超出本系统单体规模）。

## 2. 理论基线：2026 血缘管理七大最佳实践

来源：Datadef《Data Lineage Best Practices: 7 Rules》(2026)、DataHub《Where Lineage Lives》(2026)、OpenLineage 规范、阿里云 DataWorks 算子级血缘实践。

| # | 业界实践 | 本系统落地 |
|---|---|---|
| 1 | **从关键资产开始**，不追求全量覆盖 | 血缘范围 = 本系统全部"Gold 资产"：数据源表、决策简报、固化图表、语义指标 |
| 2 | **每条资产有 Owner 与新鲜度** | 边记录带上游数据源 `lastSyncedAt` 作为验证时间基准；消费物显示创建人 |
| 3 | **自动采集 + 人工治理** | 自动解析已落库 SQL（parsed 边）；无 SQL 时保留 dataSourceId 声明式绑定（declared 边，标记待验证） |
| 4 | **列级血缘用在决策需要处** | P1：`node-sql-parser` AST 提取 SQL 列引用，支撑"改这个字段影响哪些报表" |
| 5 | **敏感标签沿血缘传播** | P2：导入时已剔除的敏感列在血缘中标记并沿边提示 |
| 6 | **影响分析成为强制步骤** | 影响分析面板即"一键爆炸半径"：选表 → 下游全量清单，支持复制用于变更评审 |
| 7 | **定期重新验证（血缘会腐烂）** | 每次加载对比当前 Schema 做 stale 检测；图顶部展示解析覆盖率与失效边统计 |

> 业界"可操作性"验收标准（One-Click Blast Radius Test）：点击任何节点即可看到其下游消费者 —— 本设计的 P0 即达到此标准。

## 4. 总体设计

### 4.1 血缘模型

#### 节点（LineageNode）

```ts
type LineageNodeType = 'datasource' | 'table' | 'metric' | 'report' | 'widget';

interface LineageNode {
  id: string;              // 'ds:<dsId>' | 'tbl:<dsId>:<table>' | 'metric:<id>' | 'report:<reportId>' | 'widget:<widgetId>'
  type: LineageNodeType;
  label: string;           // 展示名（表用原始表名，指标/报表用中文名）
  dataSourceId?: string;   // 归属数据源（table/metric/report/widget 均有）
  meta?: {
    tableType?: string;        // TABLE / VIEW / MATERIALIZED_VIEW …
    expr?: string;             // 指标表达式
    metricStatus?: string;     // ACTIVE / DISABLED / 审批状态
    chartType?: string;        // 图表类型
    templateType?: string;     // 报表模板
    createdAt?: string;
  };
}
```

#### 边（LineageEdge）

```ts
type LineageEdgeKind = 'contains' | 'consumes' | 'derives';

interface LineageEdge {
  id: string;
  from: string;                    // 上游节点 id
  to: string;                      // 下游节点 id
  kind: 'contains'   // datasource → table（结构包含）
      | 'consumes'   // table → report / widget（SQL 解析）
      | 'derives';   // table → metric（指标定义基于表）
  sourceType: 'parsed' | 'declared';  // parsed=SQL 解析（高可信）；declared=人工绑定（待验证）
  evidence?: string;               // 证据：'report.executedSqls[2]' / 'widget.sourceSql' / 'metric_definitions.expr'
  lastVerifiedAt?: string;         // 验证时间：数据源 lastSyncedAt / 消费物创建时间
  status: 'active' | 'stale';      // stale=引用的表在当前 Schema 中不存在
}
```

> 该模型对齐业界审计六要素（Asset / Upstream / Transformation / Owner / Last verified / Sensitivity）：P0 落地 Asset、Upstream、Transformation、Last verified；Owner 与 Sensitivity 在 P1/P2 补充。

### 4.2 采集层设计（服务端）

新增 `server/lineage/` 目录：

| 文件 | 职责 |
|---|---|
| `graph.ts` | **纯函数** `buildLineageGraph(input)`：输入各表行数据，输出 `{ nodes, edges, stats }`。解析入库 SQL 得到边，与当前 Schema 比对得出 stale，可完全单测 |
| `service.ts` | 从 MySQL 拉取数据源/报表/图表/指标行数据，组装输入，带 30s 进程内 TTL 缓存 |
| `sqlRefs.ts` | SQL → 表名集合：复用 `sqlExecutor.extractTableRefs` 的正则思路抽取为独立函数（服务端权威口径），表名与数据源 Schema 匹配时大小写不敏感 |

**解析规则（P0）**：

1. `saved_reports`：对 `report_data.executedSqls[]` 逐条 `extractTableRefs` → `table →consume→ report` 边，evidence 标注索引；
2. `dashboard_widgets`：对 `widget_data.sourceSql` → `table →consume→ widget` 边；
3. `metric_definitions`：`table_name` 直接建边 `table →derive→ metric`（解析状态同时校验 `expr` 中的表引用做补充）；
4. 兜底（declared）：报表/图表/指标解析不到表时，按 `data_source_id` 建 `datasource →consume→ 消费物` 声明边，`sourceType='declared'`；
5. stale 检测：边引用的表不在该数据源当前 `tables` 清单中 → `status='stale'`。

**stats 口径**：`nodes / edges / parsedEdges / declaredEdges / staleEdges / parseCoverage`（parsedEdges ÷ (parsedEdges + declaredEdges)，图顶部展示）。

### 4.3 API 契约

```
GET /api/lineage/graph        # authMiddleware + requireRole('ADMIN')（仅管理员，与页面权限一致）
响应 200:
{
  "success": true,
  "generatedAt": "2026-09-24T10:00:00.000Z",
  "stats": { "nodes": 42, "edges": 87, "parsedEdges": 61, "declaredEdges": 26,
             "staleEdges": 2, "parseCoverage": 0.70 },
  "nodes": [ ...LineageNode ],
  "edges": [ ...LineageEdge ]
}
```

- 失败（DB 不可用等）返回 500 + 标准错误码，前端自动降级（见 4.6）；
- 同步更新 `docs/openapi.json`（CI `docs:check` 会校验）；
- 路由挂载 `server.ts`，复用 `requestLogger` / 统一错误码。

### 4.4 前端设计

#### 4.4.1 数据获取与降级

```
useEffect 拉取 /api/lineage/graph
 ├─ 成功 → 使用服务端图（权威）
 └─ 失败 → 降级：保留现有本地三列推导逻辑（getReportUpstreamDS / getWidgetUpstreamDS 三级兜底）
          顶部显示「血缘服务暂不可用，当前为本地声明式估算」提示条
```

#### 4.4.2 画布与分层布局（React Flow）

- **依赖**：`@xyflow/react` v12（已确认兼容 React 19；v12 内置 `colorMode` / Controls / MiniMap / Background）；引入官方 `style.css`；
- **分层布局**（纯函数 `layoutLineageGraph`，可单测）：
  - 层分配：数据源 = 0，表 = 1，语义指标 = 2，报表/图表 = 3（x 坐标 = 层序 × 340）；
  - 同层排序：数据源按名称；表按「上游数据源聚簇 + 名称」；消费物按「报表先于图表 + 创建时间倒序」，减少边交叉；
  - y 坐标 = 同层序号 × 76（验证后调优：原 96 使默认全图 fitView 缩放偏小，详见 §9）；预期规模 < 120 节点（超过 150 节点时顶部提示，P1 再做折叠优化）；
- **表节点口径**：仅展示"被消费的表"（出现在血缘边中的表）；数据源节点显示「共 M 表 · 已引用 K 表」计数——未引用表不上画布，避免噪音（对齐"关键资产优先"理念）；
- **自定义节点** `LineageNodeCard`：类型着色（数据源 indigo / 表 cyan / 指标 fuchsia / 报表 emerald / 图表 amber），含图标、标题、副标题（表名/表达式/模板）与血缘徽标；左接入 / 右输出 handle；
- **边样式**（按属性区分，自定义绘制）：`parsed` 实线（consumes emerald / derives fuchsia / contains slate 细线）、`declared` 琥珀虚线、`stale` 红色 + 警示图标；悬停/选中时同族边加粗高亮。

#### 4.4.3 交互设计

1. **悬停高亮**：hover 节点 → 计算该节点上下游闭包 → 闭包内节点与边高亮、其余降透明度（行为等价替代原三列高亮）；
2. **点击聚焦**：点击节点 → 右侧影响分析面板打开，画布 `fitView` 到该节点邻域；面板内「只看相关链路」开关可将画布过滤为以选中节点为中心的上下游闭包子图（`Esc` / 重置按钮恢复全景）；
3. **影响分析面板（爆炸半径）**：
   - 受影响报表 N 个 / 图表 M 个 / 指标 K 个（三类计数卡）；
   - 逐项清单：名称 + 血缘来源（解析/声明）+ 验证时间 + 失效警示；点击清单项画布跳转并居中该节点；
   - 「复制影响清单」按钮（纯文本，供变更评审粘贴）；
4. **搜索与过滤**：搜索框（节点名模糊匹配 → 匹配节点脉冲高亮 + fitView 定位）+ 类型过滤 chips（表/指标/报表/图表），非命中节点变暗而非隐藏（保留图结构可读性）；
5. **画布控件**：Controls（缩放/适配）、MiniMap（按类型着色）、点阵 Background、初始 `fitView`；
6. **统计条**：`节点 42 · 边 87 · 解析覆盖率 70% · 失效边 2`，覆盖率 < 60% 时琥珀色提示"建议补全 SQL 来源"。

#### 4.4.4 新增纯函数模块（可单测）

`src/utils/lineageGraph.ts`：

- `buildIndex(graph)`：邻接表索引；
- `upstreamClosure(graph, nodeId)` / `downstreamClosure(graph, nodeId)`：上下游闭包（BFS，含环保护）；
- `impactSummary(graph, nodeId)`：爆炸半径清单（分类计数 + 明细行）；
- `matchNodes(graph, query, types)`：搜索过滤；
- `layoutLineageGraph(nodes, edges)`：分层布局坐标计算（层分配 + 同层排序 + 去重叠）；
- `toFlowGraph(nodes, edges, ctx)`：领域图 → React Flow `Node[]` / `Edge[]`（含选中 / 匹配 / 变暗视觉状态）。

### 4.5 主题与规范

- 画布 `colorMode` 跟随 `UI_THEME_EVENT`（dark/light）；自定义节点与边仅复用现有色系（indigo/cyan/fuchsia/emerald/amber/rose/slate），**不新增色系**（避免 `index.css` 的 `html.light` 翻转表补录）；
- React Flow 默认样式中的浮层（Controls / MiniMap）在浅色主题下用 `html.light` 局部覆盖；
- 文案全中文，注释遵循项目规范；
- 组件拆分为 `src/components/datasource/lineage/`（画布 / 节点卡片 / 影响面板），`DataLineageView.tsx` 退化为容器（数据获取、降级、统计条、搜索状态）；
- 日志服务端走 `logger` 门面；血缘构建失败 fail-open（返回局部图或 500，绝不影响其他页面）。

### 4.6 兼容与不变量

- 现有三级兜底推导（`w.dataSourceId` → `resolveNpaDataSource` 推演 → 首个数据源）保留为降级路径，**不删除**；
- `DEFAULT_NPA_WIDGET_IDS` / `resolveNpaDataSource` 仍供降级与 seed 语义使用；
- 现有交互修复不回归：叠层不推挤布局、窄屏不横向滚动、reset 按钮常驻占位。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 报表/图表无 SQL（simulated 或旧数据） | 解析不到边 | declared 声明边兜底 + 徽标区分 + 覆盖率统计提示 |
| 表名大小写/别名差异导致误判 stale | 误报失效 | 比对大小写不敏感；仅当表中存在任何匹配时才判 active 之外的 stale |
| 图数据量随报表增长 | 前端渲染压力 | P0 规模（数十节点）无虞；服务端 TTL 缓存；搜索过滤缓解 |
| 降级路径与新路径行为不一致 | 用户体验割裂 | 降级时显式提示条说明"本地估算" |
| 血缘 API 暴露跨用户报表 | 权限边界 | 维持 ADMIN 可见；API 用 authMiddleware 且不返回报表业务数据（仅 id/标题/类型） |
| React Flow 包体积（约 50KB gzip） | 主包增大 | 内部系统可接受；如后续敏感再改 `React.lazy` 按需加载画布 |
| React Flow 默认样式与浅色翻转不匹配 | 浅色主题下浮层观感差 | `colorMode` 跟随主题 + `html.light` 局部覆盖；端到端验证含浅色一轮 |
| 分层布局在同层节点多时拥挤 | 可读性下降 | 同层排序减交叉 + MiniMap 导航；节点 >150 顶部提示（P1 折叠优化） |

## 9. 端到端验证与验证后调优（2026-09-24）

浏览器单轮验证结论：主链路（统计条 / 悬停闭包高亮 / 点击聚焦 + 影响面板 / 复制清单 / 搜索与类型过滤 / 浅色主题 / 降级）全部通过，控制台无错误。验证发现的 4 项视觉问题及修复：

| 问题 | 根因 | 修复 |
|---|---|---|
| 迷你地图无节点（空框） | React Flow 12 受控模式（未接 `onNodesChange`）不会把节点 measured 回填到 userNode，MiniMap 按 userNode 尺寸判定节点可见性 → 全部跳过 | `toFlowGraph` 为节点声明固定几何 `width: 260 / initialHeight: 52`（预测量与 MiniMap 兜底） |
| 浅色主题下变暗节点几乎不可见 | dimmed 透明度 25% 在浅底上对比度不足 | dimmed 提升至 40%（仍明确让位于命中节点，保留图结构可读性） |
| 复制成功提示滚出视口 | toast 相对整张卡片绝对定位（卡片高于视口） | 改为视口底部居中浮层（fixed），始终可见 |
| 初始 fitView 缩放偏小、文字不可读 | 行距 96 使指标列高约 1100px，成为缩放瓶颈 | 行距 96 → 76（列高约 890px），初始缩放约 0.48 → 0.62 |
