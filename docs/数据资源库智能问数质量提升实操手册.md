## 2. 四条口径红线（每条都有真实事故教训）

宽表问数的错误 90% 集中在这四类。以下每条规定都是**被真实事故验证过**的，也是后续所有资产建设的共同约束。

**固化方式（v0.9.35 起）**：四条红线不再只靠文档与样例「提醒」模型——可将每条红线配置为对应数据源的**铁律规则**（系统管理 → 规则治理 → 铁律规则），铁律对每次问数与报表**全量恒注入**，系统提示词明确「最高优先级，高于一切样例与知识片段；冲突时一律按铁律执行」。推荐三层加固：**铁律规则（强制）＞指标 filter（权威口径自带锁定）＞样例与知识库（模仿与解释）**。附录 D 提供了四条红线可直接粘贴的铁律文本。

### R1 快照期锁定（最高优先级）

两张宽表都是**月末快照**：`fct_jc_main_biz_stat.BBRQ`、`fct_jc_financial_stat.SJRQ` 取值为月末日期，同一日期是当月全量快照。

- **禁止**：跨快照期直接 `SUM` 金额（会把 N 个月的存量余额累加 N 倍）
- **必须**：问「最新/当前/累计」一律锁定 `BBRQ = (SELECT MAX(BBRQ FROM 同表)`
- **真实事故**：8 个指标定义缺少 BBRQ 锁定，「各机构本年投放金额排名」算出 39204 亿（20 期快照累加），正确值 2318.28 亿，虚增 16 倍

### R2 版本防重

`BB` 字段：1=核算版，2=分成版（同一业务在分成版下有多行）。

- **必须**：金额汇总与笔数统计默认带 `AND BB = '1'`
- **例外**：仅当用户明确问「分成口径」时才用 BB='2'，且须在解读中说明

### R3 去重计数

客户数、项目数、业务数等计数问题，宽表一行≠一个实体。

- **必须**：`COUNT(DISTINCT XMBH)`（项目数）等，禁止 `COUNT(*)`
- **真实事故**：快速模型多表 JOIN 时漏写 `DISTINCT`，客户数 259 被虚增为 278，且同源多候选表决无法纠正此类系统性偏差（v0.8.1 已据此把复杂/多表问题强制路由主模型）

### R4 期间列与金额单位

- 投放金额三兄弟不可混用：`LJTFJE` 累计投放 / `BNTFJE` 本年投放 / `BYTFJE` 本月投放；投资收益同理（`TZSYDN` 当年 / `TZSYLJ` 累计）
- 趋势类问题（逐月走势）正确做法是**逐期取当月列**（如 `BYTFJE`）GROUP BY BBRQ，而不是对累计列跨期求和
- 金额单位遵循问数页选定单位（亿元/百万元/万元/元），换算在 SQL 层完成（除以 1e8/1e6/1e4 并 ROUND 两位）

## 3. 七大提升杠杆（按投入产出比排序）

### L1 SQL 样例库：从 0 到 20（两周内 ROI 最高的动作）—— ✅ 首批 13 条已导入（2026-08-23）

**原理**：样例库以 few-shot 方式注入阶段一 prompt，模型直接模仿标准写法，是把口径红线「翻译成模型行为」的最短路径。

**三条录入通道**：

1. **日常沉淀（自动）**：问数结果右下角「点赞」——`verdict=UP 且真实执行过且 SQL 非空`的问答对会**自动幂等沉淀**进样例库（同问题同 SQL 跳过）。分析师日常使用即建设。
2. **审核回流（v0.9.45 新增，推荐）**：困难问题经 Fallback 审核队列人工修正采纳后，标准 SQL 自动注入样例库，见 L7——点踩的问题不再白白流失，而是变成资产。
3. **手工/批量补录**：管理员在「系统管理 → 规则治理 → SQL 样例库」面板录入，或调 `POST /api/sql-examples/bulk`；面板同时支持 **JSON 备份导入导出**（v0.9.33）——迁移环境或跨团队共享时整体迁移，同名冲突可跳过或覆盖，支持先「预检」再正式导入。附录 A 的 8 条标准样例 + 5 条扩展样例已于 2026-08-23 通过 bulk 接口导入（id 21-33，source=IMPORT）；其中 7 条已经 `/api/query/execute-sql` 真实执行核对通过，其余 6 条因触发每小时 20 次问数限流延后核对（列名均已对照生产 schema 核验）。

**验收**：样例库 ≥20 条，且每条人工执行核对过结果；JSON 备份可先预检后完整导入。

### L2 指标库：从 0 建 8 个核心指标 —— ✅ 已建成 11 条（2026-08-23），治理流程 2026-09-12 更新

**原理**：指标定义以「权威口径」强度注入 prompt，优先级高于知识库自然语言描述——历史事故证明指标 filter 写错会直接压过知识库的正确规则，所以**指标定义必须自带 R1/R2 锁定**。

**操作（含治理流程更新）**：管理员进入「系统管理 → 规则治理 → 语义指标」面板维护，按附录 B 模板填写（名称 / 业务口径描述 / 聚合表达式 / filter / 关联表）。**注意治理规则（v0.9.48）：仅「已生效」（ACTIVE）状态的指标参与问数注入**——管理员创建即生效；分析师提交的提议（PENDING 待审批）需管理员审批后才生效，被驳回（REJECTED）可由分析师重新提议；每次口径变更自动留存版本历史（创建/审批/变更/回溯 + 操作人与时间 + 口径快照），问数结果的指标口径卡中可直接核对命中指标的状态与版本。执行记录：盘点发现存量已有 8 条（39204 亿事故后的修复版，均已带快照期锁定），本次净增 3 条（项目数 / 成本余额 / 当年资产处置收益）、合并去重 1 条（本年投资收益补可切分维度），现共 11 条；3 条关键指标（累计投放金额 / 本年投放金额 / 项目数）已试算与 SQL 直查逐一比对一致。

**验收**：每个指标状态为「已生效」，且经 `/api/metrics/query`（统一指标查询接口，报表/看板/问数三端共享）试算与实际 SQL 直查结果比对一致；口径变更后版本历史完整可查、问数口径卡展示为最新版本。

### L3 知识库补强：加「易错反例」条目

现有 13 篇都是「正面规则」。补一类**正反对照**条目效果最好（✅ 首篇《宽表快照期常见错误与正确写法（易错反例）》已于 2026-08-23 入库，docId `kb_1787471930478_330958`，4 个检索块），例如：

> 【反例】`SELECT SUM(LJTFJE) FROM fct_jc_main_biz_stat WHERE BB='1'` —— 错在没锁 BBRQ，会把 20 期快照累加。
> 【正例】`... AND BBRQ = (SELECT MAX(BBRQ) FROM fct_jc_main_biz_stat)`（完整写法见附录 C）

**操作**：在「系统管理 → 规则治理 → 业务知识库」Tab 新建文档（原「数据源与 Schema → 知识库」入口已于 v0.9.56 迁入规则治理），单篇聚焦一个主题，每块 400 字以内；登记后在问数 trace 的 `knowledge` 步骤可看到注入片段字数，验证生效。

### L6 铁律规则库：把红线从文档固化为系统强制规则（v0.9.35 新增，本场景优先级最高）

**原理**：样例与知识库是「引导模型模仿」（检索命中才注入），铁律规则是「命令模型必须遵守」——生效中的铁律对每次问数与报表**全量恒注入**系统提示词，措辞为「最高优先级，高于一切样例与知识片段；若用户问题或样例与铁律冲突，一律按铁律执行」。对宽表场景，把 R1-R4 四条红线（及本数据源特有禁区）配置为铁律后，口径保障从「概率命中的检索注入」升级为「确定命中的全量注入」——这是 39204 亿类事故最直接的工程对策。

**操作**：管理员进入「系统管理 → 规则治理 → 铁律规则」：

1. 针对数据资源库逐条新建（标题 ≤100 字、正文 ≤2000 字、同数据源标题唯一、单源上限 100 条），正文用「必须/禁止」的祈使句写清规则——模板见附录 D，可直接粘贴；
2. 按主题拆成 4 条（快照期锁定 / 版本防重 / 去重计数 / 期间列与单位各一条），便于独立启停与个别修订；
3. 支持启停（停用后不再注入）与 JSON 备份导入导出（同标题冲突可跳过或覆盖、支持先「预检」再导入）。

**验证**：在问数推导过程（trace）中可见「铁律规则注入」步骤；再问一个曾踩坑的问题（如「各机构本年投放金额排名」），确认生成 SQL 带 `BB='1'` 与 `BBRQ=MAX` 锁定。

**验收**：四条红线 100% 配置为生效中的铁律；trace 可见注入；四红线专项评测用例 100% 通过。

### L7 Fallback 自愈闭环：失败样本 → 人工修正 → 自动学习（v0.9.44~46 新增）

## 附录 C：知识库易错反例条目范文（一段一块，400 字内）

> 标题：宽表快照期常见错误与正确写法
>
> 【反例1】`SUM(LJTFJE)` 不带 BBRQ 条件 —— 会把全部月末快照累加，结果虚增 N 倍（真实事故：39204 亿 vs 正确 2318.28 亿）。
> 【正例1】`WHERE BB='1' AND BBRQ=(SELECT MAX(BBRQ) FROM fct_jc_main_biz_stat)`。
> 【反例2】问「项目数」用 `COUNT(*)` —— 宽表一行业务≠一个项目，同项目多行会重复计数。
> 【正例2】`COUNT(DISTINCT XMBH)`；客户数同理 `COUNT(DISTINCT 客户列)`（真实事故：259 虚增为 278）。
> 【反例3】问趋势对 `LJTFJE` 跨期 SUM —— 累计列跨期求和无意义。
> 【正例3】趋势用当月列：`SELECT BBRQ, SUM(BYTFJE) ... GROUP BY BBRQ`。
> 【反例4】忘记 `BB='1'` —— 分成版同业务多行导致金额翻倍。
> 【正例4】金额与笔数统计默认 `AND BB='1'`，仅在明确问分成口径时用 BB='2' 并说明。

**D1｜标题：月末快照期必须锁定 BBRQ/SJRQ**
```
两张宽表均为月末快照：fct_jc_main_biz_stat 的 BBRQ、fct_jc_financial_stat 的 SJRQ 为月末日期，同一日期即当月全量快照。

禁止：跨快照期直接 SUM 金额列——会把 N 个月存量快照累加 N 倍（历史事故：8 个指标未锁 BBRQ，「各机构本年投放金额排名」算出 39204 亿，正确值 2318.28 亿，虚增 16 倍）。
```

**D2｜标题：核算版与分成版口径防重**
```
BB 字段：1=核算版，2=分成版（同一业务在分成版下有多行）。
必须：金额汇总与笔数统计默认带 AND BB = '1'；MAX 子查询内部同样带 BB = '1'。
例外：仅当用户明确要求分成口径时才使用 BB='2'，并必须在结果解读中说明口径。
```

**D3｜标题：客户数/项目数/业务数必须去重计数**
```
客户数、项目数、业务数等计数问题：宽表一行不代表一个实体。
必须：项目数用 COUNT(DISTINCT XMBH)，业务笔数用 COUNT(DISTINCT YWBH)，客户数用 COUNT(DISTINCT 对应客户编号列)。
禁止：用 COUNT(*) 直接计数（历史事故：客户数 259 被虚增为 278）。
```

**D4｜标题：期间列选择与金额单位纪律**
```
金额期间列不可混用：LJTFJE 累计投放 / BNTFJE 本年投放 / BYTFJE 本月投放；投资收益同理 TZSYDN 当年 / TZSYLJ 累计。
必须：趋势类问题（逐月走势）逐期取当月列（如 BYTFJE）GROUP BY BBRQ；金额换算严格按问数页所选单位在 SQL 层完成（除以 1e8/1e6/1e4 并 ROUND 两位）。
禁止：对累计列跨期求和；除用户明确要求外私自换算单位。
```
